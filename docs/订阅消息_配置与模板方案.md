# 订阅消息 · 配置与模板方案

> 本文由以下四份文档合并而成（详见「原始文档清单」）：`订阅消息配置.md`、`订阅消息模板使用方案_2026-09-12.md`、`订阅消息模板清理建议_2026-09-12.md`、`方案对比_2026-09-15_匿名互动触达通道.md`。

## 概述

- 这组文档覆盖 **2026-09-12 ~ 2026-09-15** 期间的订阅消息配置、模板选型/清理、服务端与前端配置项，以及匿名互动触达通道的选型对比。
- 当前**线上最终采用的方案**：基于「小程序一次性订阅消息 + 额度账户」实现，**3 个模板类型**（活动 / 跑腿 / 互动）+ 维修独立模板，全部为一次性订阅，**不依赖服务号**。
- 合并策略变更：**自 2026-09-15 起，全部模板关闭合并窗口**，每条消息立即独立推送（合并能力保留，可用 `SUBSCRIBE_MERGE_WINDOW_MS` 恢复）。
- 长期订阅**官方不可用**（校园论坛类目不在开放范围内），故方案完全基于一次性订阅设计；2026-09-12 文档中的「9+1 启用模板」为**尚未改代码的设计预案**，本文一并保留供后续实施参考。

## 一、模板清单与字段约定

### 1.1 线上已落地模板（3 + 维修独立）

（线上实况以 `订阅消息配置.md` 为准；下方 1.3 的 9+1 为 2026-09-12 未落地设计预案。）

| 用途 | 建议搜索词 | 字段约定 | 环境变量 |
|---|---|---|---|
| 活动提醒 | `活动提醒`、`报名成功`、`活动开始` | `thing1` 活动名称、`time2` 开始时间、`thing3` 地点 | `WX_TPL_ACTIVITY` |
| 跑腿订单 | `订单状态`、`接单通知`、`订单变更` | `character_string1` 订单号、`thing2` 状态、`amount3` 金额 | `WX_TPL_ERRAND` |
| 互动提醒 | `评论`、`回复提醒`、`留言通知` | `thing1` 昵称、`thing2` 内容、`time3` 时间 | `WX_TPL_INTERACT` |
| 报修（独立，不并入上表） | — | `thing1`/`thing2`/`thing3`/`name4`/`phone_number5`（设备-故障/地址/时间/联系人/电话） | `WX_REPAIR_TEMPLATE_ID` |

**关键约束**：选用的模板字段编号必须与上表一致。若后台模板字段编号不同（例如活动名是 `thing2` 而非 `thing1`），需同步修改 `server/services/subscribeService.js` 中对应 `pushXxx()` 方法的 `data` 映射，或改用微信后台实际提供的字段名。代码已用 `clip()` 做超长截断，超长不会再触发 `47003` 错误。

### 1.2 微信字段类型与长度限制

| 字段类型 | 长度上限 | 说明 |
|---|---|---|
| `thing` | 20 字符 | 中文短描述 |
| `character_string` | 32 字符 | 数字/字母/符号 |
| `time` | 32 字符 | 格式建议 `YYYY-MM-DD HH:mm` |
| `amount` | — | 需为「数字」格式，如 `5.00元` |
| `phone_number` | — | 手机号 |
| `name` | 10 字符 | 人名 |

> 注意：`amount` 类型字段必须传「数字」格式（如 `5.00元`），`thing` 类型上限 20 字符；`clip()` 处理了截断但未做类型转换。

### 1.4 各模板字段关键词约定（上线前必须核对）

xlsx 只给模板 ID、未给字段结构，现有 `pushXxx` 字段是硬编码的，此前核对结论是 27 个后台模板里只有「活动报名成功通知」字段吻合。每个启用模板上线前必须：

1. 在微信后台「订阅消息 → 我的模板」查该模板的**关键词 key 与类型**（thing/character_string/amount/time/phone_number…及各自长度限制，thing 最长 20 字符）；
2. 与代码侧推送字段比对，**要么改后台关键词、要么改 push 函数字段映射**，二者必须一致（不一致时微信返回 `47003`，发送静默失败，只留 `subscribe_message_log.status=failed`）；
3. 按各模板建议配置的关键词语义：
   - 订单类＝订单编号(character_string)＋事项(thing)＋金额(amount)＋时间(time)
   - 审核类＝申请内容(thing)＋审核结果(thing)＋时间(time)
   - 提现类＝单号(character_string)＋金额(amount)＋结果(thing)＋时间(time)
   - 聊天类＝发送者(thing)＋摘要(thing)＋时间(time)
   - 活动开始＝活动名(thing)＋开始时间(time)＋提醒内容(thing)

## 二、模板清理结论

### 2.1 当前后台实况（2026-09-12 清理建议）

面向微信公众平台「订阅消息 → 我的模板」当前 **27 个生效中** 模板。代码侧只定义了 **4 个模板槽位**，且这 4 个槽位的 ID **全部为空**：

| 槽位 | 环境变量 | 位置 | 当前值 |
|---|---|---|---|
| 活动 | `WX_TPL_ACTIVITY` | `server/.env:62` | 空 |
| 跑腿 | `WX_TPL_ERRAND` | `server/.env:63` | 空 |
| 互动 | `WX_TPL_INTERACT` | `server/.env:64` | 空 |
| 报修 | `WX_REPAIR_TEMPLATE_ID` | `server/.env:66` | 空 |

前端 `utils/subscribe.js` 的 `TEMPLATE_IDS` 也仍是占位符（`请填入活动提醒模板ID`），`validIds()` 会把它们全部过滤掉 → **不会弹出任何授权窗口**。结论：**27 个生效模板中，当前实际被使用的数量是 0**，所有通知目前只走站内信 + WebSocket，订阅消息通道从未开通。

### 2.2 业务域归组建议（2026-09-12 清理建议）

| 业务域 | 模板数 | 建议 | 说明 |
|---|---|---|---|
| 活动类 | 8 | 留 1 | 报名成功/报名结果/参与成功/报名通知/新活动提醒×2/活动开始提醒都是同义措辞 |
| 跑腿订单类 | 4 | 留 1 | 接单/完成/取消三套模板，`pushErrand()` 用一个「状态」字段即可覆盖全部流转 |
| 互动消息类 | 6 | 留 1 | 评论/回复/私信/聊天，`pushInteract()` 用 5 分钟合并窗口统一处理 |
| 提现类 | 3 | 全删 | `walletController` 无订阅推送调用，提现结果只发站内信 |
| 审核类 | 6 | 全删（或补齐接入） | 活动审核/认证审核/审核结果/审核通过等虽有审核流程，但代码没接订阅推送 |

> 审核类 4 个模板（举报结果通知、便民信息审核结果通知、活动审核通知、认证审核通知、审核结果通知、审核通过提醒）本身有价值，但当前无调用入口；要么补齐代码接入，要么先删减少维护负担。

### 2.3 闲置模板处置（2026-09-12 使用方案）

| 模板 | 处置 | 原因 |
|---|---|---|
| 提现成功通知 | 停用 | 被「提现结果通知」覆盖 |
| 活动报名结果通知 / 活动参与成功提醒 / 活动报名通知 | 停用 | 被「报名成功通知」+「审核结果通知」覆盖 |
| 活动审核通知 / 审核通过提醒 / 认证审核通知 | 停用 | 被「审核结果通知」统一覆盖 |
| 新活动提醒 | **暂留备用** | 未来做「推荐活动营销推送」时启用，当前无授权触点 |
| 用户私信通知 | 停用 | 被「聊天信息提醒」覆盖 |
| 评论回复通知 | 停用 | 被「新的评论提醒」覆盖 |
| 举报结果通知 | **暂留备用** | 若后续上线独立「举报处理结果」流程再启用；现阶段由「审核结果通知」或站内信承载 |

### 2.4 清理两条铁律

- **字段必须一致**：微信 `subscribe/send` 要求 `data` 字段与模板「数量、类型、编号」三者一致，否则 `47003 invalid data format`。实测 27 个模板里仅「活动报名成功通知」的 `thing1/time2/thing3` 与现有代码完全对应；跑腿/互动需回公共模板库重选，或改 `pushErrand()/pushInteract()` 适配。
- **同类只留 1 个**：额度按**模板 ID** 分别记账（`user_subscribe_quota` 的 `(user_id, tpl_type)`）。同类模板保留多份时，用户授权的是 A、服务端发的是 B，额度对不上 —— 这是「同类模板却发不出去」的根因，也是「同类只留 1 个」的核心理由。
- 模板一旦在后台删除**不可恢复**，删前确认短期内不做；重复选用的副本（如「提现结果通知」「新的评论提醒」「新活动提醒」「订单接单通知」各出现两次）属误操作，可优先删。

## 三、服务端与前端配置项

### 3.1 服务端环境变量（`server/.env`）

填入三个模板 ID（纯数字字符串，留空则对应类型自动跳过、只保留站内信，不影响业务）：

```bash
WX_TPL_ACTIVITY=1234567890
WX_TPL_ERRAND=1234567891
WX_TPL_INTERACT=1234567892
```

频控开关（合并窗口，默认关闭）：

```bash
# 0 或不设 = 不合并（当前默认）；300000 = 恢复合并（仅对 commentNew/commentReply/message 三高频模板生效）
SUBSCRIBE_MERGE_WINDOW_MS=0
```

> 报修独立变量 `WX_REPAIR_TEMPLATE_ID` 在 `server/.env:66`，保持独立通道。

### 3.2 前端常量（`utils/subscribe.js`）

顶部 `TEMPLATE_IDS` 三个 ID **必须与服务端完全一致**（前端 `wx.requestSubscribeMessage` 拉授权弹窗与服务端发消息用的是同一个模板）：

```js
const TEMPLATE_IDS = {
  activity: '请填入活动提醒模板ID',
  errand: '请填入跑腿订单模板ID',
  interact: '请填入互动提醒模板ID'
}
```

后续若落地 1.3 预案，需按新槽位扩展 `TEMPLATE_TYPES` 并同步替换 `TEMPLATE_IDS` 占位符。

### 3.3 服务端常量（`server/services/subscribeService.js`）

- 各 `pushXxx()` 方法的 `data` 字段映射须与后台模板编号一致；
- 额度模型实现于此：`user_subscribe_quota`（按 `(user_id, tpl_type)` 记账）、`subscribe_message_log`（含微信返回码）、发送与 `43101` 清零逻辑；
- 后续若落地 1.3 预案，`TEMPLATES` 字典从 3 个扩到 9 个，新增 `pushMessage/pushAudit/pushWithdraw/pushErrandAccepted/pushErrandFinished/pushErrandCancelled`。

### 3.4 数据库对象（服务启动 `runMigrations()` 自动执行，无需手工建表）

| 对象 | 说明 |
|---|---|
| `user_subscribe_quota` | 订阅额度账户，按 `(user_id, tpl_type)` 记录剩余可发条数 |
| `subscribe_message_log` | 发送流水，含微信返回码，用于排障与频控判断 |
| `subscribe_pending_message` | 合并窗口内待发表 |
| `campus_activity.remind_sent_at` | 活动提醒幂等标记，保证同一活动只提醒一轮 |

验证迁移：`SHOW TABLES LIKE '%subscribe%';` 与 `SHOW COLUMNS FROM campus_activity LIKE 'remind_sent_at';`

### 3.5 频控开关与合并策略

- **自 2026-09-15 起：全部模板不合并 —— 每收到一条消息立即独立触发一次微信提醒。**（以 2026-09-15 文档与 `订阅消息配置.md` 为准）
- 合并窗口能力**保留但默认关闭**，由 `SUBSCRIBE_MERGE_WINDOW_MS` 控制：非法值（空串/非数字/负数）一律按不合并处理。
- 微信一次性订阅硬上限：用户每点一次「允许」只增加 1 条额度（平台约束）。关闭合并后突发消息会更快耗尽额度 —— 额度归零后消息转待发表并给用户发站内信，但微信端仍收不到。若用户反馈「收不到通知」，先查 `subscribe_message_log` 里 `skipped`（额度不足）的占比，而非合并窗口。

## 四、触发场景与模板对应关系

### 4.1 双通道架构（站内信底座 + 订阅消息增强）

```
业务事件发生
   ├──▶ 站内信 createNotification()   ← 所有场景必写（底座，永不缺席）
   │        └── WebSocket 实时推送 → 消息中心 5 个 tab + tabBar 角标
   └──▶ 订阅消息 push()               ← 增强通道，逐级降级：
            1. 模板 ID 未配置 → 跳过（不报错）
            2. 无授权额度 → 跳过
            3. （合并窗口关闭后本步默认不触发）
            4. 发送成功 → 扣额度、记 sent
            5. errcode 43101 → 清零额度（用户在微信设置里拒收）
            失败一律吞异常，绝不回滚业务
```

判断标准：用户 5 分钟内必须知道的事（交易、资金、审核）用不合并订阅消息；群发/营销类（新活动提醒）暂不做。订阅消息发送失败**绝不影响**下单、评论、报名等主流程。

### 4.2 线上已接入触发点（3 模板）

| 模板 | 触发位置 | 文案 |
|---|---|---|
| 活动 | 活动开始前 30 分钟（定时任务 `activityReminderService`，每 10 分钟扫描 `remind_sent_at` 幂等） | 活动名 / 开始时间 / 地点 |
| 跑腿 | `errandController.notify()` 全部 12 个调用点 | 订单号 / 状态 / 赏金 |
| 互动 | `notificationService`（评论、点赞）、`messageController`（私信） | 昵称 / 事件 / 摘要 |

跑腿接入方式：改造统一入口 `notify()` 而非逐个分支加代码，因此接单/提交完成/确认完成/取消/异议/评价等全部状态流转自动获得订阅推送能力，后续新增状态也无需再改。

### 4.3 设计预案：9+1 触发点 & 授权时机（2026-09-12 方案）

各启用模板适配要点（接收人/触发条件/跳转页/合并窗口）：

| 槽位 | 适配场景（摘要） | 合并窗口 |
|---|---|---|
| `interact` | 帖子被评论 / 蹲贴新评论 / 被点赞 | 不合并（原 5 分钟合并，2026-09-15 起关闭） |
| `message` | 私信新消息 / 群聊新消息（补齐当前缺口） | 不合并（2026-09-15 起关闭） |
| `activity_signup` | 有人报名成功→通知发起人 | 不合并（低频重要） |
| `activity_start` | 活动开始前 30 分钟提醒全部已报名用户 | 不合并 |
| `audit` | 活动/社团/群聊/认证 审核结果（补齐缺口） | 不合并 |
| `errand_accepted` | 接单→通知发单人 | 不合并（交易类） |
| `errand_finished` | 提交完成/确认完成/超时结算/评价/裁决不成立 | 不合并 |
| `errand_cancelled` | 取消/取消接单/异议/超时自动取消/裁决成立退款 | 不合并；退款类最高优先级永不合并永不跳过 |
| `withdraw` | 提现驳回/打款/待确认/到账/失败（文案中文化） | 不合并（资金类） |

授权时机设计（每个授权点一次最多请求 3 个模板，须在用户 tap 同步链内调用）：

| # | 授权时机 | 请求槽位 | 理由 |
|---|---|---|---|
| 1 | 发布跑腿单（提交按钮） | 接单+完成+取消 | 发单人后续收这三类 |
| 2 | 接跑腿单（接单按钮） | 完成+取消 | 接单人关心完成/取消 |
| 3 | 活动报名（报名按钮） | 报名成功+活动开始+审核结果 | 报名者收开始提醒与审核结果 |
| 4 | 创建活动（提交按钮） | 报名成功+审核结果 | 发起人关心有人报名、审核结果 |
| 5 | 进入聊天页/首次发消息 | 聊天信息提醒 | 收到回复时要有提醒 |
| 6 | 发帖/发评论（提交后静默） | 新的评论提醒 | 沉浸互动时补授权 |
| 7 | 发起提现（确认按钮） | 提现结果 | 提现结果必达诉求 |
| 8 | 提交社团/群聊/认证申请 | 审核结果 | 等审核的人最需要推送 |

配套规则：默认 `silent: true`（失败不打扰），仅提现/报名可用非静默引导；授权后必调 `POST /subscribe/report` 累加额度；钱包页/消息设置页可 `GET /subscribe/quota` 展示剩余额度；不要在冷启动/进页面时弹授权。

### 4.4 跑腿状态机 × 模板映射（设计预案核心）

| 订单状态流转 | 发单人收 | 接单人收 | 模板 |
|---|---|---|---|
| `pending` 超时未支付/截止无人接单 自动取消 | 取消通知 | — | `errand_cancelled` |
| `pending → accepted` | **接单通知** | — | `errand_accepted` |
| `accepted → finishing`（提交完成） | **完成通知**（2h 内确认） | — | `errand_finished` |
| `finishing → finished`（确认完成） | — | **完成通知**（赏金入账） | `errand_finished` |
| 2 小时未确认自动结算 | 完成通知 | 完成通知 | `errand_finished` |
| 发单人取消 | — | 取消通知 | `errand_cancelled` |
| 接单方取消接单（赏金退回） | 取消通知 | — | `errand_cancelled` |
| 接单方申请取消→同意/拒绝 | — | 取消通知 | `errand_cancelled` |
| 发单人提出异议（客服介入） | — | 取消通知 | `errand_cancelled` |
| 裁决：异议成立（退款） | 取消通知 | 取消通知 | `errand_cancelled` |
| 裁决：异议不成立（订单成立） | 完成通知 | 完成通知 | `errand_finished` |
| 评价 | 完成通知 | 完成通知 | `errand_finished` |
| 退款重试结果 | 取消通知 | — | `errand_cancelled` |
| 异议待处理→管理员 | 站内信 `system`（不走订阅） | — | — |

记忆口诀：**「变好→完成通知，变没→取消通知，有人接→接单通知，管理员→站内信」**。

### 4.5 优先级与降级链（设计预案）

| 优先级 | 模板组 | 频控策略 | 降级 |
|---|---|---|---|
| P0（资金/交易） | 提现结果、订单取消（退款分支） | 永不合并，失败重试 | 站内信 + WebSocket 兜底 |
| P1（交易流转） | 订单接单/完成、活动开始提醒 | 不合并 | 站内信兜底 |
| P2（审核结果） | 审核结果、报名成功 | 不合并 | 站内信兜底 |
| P3（互动） | 新的评论提醒 | 5 分钟合并（2026-09-15 起关闭） | 站内信 + 角标兜底 |
| P3（聊天） | 聊天信息提醒 | 5 分钟合并（2026-09-15 起关闭） | 未读角标兜底 |

## 五、匿名互动触达通道选型

> 场景背景：匿名/分身私信在服务端被 `if (!channelAnonymous)` 显式跳过订阅推送（`messageController.js` 第 238–248 行），理由「保留匿名性，避免泄露身份或打扰」。本节汇总**订阅消息之外**实现匿名互动触达的全部可用方案。（以 2026-09-15 文档为准）

### 5.1 触达天花板（先明确物理限制）

| 用户状态 | 不推送的通道能否触达 |
|---|---|
| 小程序在前台 | 能，毫秒级 |
| 小程序在后台（未销毁） | 能，WebSocket 仍存活 |
| **小程序已关闭 / 微信未打开** | **不能，必须靠推送** |

「匿名互动 + 完全不推送」=「只在用户打开小程序时才能被感知」，这是通道物理限制，非实现问题。

### 5.2 方案总览

| 编号 | 方案 | 类型 | 能否跨出小程序 | 开发成本 |
|---|---|---|---|---|
| A1 | WebSocket 实时推送 | 站内 | 否 | 已具备 |
| A2 | 站内未读 + tabBar 角标 | 站内 | 否 | 已具备 |
| A3 | 冷启动强制提示 | 站内增强 | 否 | 低 |
| B1 | 公众号（服务号）模板消息 | 生态内推送 | **是** | 高 |
| B2 | 长期订阅消息 | 生态内推送 | 是 | **平台不允许** |
| B3 | 短信 / 邮件 | 站外推送 | 是 | 中 |
| C1 | 匿名互动限定在内容页 | 产品形态 | 不适用 | 中 |
| C2 | 同步在线即时会话 | 产品形态 | 否 | 中 |
| D1 | 中性文案推送 | 借用现有推送 | 是 | **极低** |
| D2 | 匿名消息聚合推送 | 借用现有推送 | 是 | 低 |

### 5.3 关键方案要点

- **A1 WebSocket**：`server/ws/wsServer.js` 的 `sendToUser()` 已在匿名路径下调用，匿名私信本来就有实时通道，只是不弹微信提醒；零成本、零额度、不暴露身份。
- **A2 角标**：`private_conversation.unread_count` + `utils/messageStore.js`（tab 索引 3）。注意项目用自定义 tabBar，`wx.setTabBarBadge` 不生效，走组件内更新，新增页面若绕过 `messageStore` 会漏角标。
- **A3 冷启动提示（最值得补）**：冷启动时 `unreadCount > 0` 在消息 tab 或首页顶部提示「你有 N 条新私信（含匿名）」，用 `messageController.unreadCount` 接口；是**唯一能弥补关闭期间零感知的时机**。
- **B1 公众号（服务号）模板消息 —— 唯一可控「出圈」替代**：小程序与服务号绑定到微信开放平台 → 经 **unionid** 打通 → 服务号模板消息下发，可点击跳回小程序，文案可中性化不暴露身份。缺点：用户须先关注服务号（最大转化门槛）；需**企业/组织主体认证的服务号**（个人主体只能订阅号，无模板消息能力）；需开放平台绑定，开发量大；有内容合规审查与日限额。校园场景若学校已有官方服务号可行性高，否则不建议新建。
- **B2 长期订阅 —— 走不通**（详见第六节）。
- **B3 短信/邮件**：到达率最高但按条计费，私信高频场景成本不可接受，需手机号且涉个人信息合规；**不适用于私信提醒**。
- **C1/C2 改变互动形态**：把匿名互动改成公开内容页（评论/树洞）或限定「仅双方同时在线实时」，彻底绕开推送但不点对点。
- **D1 中性文案推送（成本最低）**：解除 `if (!channelAnonymous)`，把 `pushMessage` 的 `thing1`（发送人）从 `sys_user.nick_name` 换成中性词（「一位同学」/「匿名用户」）或分身昵称（`ANON_NAMES` 池），`summary` 同步改。改动极小、匿名性保持、兼容现有额度/频控。
- **D2 匿名消息聚合推送**：窗口内聚合只推一条「你有 N 条新私信」，省额度、降刷屏，可复用 `subscribe_pending_message` 机制。

### 5.4 组合建议与结论

- **路径 1（推荐，零新增通道）**：A1 + A2 + A3 + D1。用中性文案解除匿名限制（改动最小立刻见效），补齐冷启动提示，完全不新增基础设施。
- **路径 2（预算允许）**：路径 1 + B1，前提是有可用认证服务号，解决「关闭小程序期间」触达。
- **路径 3（产品定位调整）**：C1 或 C2，把「匿名就是不该被通知」写进产品契约，不再修补触达。

**结论**：优先走路径 1（站内通道 + 中性文案推送），长期订阅与短信均不可行，公众号模板消息仅在已有认证服务号时作为增强。

## 六、长期订阅不可用的官方限制说明

**平台规则**：长期订阅**只对政务民生、医疗、交通、金融、教育等部分二级行业类目开放**，且「仅支持少量民生公共服务节点通知，并非所有场景都支持」；模板库里有模板才能调用。

**关键反例**：微信官方社区已明确回复「**在线教育类目暂不支持开通长期订阅模板，建议通过一次性订阅或其他方式实现**」。

**结论**：校园论坛的私信提醒属于 UGC 社交互动，既不在开放类目内，也不属于「民生公共服务节点通知」。**不要在该路上投入时间**。因此本方案完全基于「一次性订阅 + 额度账户」设计，不依赖长期订阅。

## 七、遗留问题与后续建议

1. **模板数量口径冲突待确认**：线上实况为 3 个模板（活动/跑腿/互动 + 维修），而 2026-09-12 设计预案为 9+1。需确认 9+1 是否已进入实施排期，还是仅作设计存档（当前 `WX_TPL_*` 仍为占位符，通道未真正开通）。
2. **字段映射核对是上线硬前提**：27 个后台模板中仅「活动报名成功通知」字段吻合，跑腿/互动/新增模板上线前须逐模板比对关键词，避免 `47003` 静默失败。
3. **额度耗尽体验**：关闭合并后突发消息更快耗尽额度，额度归零后微信端收不到（仅站内信兜底）。建议监控 `subscribe_message_log` 的 `skipped` 占比，并在消息中心展示剩余额度、引导再次授权。
4. **匿名触达落地**：推荐路径 1（A1+A2+A3+D1）—— 补冷启动提示 + 中性文案解除匿名限制，改动最小；公众号模板消息（B1）待确认是否有学校官方认证服务号再决定。
5. **站内信缺口补齐**：群聊、社团/群聊/认证审核结果、活动报名成功/开始提醒的站内信当前缺失，若落地 9+1 预案需同步扩 `system_notification.type` 枚举（`group/club/activity`），并注意 `migrations.js` + `sql/init.sql` + `notificationController.list` 的 `IN (...)` + `notificationService` 白名单四处同改。
6. **部署注意**：`subscribeService.js` 与新增依赖须整包闭包上传（历史上线上缺该文件曾致 pm2 100 次重启、站点 502）；上线顺序：备份 → 上传 → 跑迁移 → `SHOW COLUMNS` 核对枚举 → restart → 用 401/200 判断路由注册。
