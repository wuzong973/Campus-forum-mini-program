### 一、模板清单与字段约定

#### 1.1 线上已落地模板（3 + 维修独立）

（线上实况以 `订阅消息配置.md` 为准；下方 1.3 的 9+1 为 2026-09-12 未落地设计预案。）

| 用途 | 建议搜索词 | 字段约定 | 环境变量 |
|---|---|---|---|
| 活动提醒 | `活动提醒`、`报名成功`、`活动开始` | `thing1` 活动名称、`time2` 开始时间、`thing3` 地点 | `WX_TPL_ACTIVITY` |
| 跑腿订单 | `订单状态`、`接单通知`、`订单变更` | `character_string1` 订单号、`thing2` 状态、`amount3` 金额 | `WX_TPL_ERRAND` |
| 互动提醒 | `评论`、`回复提醒`、`留言通知` | `thing1` 昵称、`thing2` 内容、`time3` 时间 | `WX_TPL_INTERACT` |
| 报修（独立，不并入上表） | — | `thing1`/`thing2`/`thing3`/`name4`/`phone_number5`（设备-故障/地址/时间/联系人/电话） | `WX_REPAIR_TEMPLATE_ID` |

**关键约束**：选用的模板字段编号必须与上表一致。若后台模板字段编号不同（例如活动名是 `thing2` 而非 `thing1`），需同步修改 `server/services/subscribeService.js` 中对应 `pushXxx()` 方法的 `data` 映射，或改用微信后台实际提供的字段名。代码已用 `clip()` 做超长截断，超长不会再触发 `47003` 错误。

#### 1.2 微信字段类型与长度限制

| 字段类型 | 长度上限 | 说明 |
|---|---|---|
| `thing` | 20 字符 | 中文短描述 |
| `character_string` | 32 字符 | 数字/字母/符号 |
| `time` | 32 字符 | 格式建议 `YYYY-MM-DD HH:mm` |
| `amount` | — | 需为「数字」格式，如 `5.00元` |
| `phone_number` | — | 手机号 |
| `name` | 10 字符 | 人名 |

> 注意：`amount` 类型字段必须传「数字」格式（如 `5.00元`），`thing` 类型上限 20 字符；`clip()` 处理了截断但未做类型转换。

#### 1.4 各模板字段关键词约定（上线前必须核对）

xlsx 只给模板 ID、未给字段结构，现有 `pushXxx` 字段是硬编码的，此前核对结论是 27 个后台模板里只有「活动报名成功通知」字段吻合。每个启用模板上线前必须：

1. 在微信后台「订阅消息 → 我的模板」查该模板的**关键词 key 与类型**（thing/character_string/amount/time/phone_number…及各自长度限制，thing 最长 20 字符）；
2. 与代码侧推送字段比对，**要么改后台关键词、要么改 push 函数字段映射**，二者必须一致（不一致时微信返回 `47003`，发送静默失败，只留 `subscribe_message_log.status=failed`）；
3. 按各模板建议配置的关键词语义：
   - 订单类＝订单编号(character_string)＋事项(thing)＋金额(amount)＋时间(time)
   - 审核类＝申请内容(thing)＋审核结果(thing)＋时间(time)
   - 提现类＝单号(character_string)＋金额(amount)＋结果(thing)＋时间(time)
   - 聊天类＝发送者(thing)＋摘要(thing)＋时间(time)
   - 活动开始＝活动名(thing)＋开始时间(time)＋提醒内容(thing)

### 二、模板清理结论

#### 2.1 当前后台实况（2026-09-12 清理建议）

面向微信公众平台「订阅消息 → 我的模板」当前 **27 个生效中** 模板。代码侧只定义了 **4 个模板槽位**，且这 4 个槽位的 ID **全部为空**：

| 槽位 | 环境变量 | 位置 | 当前值 |
|---|---|---|---|
| 活动 | `WX_TPL_ACTIVITY` | `server/.env:62` | 空 |
| 跑腿 | `WX_TPL_ERRAND` | `server/.env:63` | 空 |
| 互动 | `WX_TPL_INTERACT` | `server/.env:64` | 空 |
| 报修 | `WX_REPAIR_TEMPLATE_ID` | `server/.env:66` | 空 |

前端 `utils/subscribe.js` 的 `TEMPLATE_IDS` 也仍是占位符（`请填入活动提醒模板ID`），`validIds()` 会把它们全部过滤掉 → **不会弹出任何授权窗口**。结论：**27 个生效模板中，当前实际被使用的数量是 0**，所有通知目前只走站内信 + WebSocket，订阅消息通道从未开通。

#### 2.2 业务域归组建议（2026-09-12 清理建议）

| 业务域 | 模板数 | 建议 | 说明 |
|---|---|---|---|
| 活动类 | 8 | 留 1 | 报名成功/报名结果/参与成功/报名通知/新活动提醒×2/活动开始提醒都是同义措辞 |
| 跑腿订单类 | 4 | 留 1 | 接单/完成/取消三套模板，`pushErrand()` 用一个「状态」字段即可覆盖全部流转 |
| 互动消息类 | 6 | 留 1 | 评论/回复/私信/聊天，`pushInteract()` 用 5 分钟合并窗口统一处理 |
| 提现类 | 3 | 全删 | `walletController` 无订阅推送调用，提现结果只发站内信 |
| 审核类 | 6 | 全删（或补齐接入） | 活动审核/认证审核/审核结果/审核通过等虽有审核流程，但代码没接订阅推送 |

> 审核类 4 个模板（举报结果通知、便民信息审核结果通知、活动审核通知、认证审核通知、审核结果通知、审核通过提醒）本身有价值，但当前无调用入口；要么补齐代码接入，要么先删减少维护负担。

#### 2.3 闲置模板处置（2026-09-12 使用方案）

| 模板 | 处置 | 原因 |
|---|---|---|
| 提现成功通知 | 停用 | 被「提现结果通知」覆盖 |
| 活动报名结果通知 / 活动参与成功提醒 / 活动报名通知 | 停用 | 被「报名成功通知」+「审核结果通知」覆盖 |
| 活动审核通知 / 审核通过提醒 / 认证审核通知 | 停用 | 被「审核结果通知」统一覆盖 |
| 新活动提醒 | **暂留备用** | 未来做「推荐活动营销推送」时启用，当前无授权触点 |
| 用户私信通知 | 停用 | 被「聊天信息提醒」覆盖 |
| 评论回复通知 | 停用 | 被「新的评论提醒」覆盖 |
| 举报结果通知 | **暂留备用** | 若后续上线独立「举报处理结果」流程再启用；现阶段由「审核结果通知」或站内信承载 |

#### 2.4 清理两条铁律

- **字段必须一致**：微信 `subscribe/send` 要求 `data` 字段与模板「数量、类型、编号」三者一致，否则 `47003 invalid data format`。实测 27 个模板里仅「活动报名成功通知」的 `thing1/time2/thing3` 与现有代码完全对应；跑腿/互动需回公共模板库重选，或改 `pushErrand()/pushInteract()` 适配。
- **同类只留 1 个**：额度按**模板 ID** 分别记账（`user_subscribe_quota` 的 `(user_id, tpl_type)`）。同类模板保留多份时，用户授权的是 A、服务端发的是 B，额度对不上 —— 这是「同类模板却发不出去」的根因，也是「同类只留 1 个」的核心理由。
- 模板一旦在后台删除**不可恢复**，删前确认短期内不做；重复选用的副本（如「提现结果通知」「新的评论提醒」「新活动提醒」「订单接单通知」各出现两次）属误操作，可优先删。

### 三、服务端与前端配置项

#### 3.1 服务端环境变量（`server/.env`）

填入三个模板 ID（纯数字字符串，留空则对应类型自动跳过、只保留站内信，不影响业务）：

```bash
WX_TPL_ACTIVITY=1234567890
WX_TPL_ERRAND=1234567891
WX_TPL_INTERACT=1234567892
```

频控开关（合并窗口，默认关闭）：

```bash
# 0 或不设 = 不合并（当前默认）；300000 = 恢复合并（仅对 commentNew/commentReply/message 三高频模板生效）
SUBSCRIBE_MERGE_WINDOW_MS=0
```

> 报修独立变量 `WX_REPAIR_TEMPLATE_ID` 在 `server/.env:66`，保持独立通道。

#### 3.2 前端常量（`utils/subscribe.js`）

顶部 `TEMPLATE_IDS` 三个 ID **必须与服务端完全一致**（前端 `wx.requestSubscribeMessage` 拉授权弹窗与服务端发消息用的是同一个模板）：

```js
const TEMPLATE_IDS = {
  activity: '请填入活动提醒模板ID',
  errand: '请填入跑腿订单模板ID',
  interact: '请填入互动提醒模板ID'
}
```

后续若落地 1.3 预案，需按新槽位扩展 `TEMPLATE_TYPES` 并同步替换 `TEMPLATE_IDS` 占位符。

#### 3.3 服务端常量（`server/services/subscribeService.js`）

- 各 `pushXxx()` 方法的 `data` 字段映射须与后台模板编号一致；
- 额度模型实现于此：`user_subscribe_quota`（按 `(user_id, tpl_type)` 记账）、`subscribe_message_log`（含微信返回码）、发送与 `43101` 清零逻辑；
- 后续若落地 1.3 预案，`TEMPLATES` 字典从 3 个扩到 9 个，新增 `pushMessage/pushAudit/pushWithdraw/pushErrandAccepted/pushErrandFinished/pushErrandCancelled`。

#### 3.4 数据库对象（服务启动 `runMigrations()` 自动执行，无需手工建表）

| 对象 | 说明 |
|---|---|
| `user_subscribe_quota` | 订阅额度账户，按 `(user_id, tpl_type)` 记录剩余可发条数 |
| `subscribe_message_log` | 发送流水，含微信返回码，用于排障与频控判断 |
| `subscribe_pending_message` | 合并窗口内待发表 |
| `campus_activity.remind_sent_at` | 活动提醒幂等标记，保证同一活动只提醒一轮 |

验证迁移：`SHOW TABLES LIKE '%subscribe%';` 与 `SHOW COLUMNS FROM campus_activity LIKE 'remind_sent_at';`

#### 3.5 频控开关与合并策略

- **自 2026-09-15 起：全部模板不合并 —— 每收到一条消息立即独立触发一次微信提醒。**（以 2026-09-15 文档与 `订阅消息配置.md` 为准）
- 合并窗口能力**保留但默认关闭**，由 `SUBSCRIBE_MERGE_WINDOW_MS` 控制：非法值（空串/非数字/负数）一律按不合并处理。
- 微信一次性订阅硬上限：用户每点一次「允许」只增加 1 条额度（平台约束）。关闭合并后突发消息会更快耗尽额度 —— 额度归零后消息转待发表并给用户发站内信，但微信端仍收不到。若用户反馈「收不到通知」，先查 `subscribe_message_log` 里 `skipped`（额度不足）的占比，而非合并窗口。

### 四、触发场景与模板对应关系

#### 4.1 双通道架构（站内信底座 + 订阅消息增强）

```
业务事件发生
   ├──▶ 站内信 createNotification()   ← 所有场景必写（底座，永不缺席）
   │        └── WebSocket 实时推送 → 消息中心 5 个 tab + tabBar 角标
   └──▶ 订阅消息 push()               ← 增强通道，逐级降级：
            1. 模板 ID 未配置 → 跳过（不报错）
            2. 无授权额度 → 跳过
            3. （合并窗口关闭后本步默认不触发）
            4. 发送成功 → 扣额度、记 sent
            5. errcode 43101 → 清零额度（用户在微信设置里拒收）
            失败一律吞异常，绝不回滚业务
```

判断标准：用户 5 分钟内必须知道的事（交易、资金、审核）用不合并订阅消息；群发/营销类（新活动提醒）暂不做。订阅消息发送失败**绝不影响**下单、评论、报名等主流程。

#### 4.2 线上已接入触发点（3 模板）

| 模板 | 触发位置 | 文案 |
|---|---|---|
| 活动 | 活动开始前 30 分钟（定时任务 `activityReminderService`，每 10 分钟扫描 `remind_sent_at` 幂等） | 活动名 / 开始时间 / 地点 |
| 跑腿 | `errandController.notify()` 全部 12 个调用点 | 订单号 / 状态 / 赏金 |
| 互动 | `notificationService`（评论、点赞）、`messageController`（私信） | 昵称 / 事件 / 摘要 |

跑腿接入方式：改造统一入口 `notify()` 而非逐个分支加代码，因此接单/提交完成/确认完成/取消/异议/评价等全部状态流转自动获得订阅推送能力，后续新增状态也无需再改。

#### 4.3 设计预案：9+1 触发点 & 授权时机（2026-09-12 方案）

各启用模板适配要点（接收人/触发条件/跳转页/合并窗口）：

| 槽位 | 适配场景（摘要） | 合并窗口 |
|---|---|---|
| `interact` | 帖子被评论 / 蹲贴新评论 / 被点赞 | 不合并（原 5 分钟合并，2026-09-15 起关闭） |
| `message` | 私信新消息 / 群聊新消息（补齐当前缺口） | 不合并（2026-09-15 起关闭） |
| `activity_signup` | 有人报名成功→通知发起人 | 不合并（低频重要） |
| `activity_start` | 活动开始前 30 分钟提醒全部已报名用户 | 不合并 |
| `audit` | 活动/社团/群聊/认证 审核结果（补齐缺口） | 不合并 |
| `errand_accepted` | 接单→通知发单人 | 不合并（交易类） |
| `errand_finished` | 提交完成/确认完成/超时结算/评价/裁决不成立 | 不合并 |
| `errand_cancelled` | 取消/取消接单/异议/超时自动取消/裁决成立退款 | 不合并；退款类最高优先级永不合并永不跳过 |
| `withdraw` | 提现驳回/打款/待确认/到账/失败（文案中文化） | 不合并（资金类） |

授权时机设计（每个授权点一次最多请求 3 个模板，须在用户 tap 同步链内调用）：

| # | 授权时机 | 请求槽位 | 理由 |
|---|---|---|---|
| 1 | 发布跑腿单（提交按钮） | 接单+完成+取消 | 发单人后续收这三类 |
| 2 | 接跑腿单（接单按钮） | 完成+取消 | 接单人关心完成/取消 |
| 3 | 活动报名（报名按钮） | 报名成功+活动开始+审核结果 | 报名者收开始提醒与审核结果 |
| 4 | 创建活动（提交按钮） | 报名成功+审核结果 | 发起人关心有人报名、审核结果 |
| 5 | 进入聊天页/首次发消息 | 聊天信息提醒 | 收到回复时要有提醒 |
| 6 | 发帖/发评论（提交后静默） | 新的评论提醒 | 沉浸互动时补授权 |
| 7 | 发起提现（确认按钮） | 提现结果 | 提现结果必达诉求 |
| 8 | 提交社团/群聊/认证申请 | 审核结果 | 等审核的人最需要推送 |

配套规则：默认 `silent: true`（失败不打扰），仅提现/报名可用非静默引导；授权后必调 `POST /subscribe/report` 累加额度；钱包页/消息设置页可 `GET /subscribe/quota` 展示剩余额度；不要在冷启动/进页面时弹授权。

#### 4.4 跑腿状态机 × 模板映射（设计预案核心）

| 订单状态流转 | 发单人收 | 接单人收 | 模板 |
|---|---|---|---|
| `pending` 超时未支付/截止无人接单 自动取消 | 取消通知 | — | `errand_cancelled` |
| `pending → accepted` | **接单通知** | — | `errand_accepted` |
| `accepted → finishing`（提交完成） | **完成通知**（2h 内确认） | — | `errand_finished` |
| `finishing → finished`（确认完成） | — | **完成通知**（赏金入账） | `errand_finished` |
| 2 小时未确认自动结算 | 完成通知 | 完成通知 | `errand_finished` |
| 发单人取消 | — | 取消通知 | `errand_cancelled` |
| 接单方取消接单（赏金退回） | 取消通知 | — | `errand_cancelled` |
| 接单方申请取消→同意/拒绝 | — | 取消通知 | `errand_cancelled` |
| 发单人提出异议（客服介入） | — | 取消通知 | `errand_cancelled` |
| 裁决：异议成立（退款） | 取消通知 | 取消通知 | `errand_cancelled` |
| 裁决：异议不成立（订单成立） | 完成通知 | 完成通知 | `errand_finished` |
| 评价 | 完成通知 | 完成通知 | `errand_finished` |
| 退款重试结果 | 取消通知 | — | `errand_cancelled` |
| 异议待处理→管理员 | 站内信 `system`（不走订阅） | — | — |

记忆口诀：**「变好→完成通知，变没→取消通知，有人接→接单通知，管理员→站内信」**。

### 五、匿名互动触达通道选型

> 场景背景：匿名/分身私信在服务端被 `if (!channelAnonymous)` 显式跳过订阅推送（`messageController.js` 第 238–248 行），理由「保留匿名性，避免泄露身份或打扰」。本节汇总**订阅消息之外**实现匿名互动触达的全部可用方案。（以 2026-09-15 文档为准）

#### 5.1 触达天花板（先明确物理限制）

| 用户状态 | 不推送的通道能否触达 |
|---|---|
| 小程序在前台 | 能，毫秒级 |
| 小程序在后台（未销毁） | 能，WebSocket 仍存活 |
| **小程序已关闭 / 微信未打开** | **不能，必须靠推送** |

「匿名互动 + 完全不推送」=「只在用户打开小程序时才能被感知」，这是通道物理限制，非实现问题。

#### 5.2 方案总览

| 编号 | 方案 | 类型 | 能否跨出小程序 | 开发成本 |
|---|---|---|---|---|
| A1 | WebSocket 实时推送 | 站内 | 否 | 已具备 |
| A2 | 站内未读 + tabBar 角标 | 站内 | 否 | 已具备 |
| A3 | 冷启动强制提示 | 站内增强 | 否 | 低 |
| B1 | 公众号（服务号）模板消息 | 生态内推送 | **是** | 高 |
| B2 | 长期订阅消息 | 生态内推送 | 是 | **平台不允许** |
| B3 | 短信 / 邮件 | 站外推送 | 是 | 中 |
| C1 | 匿名互动限定在内容页 | 产品形态 | 不适用 | 中 |
| C2 | 同步在线即时会话 | 产品形态 | 否 | 中 |
| D1 | 中性文案推送 | 借用现有推送 | 是 | **极低** |
| D2 | 匿名消息聚合推送 | 借用现有推送 | 是 | 低 |

#### 5.3 关键方案要点

- **A1 WebSocket**：`server/ws/wsServer.js` 的 `sendToUser()` 已在匿名路径下调用，匿名私信本来就有实时通道，只是不弹微信提醒；零成本、零额度、不暴露身份。
- **A2 角标**：`private_conversation.unread_count` + `utils/messageStore.js`（tab 索引 3）。注意项目用自定义 tabBar，`wx.setTabBarBadge` 不生效，走组件内更新，新增页面若绕过 `messageStore` 会漏角标。
- **A3 冷启动提示（最值得补）**：冷启动时 `unreadCount > 0` 在消息 tab 或首页顶部提示「你有 N 条新私信（含匿名）」，用 `messageController.unreadCount` 接口；是**唯一能弥补关闭期间零感知的时机**。
- **B1 公众号（服务号）模板消息 —— 唯一可控「出圈」替代**：小程序与服务号绑定到微信开放平台 → 经 **unionid** 打通 → 服务号模板消息下发，可点击跳回小程序，文案可中性化不暴露身份。缺点：用户须先关注服务号（最大转化门槛）；需**企业/组织主体认证的服务号**（个人主体只能订阅号，无模板消息能力）；需开放平台绑定，开发量大；有内容合规审查与日限额。校园场景若学校已有官方服务号可行性高，否则不建议新建。
- **B2 长期订阅 —— 走不通**（详见第六节）。
- **B3 短信/邮件**：到达率最高但按条计费，私信高频场景成本不可接受，需手机号且涉个人信息合规；**不适用于私信提醒**。
- **C1/C2 改变互动形态**：把匿名互动改成公开内容页（评论/树洞）或限定「仅双方同时在线实时」，彻底绕开推送但不点对点。
- **D1 中性文案推送（成本最低）**：解除 `if (!channelAnonymous)`，把 `pushMessage` 的 `thing1`（发送人）从 `sys_user.nick_name` 换成中性词（「一位同学」/「匿名用户」）或分身昵称（`ANON_NAMES` 池），`summary` 同步改。改动极小、匿名性保持、兼容现有额度/频控。
- **D2 匿名消息聚合推送**：窗口内聚合只推一条「你有 N 条新私信」，省额度、降刷屏，可复用 `subscribe_pending_message` 机制。

#### 5.4 组合建议与结论

- **路径 1（推荐，零新增通道）**：A1 + A2 + A3 + D1。用中性文案解除匿名限制（改动最小立刻见效），补齐冷启动提示，完全不新增基础设施。
- **路径 2（预算允许）**：路径 1 + B1，前提是有可用认证服务号，解决「关闭小程序期间」触达。
- **路径 3（产品定位调整）**：C1 或 C2，把「匿名就是不该被通知」写进产品契约，不再修补触达。

**结论**：优先走路径 1（站内通道 + 中性文案推送），长期订阅与短信均不可行，公众号模板消息仅在已有认证服务号时作为增强。

### 六、长期订阅不可用的官方限制说明

**平台规则**：长期订阅**只对政务民生、医疗、交通、金融、教育等部分二级行业类目开放**，且「仅支持少量民生公共服务节点通知，并非所有场景都支持」；模板库里有模板才能调用。

**关键反例**：微信官方社区已明确回复「**在线教育类目暂不支持开通长期订阅模板，建议通过一次性订阅或其他方式实现**」。

**结论**：校园论坛的私信提醒属于 UGC 社交互动，既不在开放类目内，也不属于「民生公共服务节点通知」。**不要在该路上投入时间**。因此本方案完全基于「一次性订阅 + 额度账户」设计，不依赖长期订阅。

#### 1.1 `audit`（审核结果通知）接入真实发送点

- **接线位置**：`server/controllers/adminController.js` 的 `reviewErrandDispute`（管理后台「日志 → 有异议」中对跑腿订单的客服裁决）。此前裁决结果只发站内信，微信端收不到。
- **做法**：新增 `notifyDisputeSubscribe(order, action, note)`，在事务提交后以**不 await** 方式对发单人与接单人各推一条。模板字段映射：`thing5 审核内容`、`phrase1 审核结果`（≤5 字，取值 `异议成立` / `异议不成立`）、`thing16 未通过原因`、`thing3 审核类型`（`订单异议裁决`）、`character_string10 订单号`；空值字段兜底为默认文案（微信不接受空值），并支持传 `orderId` 让落地页直达订单详情。
- 顺带修掉 47003 隐患：原 `pushAuditResult` 对可能为空的字段直接传空串，改用 `clipOr(value, max, fallback)` 兜底（详见 §4.2 与 §5.2）。

#### 1.2 入口显隐加服务端额度复核（修复 1，高）

- **问题**：8 个页面入口原用 `entryVisible()`，只看本地偏好与 granted。用户授权过 → 入口永久隐藏 → 额度被耗尽（一次「允许」只 +1 条，评论/私信极易耗尽）→ 之后 100% `skipped`，入口不再出现，用户无从重新订阅。
- **做法**：`utils/subscribe.js` 新增 `entryVisibleAsync(trigger)`——本地就需引导则直接返回 true，否则查一次服务端额度复核。仅本地判定「已订阅」时才发一次请求，正常路径零额外请求；额度接口异常时回落本地判定，不会误显示。8 个页面的 `refreshXxxSubscribeEntry` 统一优先使用，保留 `entryVisible` 兜底。

#### 1.3 `merged` / 无额度不再静默丢弃（修复 2，高）

- **新增表 `subscribe_pending_message`**（迁移 + `sql/init.sql` 同步）。语义为**每个 `(user_id, tpl_type)` 一个槽位**，只保留最近一条待发内容；窗口内 10 条评论最终补发 1 条（取最新），既不刷屏也保证至少一条能到。
- `push()` 命中 `no_quota` / `merged` 时 → `deferMessage()` 落槽位（原直接 return 丢内容）。
- 新增 `services/subscribeRetryService.js`（每分钟扫描，启动 20 秒后先跑一轮），调 `flushPending()`：
  - **多实例抢占**：先把自己的 `next_retry_at` 推后，`affectedRows` 抢不到就跳过（pm2 两实例不重复发）；
  - 过窗 / 额度恢复 → 补发置 `sent`；仍不可发 → 留 `pending`；重试超限（15 次）或遇永久失败（43101 / 47003）→ 置 `dropped`；
  - `push()` 新增 `fromPending` 选项：补发路径不再二次落待发，防无限套娃。

#### 1.4 `push()` 加退避重试，严格区分可重试与不可重试（修复 3，中）

抽出单次发送 `postToWechat()` 与带重试的 `callWechatSend()`，最多 1 + 2 次、退避 400ms / 1200ms。

| 可重试 | 绝不重试 |
|---|---|
| 网络超时 / 连接重置 / DNS 抖动 / HTTP 5xx | **43101** 用户拒收（额度已清零，重试只白发） |
| 微信 `-1` 系统繁忙、`45009` 接口超限、`43004` | **47003** 模板字段不符（配置问题，重试不自愈，只掩盖 bug） |

#### 1.5 广播改分批并发（修复 4，中）

`pushBroadcast` 由串行 `for-await` 改为每批 15 人 `Promise.allSettled`，批次间串行以控压。原 200 人串行时队尾延迟可累积数十秒。调用方仍不 await，不阻塞业务响应。

#### 1.6 跑腿模板路由改显式事件类型（修复 5，中）

#### 2.7 重要边界

关闭合并窗口**不能突破微信额度硬上限**：用户每点一次「允许」只 +1 条可发额度（`user_subscribe_quota.remain`，主键 `(user_id, tpl_type)`），额度耗尽后第 2 条起必然转待发表 + 站内信；突发高频场景关闭合并后更快耗尽额度。排查「收不到通知」顺序：

```sql
SELECT status, COUNT(*) FROM subscribe_message_log WHERE user_id = ? GROUP BY status;
```

| 状态 | 含义 | 处理 |
|---|---|---|
| `skipped` 占多数 | 额度不足（最可能） | 引导重新订阅；查 `user_subscribe_quota.remain` |
| `merged` 占多数 | 合并窗口命中（本改动后应趋近 0） | 确认线上 `SUBSCRIBE_MERGE_WINDOW_MS` 仍为 0 |
| `failed` | 43101 拒收 / 47003 字段不符 | 看 errcode 分别处理 |
| `sent` 占多数 | 已交给微信，到达时间由微信决定 | 属微信侧延迟，服务端不可观测 |

| 层 | 判定方 | 规则 |
|---|---|---|
| 1. 应用层「要不要调微信」 | 本项目的 tap 处理函数 | 新增入口**一律调用** `requestTriggerByTap`，不做本地短路 |
| 2. 弹窗「要不要真的弹出来」 | **微信客户端** | 用户若此前勾选过「总是保持以上选择」，微信记住选择、**不再弹窗**，静默返回上次结果（accept / reject）。平台行为，代码无法绕过 |
| 3. 页面顶部入口「要不要显示」 | `entryVisibleAsync(trigger)` | 组内每个开关偏好已开（`=== true`）**且**对应 `grantedXxx === true` **且**服务端额度 > 0 才隐藏；任一不满足则显示 |

**关键区别**：第 3 层只管**页面顶部入口的显隐**，不影响业务 tap 的弹窗。业务 tap 走 `requestTriggerByTap`，其注释明确写了「不能被本地 granted 缓存或服务端额度状态短路」—— 因为这是用户主动点击，必须把决定权交给微信客户端。

### 七、弹窗触发节流层（2026-09-16）

#### 7.1 需求

8 个订阅消息模板触发组，针对**同一触发组**，当用户**未勾选「总是允许」**时，
限制该组的授权弹窗**每天最多弹出 3 次**，达到上限后当天不再弹出。

实现在 `utils/subscribe.js`，闸门加在 `requestTriggerByTap()` 里。

#### 7.2 设计要点 1：节流计数的存储与管理

**两个本地存储键（`wx.getStorageSync` / `setStorageSync`）：**

```js
// 1) 节流计数（按触发组维度）
'subscribe_popup_throttle' = {
  day: '2026-09-16',              // 计数所属的自然日，跨天判定的唯一依据
  groups: {                       // 触发组 → 当天已弹次数
    postPublish: 3,
    errandPublish: 1
  }
}

// 2) 微信侧「总是」选择的本地缓存（按模板类型维度）
'subscribe_always_choice' = {
  commentNew: 'accept',           // 'accept' | 'reject' | 'ban'
  commentReply: 'accept',
  updatedAt: 1758000000000
}
```

**为什么必须放本地存储，不能放服务端**（这是整个设计的硬约束）：

> 微信要求 `wx.requestSubscribeMessage` 必须在用户点击手势的**同步调用调用链**内调用。
> 因此「今天还能不能弹」必须在 tap 里**同步判定完毕** —— 来不及等任何异步接口返回。
> 只能用 `getStorageSync` / `setStorageSync` 这对同步 API。

**为什么两个键分开、而不是合并成一个：**

| | 键 1 节流计数 | 键 2 总是选择缓存 |
|---|---|---|
| 维度 | 触发组（8 个） | 模板类型（20 个） |
| 写入时机 | 每次业务触发 | app onShow + 每次授权回调 |
| 跨天处理 | 需要重置 | **不能**重置（与日期无关） |

两者的生命周期完全不同，合在一起会让「跨天重置」误清掉「总是允许」的缓存。

**为什么计数用「一个键 + groups 对象」而不是「每组一个键」：**
一次触发只需要读改写一个键，且**便于整体查看/清空**（`clearThrottle()`）。
小程序存储是同步 API，不存在并发写冲突，所以不需要分散成多个键。

#### 7.3 设计要点 2：每天的计数重置规则

| 项 | 规则 |
|---|---|
| **判定依据** | 存储里的 `day` 字段与「当前**本地**自然日 `YYYY-MM-DD`」是否一致 |
| **重置时机** | **惰性重置** —— 每次读取节流状态时比对；不一致就整组清零并写入新 `day` |
| **不重置的东西** | `subscribe_always_choice`（总是选择与日期无关） |

**为什么用本地时区而不是 UTC**：用 UTC 的话，东八区要到早上 8 点才「换天」，
用户在 00:00~08:00 之间会被算作前一天，出现「明明是新的一天却已经用满 3 次」的怪象。
实现里用 `getFullYear()` / `getMonth()` / `getDate()`（本地时区）拼接。

**为什么用惰性重置而不是定时器**：小程序没有可靠的常驻定时器
（用户可能整天不打开、进程随时被回收），定时器方案在「整天没打开」时根本不会跑。
惰性判定天然覆盖这个场景，语义上等价于每天 00:00 清零。

#### 7.4 设计要点 3：勾选「总是允许」后的行为差异

**判定方式**：`wx.getSetting({ withSubscriptions: true })` 的
`subscriptionsSetting.itemSettings[模板ID] === 'accept'`。
**键不存在 = 用户没做过「总是」选择**（即未勾选）。

**口径**：组内**全部**模板都是 `accept` 才算「已勾选总是允许」——
与 `shouldShowDialog`「组内每个都满足才静默」保持一致。

**但 `getSetting` 是异步的，不能在 tap 里现查**，所以维护本地缓存
`subscribe_always_choice`，由**非 tap 路径**刷新：

1. `app.js` 的 `onShow()`（用户可能刚在小程序设置页改过选择）；
2. 每次 `wx.requestSubscribeMessage` 回调之后（用户可能就是在这一次勾上了「总是保持以上选择」）。

**行为差异：**

| 用户状态 | 是否节流 | 是否调用微信 | 说明 |
|---|---|---|---|
| **已勾选「总是允许」** | **跳过**（不读也不写计数） | **照常调用** | 微信不会再弹窗，但每次调用仍会**静默 accept 并 +1 条额度**。停掉调用等于主动掐断额度来源 —— 本项目额度覆盖率本就是瓶颈，所以这里必须继续调 |
| 未勾选（键不存在） | 应用 | 前 3 次调用，之后不调用 | 需求要求的默认行为 |
| 「总是拒绝」(`reject`/`ban`) | 应用 | 前 3 次调用，之后不调用 | 需求原文是「未勾选总是允许即节流」，`reject` 属于未勾选。此时微信也不弹窗，会白耗次数；但用户仍可通过**顶部订阅入口**恢复（见 7.6 第 5 条） |

**缓存撤销的处理**：`refreshAlwaysChoice()` 里，若 `itemSettings` 中**键消失**
（用户把「总是允许」改回「每次询问」），必须 **`delete cache[模板]`**。
漏了这一步会让缓存永远停在 `accept`，表现为「永久跳过节流」。

#### 7.5 整体触发流程

```
业务 tap（点帖子 / 发布需求 / 消息 tab / 发起活动 …）
  │  必须仍在 tap 的同步调用链内
  ▼
subscribe.requestTriggerByTap('<触发组>')
  │
  ├─ ① 该组有可用的模板 ID 吗？
  │      否 ──► 直接返回（不计数、不调用微信）
  │
  ├─ ② 读「总是允许」缓存：组内模板**全部** accept ？
  │      是 ──► 【跳过节流】────────────────┐
  │      否 ↓                                │
  │                                          │
  ├─ ③ 读节流计数（day 不匹配则惰性清零）      │
  │      used >= 3 ──► 上报一行「命中节流」日志 │
  │                    （fire-and-forget）      │
  │                    返回 { throttled:true }  │
  │                    **不调用微信**，静默无提示
  │      used <  3 ──► used+1 写回存储 ──────┤
  │                                          │
  ▼                                          ▼
④ wx.requestSubscribeMessage（原生弹窗）
  │
  ▼

        + refreshAlwaysChoice 刷新「总是允许」缓存
```

#### 7.6 关键边界情况

| # | 边界 | 行为 | 理由 |
|---|---|---|---|
| 1 | **顶部入口 `requestEntryByTap` 不受节流** | 走 `requestTypesByTap`，不经过闸门 | 那是用户**主动**点订阅入口；被拦会变成「点了没反应」—— 本项目修过的老问题（`requestEntryByTap` 注释里专门写了这条） |
| 2 | **计数在调用微信「之前」+1**（乐观计数） | 写存储成功后才调微信 | 可重入安全：同步连点 5 次只会调用 3 次微信；若改在回调里补记，页面中途卸载就会漏记 |
| 3 | **同步连点** | 第 4 次起直接返回 `throttled` | 由第 2 条保证，不会超限 |
| 4 | **跨天时用户仍在小程序里** | 下一次触发时才重置 | 惰性重置的必然结果，语义等价于每天 00:00 清零 |
| 5 | **「总是拒绝」用户** | 仍受节流（3 次/天） | 需求原文如此。此时微信静默 reject、弹窗不出现，会白耗次数；但 `entryVisibleAsync` 要求 `grantedXxx === true` 才隐藏入口，所以他们的**顶部入口一直可见**，点它走 `requestEntryByTap` → `guideReopen` 引导去设置页 —— 恢复路径不受节流影响 |
| 6 | **`types` 为空**（触发组不存在 / 模板 ID 未配置） | 提前返回，**不计数** | 避免无效触发占用当天额度 |
| 7 | **`setStorageSync` 抛错**（存储超限/被清理） | 退化为**不节流** + `console.warn` | 宁可多弹一次，也不能因存储异常让用户彻底看不到授权入口（那会直接掐断额度来源） |
| 8 | **`getSetting` 失败** | `refreshAlwaysChoice` resolve `null`，**保留旧缓存不清空** | 避免误伤真·总是允许用户的额度累积；失败是极少数情况 |
| 9 | **缓存陈旧** | 最坏多弹 1~3 次，下次刷新即纠正 | 刷新时机见 7.4；用户在设置页改选择后，最迟回到前台就纠正 |
| 10 | **系统时间被手动改** | `day` 变化即重置 | 不精确（往前调也会重置），但不会把用户卡死 |
| 11 | **多端 / 重装 / 清缓存** | 计数不跨设备同步，清缓存即归零 | 计数是纯本地存储，这是已知取舍 |
| 12 | **与「额度不足」无关** | 节流只管「弹不弹窗」，不管「能不能发出去」 | 额度不足是服务端 `skipped`（见 §3），两回事；没额度时更要弹，否则用户无从恢复 |
| 13 | **节流时不弹任何提示** | 静默返回 | 每天提示「今天不能再弹了」本身就是另一种打扰 |

#### 7.9 命中节流日志（管理后台「命中节流」）

节流命中会写一行 `status='throttled'` 的日志，管理后台「日志 → 订阅消息」筛选栏最右侧新增 **「命中节流」** 按钮查看。

**为什么必须由客户端上报**：节流判定发生在 `wx.requestSubscribeMessage` 的同步调用链内，
服务端完全无从感知「这次点击被本地拦下了」。所以 `throttled` 是**唯一由客户端主动写入**的状态。

链路：

```
requestTriggerByTap 判定 used >= 3
  └─ reportThrottleHit(trigger, used)      ← fire-and-forget，不 await、不抛错
       └─ POST /api/v1/subscribe/throttled  (auth)
            └─ subscribeService.logThrottleHit() → INSERT subscribe_message_log(status='throttled')
```

上报字段与落库映射：

| 上报字段 | 落库列 | 说明 |
|---|---|---|
| `tplType` | `tpl_type` | 取该触发组的**首个模板类型** —— 触发组是客户端概念，服务端只认模板类型；用真实模板类型才能让后台显示中文标签 |
| `triggerLabel` | `summary` | 渠道文案（如「评论通知」），后台单独一行展示，也便于关键词搜索 |
| `used` / `limit` | `errmsg` | 渲染成「今日已弹 3 次，上限 3 次，本次不再弹窗」 |

后台展示效果：

```
#1023  命中节流  [紫色角标]
2026-09-16 21:00:04 · 用户 广轻观察(67)
评论通知
命中弹窗节流（该组当天已达 3 次上限，未调用微信）：今日已弹 3 次，上限 3 次，本次不再弹窗
```

**边界**：
- 上报是 **fire-and-forget**：`reportThrottleHit` 不 await、内部 `.catch(() => null)`，且调用点再包一层 try/catch ——
  **上报失败绝不影响节流判定**（护栏 K2）。
- **每次都上报**（不按天去重）：与 `skipped` 一样按次记录，便于看「这个用户/这个入口被拦得有多频繁」。
  代价是量级与用户点击次数同阶 —— 若日后觉得太吵，在 `reportThrottleHit` 里加一个「同组每天只报一次」的窗口即可（一处改动）。
- `throttled` 行**没有 errcode**，所以后台不需要 errcode 中文映射。

**数据库改动**：`subscribe_message_log.status` 枚举从
`('sent','merged','skipped','failed')` 扩到 `('sent','merged','skipped','failed','throttled')`，
`migrations.js`（带 `SHOW COLUMNS` 守卫的 `MODIFY COLUMN`）与 `sql/init.sql` 都已同步；
漏了枚举会导致写入被截断成空串（`ER_DATA_TRUNCATED`）。

**管理后台改动**：`pkg-admin/admin/` 的 `index.wxml`（筛选按钮 + 状态角标映射）、
`index.js`（`SUBSCRIBE_STATUS_TEXT` / `SUBSCRIBE_STATUS_HINT` 增加 throttled）、
`index.wxss`（`.st-throttled` 紫色，与「发送失败」的红色区分开）。

#### 7.10 顺带补的健壮性保护

`persistAccepted()` 原来直接调 `wx.getStorageSync` / `setStorageSync` 且**没有 try/catch**。
它是在 `.then` 里被调用的，而调用方写的是 `subscribe.requestTriggerByTap('x')`（没接 catch）——
存储一旦抛错（超限、被系统清理）就会冒泡成**未处理的 promise rejection**。
现已把整个循环体包进 try/catch，失败只 `console.warn`：
授权结果写不进去只影响后续的静默判定，绝不能因此影响主流程。

### 一、排查订阅消息的标准动作与判据

#### 1. 核心表与各状态含义

排查以 `subscribe_message_log` 为唯一事实源。拿用户 id 跑一句 SQL，按 `status` 分流：

```sql
SELECT id, user_id, tpl_type, status, errcode, errmsg, page, created_at
FROM subscribe_message_log
WHERE user_id = ? ORDER BY id DESC LIMIT 20;
```

| 查到的状态 | 含义 | 是不是「延迟」 |
|---|---|---|
| 查不到记录 | 业务事件没触发；或该类型不推送（点赞只发站内信，`notificationService` 只推 comment/follow/reply）；或消息被合并窗口判到别处 | 不是延迟，是没发 |
| `skipped`（errmsg = 额度不足） | 用户没授权过，或授权次数已用尽 | 不是延迟，是没发 → 引导重新订阅 |
| `merged` | 5 分钟窗口内同类消息已发过，本次**直接丢弃且不补发** | 不是延迟，是丢弃 |
| `failed` + errcode | `43101` 用户拒收/未订阅（服务端已清零额度）· `47003` data 字段超长/与模板不符 · `40003` openid 无效 · `45009` 接口调用超限 | 是失败，不是延迟 |
| `throttled` | **客户端本地弹窗节流命中**：该触发组当天已弹满 3 次，本次**连微信都没调用**。这是唯一由客户端上报写入的状态（见《功能实现与改造》§七） | 不是延迟、也不是失败 → 用户当天被弹窗次数上限拦下，次日自动恢复 |
| `sent` | **我方已成功交给微信**，之后到达时间由微信投递决定，服务端无任何可观测手段 | 延迟在微信侧 |

> `sent` 之后的延迟只能靠用户配合定位：① 微信是否在后台运行/刚开机联网；② 微信「设置 → 新消息通知」是否开启；③ 小程序订阅消息设置里该项是「允许」还是「拒绝」。这三项都在微信客户端，服务端查不到。

#### 2. 如何自证我方无延迟（时间戳对比法）

把 `subscribe_message_log.created_at`（发送成功返回后才写）与业务表（`private_message` / `forum_comment`）的 `created_at` 对齐比较，**同秒即证明我方即时发出**。

此外：`subscribe_message_log` 是**授权阶段不产生流水**的——订阅授权（微信弹窗）阶段不会有新记录，故「开关自动关闭」类问题**不能靠查库**，必须在客户端看（见第七节）。

#### 3. 标准排查顺序（可复用）

1. 取 `subscribe_message_log` 按用户/类型/状态分流（上表）。
2. 看 `status` 分布：`skipped` 多 → 额度；`failed` 多 → 看 errcode；`merged` 多 → 合并窗口。
3. 服务端 `err.log` 中 `[Subscribe]`/`[MessageSubscribe]`/`[ErrandSubscribe]`/`[SubscribeLog]` 计数若为 0，说明微信接口从未返回 errcode、也从未抛异常。
4. 客户端问题（授权弹窗/开关回弹）→ 用 vConsole 看原生弹窗、`wx.getStorageSync('subscribe_comment_prefs')`、`subscribe_reopen_guide_*` 节流键。

### 二、推送延迟排查结论（2026-09-14）

#### 现象

用户反馈订阅消息「明显延迟 / 收不到」。

#### 根因结论

**不是小程序/服务端发送时机问题。** 实测服务端在业务事件发生的**同一秒**就调用了微信发送接口，全链路耗时 < 1 秒，且历史 156 次发送**零失败**。真实原因排序：

| 排序 | 真实原因 | 占比/证据 | 是否小程序自身问题 |
|---|---|---|---|
| 1 | 订阅额度已用尽被跳过（`skipped` 额度不足） | 125 / 156 = **80%** | 是（机制设计导致，需补引导） |
| 2 | 5 分钟合并窗口把重复提醒直接丢弃（`merged`） | 13 / 156，集中在高频类型 | 是（丢弃且不补发） |
| 3 | 微信客户端投递延迟（用户不在线/被后台清理时下次联网才到达） | 服务端不可观测 | 否（微信机制） |

### 三、订阅开关「开启后自动关闭」根因与修复（2026-09-15）

#### 现象

视频（7.05 秒）逐帧还原：顶部「订阅评论消息提醒」开关在 2.4s 点亮变绿，2.80~2.93s 动画回弹到灰色关闭，全程**无微信原生授权弹窗、无任何 toast/提示**。

#### 根因

1. **受控组件被无条件复位**：入口行 `<switch checked="{{xxxSubscribeChecked}}">`，点击链 `onXxxSubscribeTap → applyXxxSubscribe`（先 `setData({xxxSubscribeChecked:true})` 变绿，再 `subscribe.requestEntryByTap(trigger)`），而 `refreshXxxSubscribeEntry()` **无条件**把开关置回关闭：

   ```js
   refreshXxxSubscribeEntry() {
     ...
     subscribe.entryVisibleAsync('trigger')
       .then((need) => this.setData({ showXxxSubscribeEntry: !!need, xxxSubscribeChecked: false }))
     //                                                              ↑ 无条件复位
   }
   ```

   请求一返回（不论成败）开关就被数据拽回关闭。

2. **主动点击被 7 天节流导致「无任何提示」**：`requestEntryByTap()` 把用户主动点击也交给带 7 天节流的 `guideReopen()`（`subscribe_reopen_guide_post_publish`），节流初衷是「别被动打扰」，但主动求助被节流 `if (last && Date.now() - last < 7天) return false` → 静默返回。这是「自动关闭且无解释」的确定性根因。

3. **请求为何快且无声**：`utils/subscribe.js` 的 `requestSubscribe()` 四条出口中三条不弹窗——① 无可用模板 ID（`validIds()` 为空）直接 resolve 不弹窗；② 微信侧已「拒绝/不再询问」（`reject`/`ban`/`filter`）不展示弹窗；③ 接口失败（20004 总开关关闭 / 20001 模板不可用）有 toast（已排除，因视频无 toast）；④ 正常有弹窗（已排除）。结合 `TEMPLATE_IDS` 的 `commentNew`/`commentReply` 均为真实有效 ID，最可能是 **② 微信侧已记住「拒绝」**。

#### 处理

`utils/subscribe.js`：

- `requestEntryByTap` 调用 `guideReopen` 时**不再传 `throttleKey`**（节流只保留给被动触达如聊天页发送顺带引导），用户每次主动点击必得反馈。
- `requestSubscribe()` 返回值新增 `failed` 字段；`requestEntryByTap()` 新增 `guided` 字段。
- 三条静默路径全部补齐可见反馈：

  | 场景 | 修复前 | 修复后 |
  |---|---|---|
  | 微信侧已拒绝/不再询问 | 静默回弹 | 弹「微信通知已关闭」引导弹窗，带「去开启」跳设置页 |
  | 用户本次点了「取消」 | 静默回弹 | toast「未开启，可再次点击重试」/「部分未开启，可再次点击补齐」 |
  | 请求失败（20004/20001） | 已有 toast | 保留 toast，不再叠加引导弹窗 |
  | 无可用模板 ID | 完全静默 | toast「订阅模板暂不可用」+ `console.warn` 留痕 |

- 补 `TPL_LABELS`（20 个模板中文名，与服务端 `subscribeService.js` 的 `TPL_CONFIG.label` 同源一致），提示改为点名式：漏 1 项 →「评论回复通知未勾选，再点一次勾上」；漏 2+ 项 →「还有 N 项未勾选，再点一次逐项勾上」；全未勾 →「未勾选，再点一次逐项勾上」。
- 新增 `pendingTypesFor(trigger)`：**只申请还没允许的那几项**，第二次点击原生弹窗里只剩缺的项；全已授权时回退整组（`rule.keys.slice()`）用于额度耗尽后重新攒。抽出 `requestTypesByTap(types)` 复用「申请 + 落库」。

> 微信硬约束：`wx.requestSubscribeMessage` 必须在用户点击手势同步调用栈内调用，原生弹窗 `success` 回调里再调会被拒（`fail: can only be invoked by user TAP gesture`），故技术上无法自动连弹两次——只能让下一次点击弹窗只剩缺的项。

#### 涉及文件·接口·表

| 文件 | 改动 |
|---|---|
| `utils/subscribe.js` | `requestSubscribe` 新增 `failed` + 无模板 ID 留痕；`requestEntryByTap` 去节流、补三类反馈、返回 `guided`；新增 `TPL_LABELS`；新增 `pendingTypesFor` + `requestTypesByTap` |
| `server/tests/top-subscribe-entries.test.js` | 新增 F3（点名式反馈）与 F4（补齐时弹窗只含缺的项）；A~E/F 断言按新语义更新 |

#### 验证

- F4 核心断言第二次点击 `tmplIds` 只含未勾选项（反向验证：换回 `typesForTrigger` 立刻变红）。
- 全量回归：**71 / 71 通过**。

#### 结论与进一步建议（待拍板）

根因是交互语义：一次性订阅额度会被用尽，开关永远无法如实表达状态。建议把入口右侧 `<switch>` 改为按钮式（`[ 去订阅 › ]`），点一次申请一次授权，右侧显示真实状态文案（`未订阅` / `已订阅 · 剩余 2 次`），从根上消除「开关自动关闭」误解，也顺带解决「额度耗尽后用户不知要补订阅」。影响面：8 个页面 WXML 各一行 + `app.wxss` 的 `.sub-notice-*` 样式 + 相关测试断言，属视觉改动需确认。

### 五、凭据失效（access_token / 模板 ID 失效）的处理

> 与第四节同源（2026-09-16 修复说明 + 排查报告第八节）。冲突以最新（2026-09-16）为准：凭据失效的代码修复**已实现，但截至 2026-09-16 13:19 排查采集时尚未部署上线**。

#### 现象

管理后台「发送失败」截图：`#733 message`、`#720 auditPass` 报 `invalid credential, access_token is invalid or not latest`；`#259/#258/#252 commentReply` 报 `argument invalid! data.thing20.value is empty`。实为**两类互不相干的失败**。

#### 根因 A（真 Bug，本次修复）：access_token 被多实例互相作废

1. **用了会互相作废的 `cgi-bin/token`**：`server/utils/wechatToken.js` 原本请求 `GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&...`。微信文档明确：该接口每调用一次就签发新 token 并让上一次立即失效。而本服务是 **pm2 cluster 2 实例**，`cachedToken` 是**进程内变量**（每实例一份）：

   ```
   实例 A 缓存到期 → 刷新 → 拿到 token-A2（token-A1 作废）
   实例 B 手里还是 token-A1（本地缓存认为没过期）→ 发消息 → 微信拒绝 40001
   ```

2. **40001 不在重试列表、也没换 token 动作**：修复前 `const RETRYABLE_WECHAT_CODES = [-1, 45009, 43004]`，`callWechatSend` 遇不在列表的码立刻 return，`postToWechat` 只 `getAccessToken()` 读本地缓存。token 被顶掉后这条消息直接记 `failed` 永久失败，无自愈。

3. **为什么能确定是多实例不一致而非 token 全局失效**：看 2026-09-15 23:42~23:49 上下文，失败与成功在几分钟内交替出现（720 失败 23:42:13 → 722 成功 23:43:53 → … → 733 失败 23:49:04 → 734 成功 23:49:54）。若全局失效会全部失败。微信报错文案自身即答案：`...could get access_token by getStableAccessToken`。

#### 处理 A（凭据失效）

1. `server/utils/wechatToken.js` 改用 **`cgi-bin/stable_token`**（POST JSON）：

   ```json
   { "grant_type": "client_credential", "appid": "..", "secret": "..", "force_refresh": false }
   ```

   `force_refresh=false` 时有效期内反复调用**返回同一 token**，多实例互不作废。`forceRefresh: true` 映射 `force_refresh: true`（签发新 token），**只在拿到 40001/42001 之后的自愈路径用**，常规路径绝不传。

2. `server/services/subscribeService.js`：

   ```js
   const RETRYABLE_WECHAT_CODES = [-1, 45009, 43004, 40001, 42001, 40014]
   const TOKEN_ERROR_CODES = [40001, 42001, 40014]
   ```

   命中 `TOKEN_ERROR_CODES` 打标记，下一轮 `postToWechat` 用 `getAccessToken({ forceRefresh: true })` 换新 token 重发，属可自愈错误，不该记 failed。

3. `server/scripts/verify-wechat-config.js` 也改 `stable_token`——原脚本走 `cgi-bin/token`，**跑一次就把线上正在用的 token 弄失效**，是隐藏地雷。

#### 根因 B（已修复的历史记录）：`thing20` 空值

`argument invalid! data.thing20.value is empty` 是 `commentReply` 模板 `thing20`（原文内容）为空，微信返回 47003（不可重试）。该模板历史 11 次发送 **100% 失败、0 次成功**，已于 2026-09-15 修复：

```js
thing20: { value: clipOr(postDigest, 20, '你发布的帖子') }
```

截图里 `#259/#258/#252` 的时间是 2026-09-15 02:21~02:23，早于修复部署，属修复前历史流水。

#### 区分两类失败

| 判据 | 凭据失效（Bug A） | 字段空值（Bug B） |
|---|---|---|
| errmsg 关键词 | `invalid credential` / `access_token is invalid or not latest` | `argument invalid! data.xxx.value is empty` |
| 涉及模板 | 随机（取决于命中哪个实例） | 固定（同一模板同一字段） |
| 时间分布 | 零散、突发 | 连续、稳定复现 |

### 六、匿名私信订阅提醒（2026-09-15 修复说明）

#### 现象

使用匿名（分身）私信发消息后，对方明明已开启订阅消息，却收不到任何微信提醒；且 `subscribe_message_log` **连一行记录都不留**（既无 `sent` 也无 `skipped`），与「额度不足」症状极相似，是本次排查绕弯的主因。

#### 根因

`server/controllers/messageController.js` 的 `createPrivateMessage()` 把推送逻辑整块包在条件里，由 commit `a863751b`（2026-09-11）引入，理由「保留匿名性，避免泄露身份或打扰」：

```js
// 修复前
const channelAnonymous = conversation.isAnonymous || conversation.peerIsAnonymous
...
if (!channelAnonymous) {                 // ← 匿名会话永远进不来
  pool.query('SELECT nick_name FROM sys_user WHERE id = ?', [senderId])
    .then(([rows]) => subscribeService.pushMessage(receiverId, {...}))
}
```

`channelAnonymous` 是**会话级**（`isAnonymous || peerIsAnonymous`，任一侧匿名即为真），故：匿名发起方发消息 → 不推；**普通用户回到匿名会话回复 → 也不推**（很多人不知自己在「匿名渠道」）。该分支在 `writeLog()` 之前就返回，故无日志。

#### 处理

| 位置 | 问题 | 修复 |
|---|---|---|
| `messageController.js`（新增 `resolveSenderNick`） | 匿名身份只能靠「不推」保护，代价功能不可用 | 抽昵称解析：**匿名方用分身昵称**（会话存档 `anon_self_identity`，与聊天页同源），匿名分支刻意不查 `sys_user.nick_name` |
| `messageController.js`（`createPrivateMessage` 推送段） | `if (!channelAnonymous)` 整块跳过 | 移除该条件，**改为无条件推送**，发送人昵称统一经 `resolveSenderNick` 解析 |
| `app.js`（新增 `noticeColdStartUnread`） | 小程序关闭期间收到消息零触达 | 冷启动拿到未读总数后延时 1.5s 给一次 toast；已在消息页不打扰，一次冷启动只提示一次 |
| `utils/messageStore.js` | — | 未改动，A1/A2 原本具备 |
| `wsServer.sendToUser()` 调用 | — | 未改动，原本就在 `if (!channelAnonymous)` **之前**，匿名私信一直有实时通道，只是不弹微信提醒 |

#### 昵称判定为什么用 `isAnonymous` 而不是 `channelAnonymous`

| 谁在发 | `channelAnonymous` | `isAnonymous` | 推送该显示 |
|---|---|---|---|
| 匿名发起方 | true | **true** | 分身昵称（如「深幽的洞穴」） |
| 普通用户回复匿名方 | true | **false** | 真实昵称 |

普通用户回复时聊天页显示他自己的真名，推送文案须一致，否则对方看到的身份对不上。故判定锚定**发送方自己那一侧**的匿名标记。

#### 涉及文件·接口·表

- 服务端：`server/controllers/messageController.js`（`resolveSenderNick`、`createPrivateMessage` 推送段）。
- 小程序端：`app.js`（`noticeColdStartUnread`）。
- 既有未改：`utils/messageStore.js`、`wsServer.sendToUser()`。
- 表：`private_message`、`sys_user`、`private_conversation.unread_count`、`subscribe_message_log`。
- **无数据库迁移**（不涉及表结构）。

#### 验证

新增 `server/tests/anonymous-message-subscribe.test.js`（9 条，全量回归 **74 / 74 通过**）：匿名方→必调 `pushMessage` 且 `senderNick`=分身昵称；匿名分支不得查 `sys_user.nick_name`；普通私信 `senderNick`=真实昵称；**普通用户回复匿名方同样必推送**（旧实现整块跳过，核心回归点）；分身缺失兜底「匿名用户」且不查真名不产生空值（防微信 47003）；源码护栏不得再出现 `if (!channelAnonymous)`；A1 推送位于订阅前、A2 联动角标、A3 冷启动提示仅一次。

#### 影响与注意事项

1. 匿名私信会消耗对方 `message` 模板额度（每次扣 1 条），同一收件人若同时收普通与匿名私信，额度更快耗尽——既有机制必然结果，非新增缺陷。
2. 消息摘要出现在微信通知（`digest` = 内容前 20 字），锁屏可见，与普通私信一致。
3. 匿名性未被削弱：发送人栏只有分身昵称，分身缺失兜底「匿名用户」，**绝不回落真实昵称**。
4. 不会刷屏：`SUBSCRIBE_MERGE_WINDOW_MS=0`（不合并）保持原样。

#### 部署清单

- 服务端 `server/controllers/messageController.js`：`deploy.py`/`deploy_full.py`，改完 `pm2 restart`。
- 小程序端 `app.js`：开发者工具「上传」（A3 才生效）。
- 三端发布互不联动；真机仍显示旧聊天页入口说明上次入口改动也还没上传，本次一起发布。
