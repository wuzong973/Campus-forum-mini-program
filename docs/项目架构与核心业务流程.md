# 项目架构与核心业务流程

## 概述

本仓库是一个「微信小程序前端 + Node.js 后端 + MySQL 数据库 + 教务系统爬虫」的校园综合服务项目，承载校园服务导航、课程表同步、社区论坛、代拿跑腿与私信等能力。

技术栈：小程序端为原生微信小程序（WXML/WXSS/JS）；服务端为 Node.js + Express + MySQL（另含 Redis 7，见 FEATURE_DOC.md），鉴权用 JWT（Bearer Token），实时消息用 WebSocket；教务爬虫基于 Node.js + axios + cheerio + tesseract.js。

仓库结构：小程序前端位于仓库根目录（`pages/` `components/` `utils/` `assets/`）；后端服务位于 `server/`；教务系统爬虫位于 `jw-crawler/`。三者单仓维护，非多仓前后端分离模式。

## 一、整体架构

### 1.1 分层架构图

```text
┌───────────────────────────────────────────────────────┐
│ 小程序端（pages / components / utils）                  │
│  utils/request.js → utils/api.js → 业务页面             │
└───────────────────────────┬───────────────────────────┘
                            │ HTTPS + Authorization: Bearer <JWT>
                            ▼
┌───────────────────────────────────────────────────────┐
│ Node.js + Express 服务端（server/）                     │
│  middleware/* → routes/* → controllers/*                │
│  services/*（如 jwScheduleSyncService）                 │
│  WebSocket 服务（wss://<域名>/ws?token=<JWT>）          │
└──────────┬─────────────────────────────┬───────────────┘
           │                              │
           ▼                              ▼
      MySQL 8.0 (+Redis 7)          微信（登录 / 内容安全 / 支付）
           ▲
           │ 服务端内部调用
┌──────────┴────────────────────────────────────────────┐
│ jw-crawler/ 教务系统爬虫（登录 / OCR / 抓取 / 解析）     │
└───────────────────────────────────────────────────────┘
```

数据归属（以 api-contract.md 为准）：服务端是用户、帖子、评论、对话、课程、跑腿与维修订单的**单一数据源**；本地存储仅缓存读取模型或排队可合并的设置（如个人资料、课表配置），支付完全由服务端微信回调最终确认。

### 1.2 目录职责

- **仓库根目录（小程序前端）**
  - `app.js` / `app.json` / `app.wxss`：小程序全局入口与全局配置（TabBar 四个页面在 `app.json` 的 `pages` 注册）。
  - `pages/`：业务页面，按主导航、课表、社区、用户设置等分组。
  - `components/`：通用组件（`service-grid`、`post-card`、`errand-card`、`load-more`、`empty-state` 等）。
  - `utils/`：公共工具层（请求封装、API、鉴权、课表标准化、WebSocket 等）。
  - `assets/`：图标、TabBar、横幅等静态资源。
- **`server/`（Node.js 后端）**
  - `app.js`：服务入口。
  - `routes/*.js`：路由层；`controllers/*.js`：控制器层；`services/*.js`：业务聚合（如 `jwScheduleSyncService`）。
  - `middleware/*.js`：鉴权、限流、日志、异常处理、内容安全。
  - `utils/migrations.js`：数据库迁移；`sql/init.sql`：初始化脚本。
  - `.env`（复制自 `.env.example`）：DB、Redis、JWT、微信 AppID 等环境变量。
- **`jw-crawler/`**
  - 教务系统登录、验证码 OCR、课表 HTML 抓取与结构化解析；**不直接运行在小程序内**，由后端 `server/services/jwScheduleSyncService.js` 调用。

## 二、核心业务流程

> 以下流程中，接口路径以 `api-contract.md` 为准，交互细节以 `核心业务流程说明.md`（2026-09-11）为准。

### 2.1 用户身份链路

**微信登录**（前端 `pages/login/index` + `utils/auth.js`；后端 `POST /api/v1/user/phone-login` → `userController.phoneLogin`）：

1. 小程序获取微信登录 `code`。
2. 小程序获取手机号授权 `phoneCode`。
3. 后端调用微信接口换取 `openid` 与手机号。
4. 后端按手机号优先匹配 `sys_user`。
5. 后端签发 JWT。
6. 前端保存 `token` 与 `userInfo`。

身份结果：小程序内业务鉴权依赖 JWT；`req.userId` 成为后端所有业务数据隔离依据。

**身份与课表同步的衔接**：课表同步接口必须先经 JWT 认证——未登录由前端直接拦截；已登录未认证学号允许输入教务账号同步；已认证学号仅允许同步与当前认证学号一致的教务账号，避免写入他人课表。

### 2.2 课程表读取链路

入口：`pages/schedule/index`、`pages/index/index`、`utils/api.getScheduleList`；后端 `GET /api/v1/schedule/list`。

1. 前端请求后端课表列表。
2. 后端读取 `user_schedule`。
3. 前端用 `utils/schedule.normalizeCourse()` 标准化课程字段。
4. 按 `startWeek / endWeek / weekType` 过滤当前周课程。
5. 课表页渲染周视图。
6. 首页按「当前周 + 今天星期 + 单双周」提取今日课程提醒。

**当前周过滤规则**：当前周须满足 `startWeek <= currentWeek <= endWeek`；`weekType = all` 直接展示，`odd` 仅奇数周展示，`even` 仅偶数周展示。

### 2.3 教务系统课表同步主流程

**用户触发**（`pages/schedule/index`）：打开课程表左侧抽屉 → 点击「同步我的课表」→ 前端检查是否已登录 → 已登录则跳转 `pages/schedule-login/index`。

**教务登录页**（`pages/schedule-login/index`）：若用户资料已有 `studentId` 自动回填账号；输入密码点「同步课表」→ 前端调用 `api.syncSchedule(username, password)`，请求层使用更长超时避免被 15 秒超时截断。

**后端同步接口**（`POST /api/v1/schedule/sync`）：

1. 校验 JWT。
2. 校验账号密码非空、账号格式合法。
3. 若用户已认证学号，则校验输入账号必须一致。
4. 读取用户 `schedule_config.start_date`。
5. 调用 `jwScheduleSyncService.syncScheduleFromJw()`。

**爬虫适配服务**（`server/services/jwScheduleSyncService.js`）：

1. 创建 `JwCrawler` 实例。
2. 注入 OCR 语言包路径与超时、限流参数。
3. 按登录模式登录教务系统。
4. OCR 自动识别验证码。
5. 逐周抓取课表 HTML。
6. 解析为课程数组。
7. 将多周课程聚合成「课程 + 周范围 + 单双周」标准结构。

聚合结果字段：`name`、`location`、`teacher`、`weekDay`、`startTime`、`endTime`、`startWeek`、`endWeek`、`weekType`、`color`。

**数据入库**（`user_schedule`，本次新增字段 `week_type` 用于表达单双周）：开启事务 → 删除该用户旧课表 → 插入新课表 → 提交事务 → 返回课程数组与学期开始日期。

**前端同步收口**：将课程数组写入本地 `schedule_courses`；将 `startDate` 写入 `scheduleConfig`；返回上一页；课表页 `onShow` 重新计算当前周并重新拉取列表。最终本地缓存、后端数据库、页面展示三者均刷新。

### 2.4 同步异常处理

| 场景                       | 处理                                                   |
| -------------------------- | ------------------------------------------------------ |
| 学号/密码为空（前端）      | `wx.showToast`                                         |
| 未登录 / 学号不匹配        | 后端返回 `401/403`，前端弹框提示                       |
| 教务账号/密码错误          | 归一化为「教务系统登录失败，请检查账号或密码」         |
| 网络异常（连接重置/DNS）   | 归一化为「网络异常，暂时无法连接教务系统」             |
| 爬虫请求超时               | 归一化为「爬虫请求超时，请稍后重试」                   |
| 验证码识别失败             | 归一化为「验证码识别失败，请稍后重试」                 |
| 课表数据解析失败           | 归一化为「课表数据解析失败，请稍后重试」               |
| 频繁/重复触发同步          | 同步中再次触发直接拒绝；短时间重复返回限频提示         |

### 2.5 首页课表提醒流程

入口 `pages/index/index`：读取课程表列表 → 根据 `scheduleConfig.startDate` 推导当前周 → 根据今天星期过滤当日课程 → 根据 `weekType` 判断单双周是否命中 → 根据结束时间判断「今日剩余几节课」→ 渲染到首页提醒卡片/横幅。

### 2.6 OCR 导入流程

入口 `pages/schedule-ocr/index`；后端 `POST /api/v1/schedule/ocr`：前端上传 OCR 文本或截图 → 后端按规则解析课程文本 → 对低置信度课程给出提示 → 识别结果可再导入为正式课表。与教务同步链互补（OCR 适合截图导入，教务同步适合直接拉全量）。

### 2.7 社区与私信主流程

**社区内容链**：首页加载帖子流 → 进入帖子详情 → 评论/点赞/收藏/转发 → 数据落到 `forum_post / forum_comment / forum_like / forum_favorite / forum_share`。

**发帖/评论数据流**（来自 FEATURE_DOC.md）：

1. 用户点击发布 → `auth.requireLogin` 检查。
2. 选择图片 → `imageUtil.chooseAndCompress`。
3. 提交 → `wechat.checkContent` 内容安全。
4. `wechat.uploadImages` 上传图片。
5. `POST /post` 创建帖子。
6. 服务端持久化并返回真实记录。

**私信链**：登录成功后 `app.onLogin()` 建立 WebSocket；`messageStore` 同步未读数；聊天页走消息接口 + WebSocket 实时收发。

**聊天页「回到帖子」入口**（`pages/chat/index`）：顶部自定义导航栏提供「回到帖子」胶囊按钮，从聊天直接回到对话发起的原帖子详情页。显示位置为自定义导航栏水平正中（`.back-post-btn` 圆角胶囊），与「返回」同级。

触发条件 `showBackToPost`（解析顺序 `resolveBackToPost`）：

1. 页面栈中仍存在入口携带的原帖子详情页，且 `route` 与 `id` 同时命中 → 目标为该页面实例。
2. 入口未携带 `postId`（如列表卡片直接私信）→ 目标为页面栈中最近的帖子详情页。
3. 携带 `postId` 但原帖子详情页已移出页面栈 → 跳转该帖子详情页。
4. 入口未携带 `postId`，但本地缓存已记录会话来源帖子（如「首页私信入口 → 私信列表 → 聊天」）→ 跳转来源帖子详情页。
5. 页面栈无帖子详情页也无已知来源帖子 → 兜底最近的帖子列表页（首页/搜索/热榜/我的帖子/我的互动）或用户主页，标记「非精确」（`precise = false`）。
6. 仍未命中 → 用服务端记录的会话来源帖子或本地缓存 `pm_src_post_<peerId>[_p_<personaKey>]` 兜底，覆盖第 5 条列表页目标。
7. 以上均无 → 不展示按钮。

> 第 4 条是修复「首页私信入口 → 聊天 → 回到帖子」误回首页的关键：首页是 tabBar 常驻页面永留栈底，来源帖子必须优先于列表页兜底。

**来源帖子持久化**：进入聊天时写入本地缓存 `pm_src_post_<peerId>[_p_<personaKey>]`；`GET /message/history`（`postId` 参数）与 `POST /message/send`（`body.postId`）均上报来源帖子，服务端 `getOrCreateConversation` 仅在 `private_conversation.source_post_id IS NULL` 时写入一次（双方会话都写），之后历史接口返回 `sourcePostId`。来源只在首次写入、不覆盖；从「我的消息」进入匿名会话时可能首屏读缓存落空，需在历史响应拿到真实 `personaKey` 后补读缓存。

**返回逻辑示例**：

| 进入路径                                       | 解析结果           | 点击后                                       |
| ---------------------------------------------- | ------------------ | -------------------------------------------- |
| 帖子详情 → 头像 → 私信 → 聊天                  | 第 1 条，`delta=1` | `navigateBack(1)` 回原帖（保留状态）         |
| 帖子详情 → 个人主页 → 私信 → 聊天              | 第 1 条，`delta=2` | `navigateBack(2)` 回原帖                     |
| 帖子详情 → 个人主页 → 打开另一帖 → 私信        | 第 1 条（新帖 id） | 回到新帖详情                                 |
| 消息通知/列表 → 聊天                           | 第 6 条            | `navigateTo` 跳转缓存来源帖详情页            |
| 首页私信入口 → 私信列表 → 聊天                 | 第 4 条            | `navigateTo` 跳转来源帖详情页（**非首页**）  |
| 帖子列表卡片 → 私信 → 聊天                     | 第 5 条（无来源）  | 回到原列表                                   |

**来源帖子透传链**：帖子详情页经 `profileUrl(userId)` 携带 `postId` 跳个人主页；个人主页 `onLoad` 读 `options.postId` 存 `this.sourcePostId`，「私信」时透传 `&postId=`；`post-card` 头像菜单「私信」直接携带 `this.data.post.id`。用户主页优先级必须低于帖子详情页。

### 2.8 代拿跑腿流程

来自 FEATURE_DOC.md 与 api-contract.md：大厅（`pages/errand/index`）按类型 Tab + 校区切换展示订单列表（`GET /errand/list`）；发布需登录拦截 + 表单校验后 `POST /errand` 提交；接单时确认弹窗后 `POST /errand/:id/accept`；完成走 `POST /errand/:id/finish`。前端用 `normalizeOrder` 统一 Mock/API 字段差异。

### 2.9 维修与支付流程

来自 api-contract.md（四篇源文档中未展开详细步骤，此处依据接口契约描述）：用户创建维修预约 `POST /repair/orders` → 支付 `POST /repair/orders/:id/pay` 获取支付参数 → 微信支付回调 `POST /repair/payment/notify` 由服务端最终确认支付状态（该回调为微信服务器调用，无 JWT 鉴权）。支付结果以服务端回调为准。

## 三、接口契约

> 以 `api-contract.md`（2026-09-10）为准。基础协议：基础 URL `https://<域名>/api/v1`；HTTPS + JSON UTF-8；需认证请求带 `Authorization: Bearer <JWT>`；所有响应统一为 `{ "code": 数字, "message": 字符串, "data": 对象|null, "requestId": 字符串 }`；客户端发 `X-Request-Id` 链路追踪，`X-Idempotency-Key` 支持个人资料与课表配置写入幂等（单进程 10 分钟有效）。`GET` 最多重试两次（针对网络错误、502/503/504，间隔 300ms、600ms），业务写入默认不自动重试；个人资料与课表设置合并到离线队列，回前台重放。

### 4.2 用户认证系统

- 登录：`pages/login` → `wx.login` → `POST /user/phone-login`（以 api-contract 为准，见 3 节冲突标注）→ JWT。
- 持久化：token/userInfo 写入 Storage + globalData。
- 资料管理：`pages/settings` → `PUT /user/info`（昵称/头像/性别/校区/手机）。
- 学号认证：`POST /user/verify`（后端校验学号格式 + 防重复）。
- 登录拦截：发帖、评论、点赞、发布跑腿等调用 `auth.requireLogin`。

### 4.3 校园服务入口

- 首页宫格：`components/service-grid` + mock/API 双数据源。
- 全部服务：`pages/service-all` → `GET /service/list`。
- 路由映射：代拿跑腿/课程表/社区 → `switchTab` 跳转。

### 4.4 社区论坛

- 列表：首页分类筛选 + 下拉刷新 + 上拉分页。
- 搜索：`pages/search` 防抖 400ms + 关键词过滤。
- 发帖：标签选择 + 图片压缩 + 内容安全检查。
- 详情：评论列表 + 点赞 + 本地/API 双写。

### 4.5 课程表

- 网格视图：按星期 × 时间段渲染课程卡片。
- 添加课程：表单校验 → localStorage + `POST /schedule/add`。
- OCR 识别：模拟/接口识别 → 批量导入课表。
- 配置：开始日期、隐藏周末、背景色、提醒开关（持久化 Storage）。
- 教务同步：见 2.3 节（受控登录页 + 真实爬虫同步，新增 `week_type` 字段）。

### 4.6 代拿跑腿

- 发布：表单校验 + 登录拦截 + API 提交。
- 接单：确认弹窗 + `POST /errand/:id/accept`。

### 4.8 视觉与排版

## 遗留问题与后续建议

1. **内容安全待落地**：`middleware/contentSecurity.js` 仅为占位层，需接入真实微信内容安全（`utils/wechat.js` 的 `checkContent` 已在发帖链路调用），补齐评论/转发等入口。
2. **登录时效管理**：`utils/login-expiry.js` 管理 90 天登录时效，需确认与服务端 JWT 过期策略一致，避免前端拦截与服务端校验错位。
3. **课表同步健壮性**：教务系统不稳定时已有异常归一化，但验证码 OCR 连续失败缺乏人工输入兜底路径，建议补充「验证码识别失败 → 用户手动输入」分支。
4. **支付覆盖不全**：当前仅维修模块含支付与微信回调（`/repair/payment/notify`），跑腿订单完成未涉及支付；若跑腿需担保交易，需参照维修支付模式补齐。
5. **订阅消息文档缺位**：四篇源文档未覆盖订阅消息接口与流程，建议将 `docs/` 下订阅消息相关独立文档纳入本架构文档的「接口契约 / 业务流程」章节，避免架构文档与实现脱节。
6. **计数与一致性**：高赞/计数类指标建议复用后台重算与对账服务（如 `counterReconcileService` 思路），避免前端双写不一致。
7. **后续可扩展能力**：成绩查询、考试安排、空教室查询可直接沿用现有模式「小程序页面 → server 路由/控制器 → 爬虫适配服务 → 教务系统」。
8. **数据归属纪律**：坚持「服务端为单一数据源、本地仅缓存/离线队列」原则，个人资料与课表配置走离线队列前台重放，避免多端状态漂移。
