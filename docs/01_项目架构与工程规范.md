## 1、项目架构与核心业务流程

> 来源文档：`项目架构与核心业务流程.md`（415 行）

### 概述

本仓库是一个「微信小程序前端 + Node.js 后端 + MySQL 数据库 + 教务系统爬虫」的校园综合服务项目，承载校园服务导航、课程表同步、社区论坛、代拿跑腿与私信等能力。

技术栈：小程序端为原生微信小程序（WXML/WXSS/JS）；服务端为 Node.js + Express + MySQL（另含 Redis 7，见 FEATURE_DOC.md），鉴权用 JWT（Bearer Token），实时消息用 WebSocket；教务爬虫基于 Node.js + axios + cheerio + tesseract.js。

仓库结构：小程序前端位于仓库根目录（`pages/` `components/` `utils/` `assets/`）；后端服务位于 `server/`；教务系统爬虫位于 `jw-crawler/`。三者单仓维护，非多仓前后端分离模式。

### 一、整体架构

#### 1.1 分层架构图

```text
┌───────────────────────────────────────────────────────┐
│ 小程序端（pages / components / utils）                  │
│  utils/request.js → utils/api.js → 业务页面             │
└───────────────────────────┬───────────────────────────┘
                            │ HTTPS + Authorization: Bearer <JWT>
                            ▼
┌───────────────────────────────────────────────────────┐
│ Node.js + Express 服务端（server/）                     │
│  middleware/* → routes/* → controllers/*                │
│  services/*（如 jwScheduleSyncService）                 │
│  WebSocket 服务（wss://<域名>/ws?token=<JWT>）          │
└──────────┬─────────────────────────────┬───────────────┘
           │                              │
           ▼                              ▼
      MySQL 8.0 (+Redis 7)          微信（登录 / 内容安全 / 支付）
           ▲
           │ 服务端内部调用
┌──────────┴────────────────────────────────────────────┐
│ jw-crawler/ 教务系统爬虫（登录 / OCR / 抓取 / 解析）     │
└───────────────────────────────────────────────────────┘
```

数据归属（以 api-contract.md 为准）：服务端是用户、帖子、评论、对话、课程、跑腿与维修订单的**单一数据源**；本地存储仅缓存读取模型或排队可合并的设置（如个人资料、课表配置），支付完全由服务端微信回调最终确认。

#### 1.2 目录职责

- **仓库根目录（小程序前端）**
  - `app.js` / `app.json` / `app.wxss`：小程序全局入口与全局配置（TabBar 四个页面在 `app.json` 的 `pages` 注册）。
  - `pages/`：业务页面，按主导航、课表、社区、用户设置等分组。
  - `components/`：通用组件（`service-grid`、`post-card`、`errand-card`、`load-more`、`empty-state` 等）。
  - `utils/`：公共工具层（请求封装、API、鉴权、课表标准化、WebSocket 等）。
  - `assets/`：图标、TabBar、横幅等静态资源。
- **`server/`（Node.js 后端）**
  - `app.js`：服务入口。
  - `routes/*.js`：路由层；`controllers/*.js`：控制器层；`services/*.js`：业务聚合（如 `jwScheduleSyncService`）。
  - `middleware/*.js`：鉴权、限流、日志、异常处理、内容安全。
  - `utils/migrations.js`：数据库迁移；`sql/init.sql`：初始化脚本。
  - `.env`（复制自 `.env.example`）：DB、Redis、JWT、微信 AppID 等环境变量。
- **`jw-crawler/`**
  - 教务系统登录、验证码 OCR、课表 HTML 抓取与结构化解析；**不直接运行在小程序内**，由后端 `server/services/jwScheduleSyncService.js` 调用。

#### 1.3 技术栈与依赖

| 层          | 技术栈 / 依赖                                                        |
| ----------- | ------------------------------------------------------------------- |

### 二、核心业务流程

> 以下流程中，接口路径以 `api-contract.md` 为准，交互细节以 `核心业务流程说明.md`（2026-09-11）为准。

#### 2.1 用户身份链路

**微信登录**（前端 `pages/login/index` + `utils/auth.js`；后端 `POST /api/v1/user/phone-login` → `userController.phoneLogin`）：

1. 小程序获取微信登录 `code`。
2. 小程序获取手机号授权 `phoneCode`。
3. 后端调用微信接口换取 `openid` 与手机号。
4. 后端按手机号优先匹配 `sys_user`。
5. 后端签发 JWT。
6. 前端保存 `token` 与 `userInfo`。

身份结果：小程序内业务鉴权依赖 JWT；`req.userId` 成为后端所有业务数据隔离依据。

**身份与课表同步的衔接**：课表同步接口必须先经 JWT 认证——未登录由前端直接拦截；已登录未认证学号允许输入教务账号同步；已认证学号仅允许同步与当前认证学号一致的教务账号，避免写入他人课表。

#### 2.2 课程表读取链路

入口：`pages/schedule/index`、`pages/index/index`、`utils/api.getScheduleList`；后端 `GET /api/v1/schedule/list`。

1. 前端请求后端课表列表。
2. 后端读取 `user_schedule`。
3. 前端用 `utils/schedule.normalizeCourse()` 标准化课程字段。
4. 按 `startWeek / endWeek / weekType` 过滤当前周课程。
5. 课表页渲染周视图。
6. 首页按「当前周 + 今天星期 + 单双周」提取今日课程提醒。

**当前周过滤规则**：当前周须满足 `startWeek <= currentWeek <= endWeek`；`weekType = all` 直接展示，`odd` 仅奇数周展示，`even` 仅偶数周展示。

#### 2.3 教务系统课表同步主流程

**用户触发**（`pages/schedule/index`）：打开课程表左侧抽屉 → 点击「同步我的课表」→ 前端检查是否已登录 → 已登录则跳转 `pages/schedule-login/index`。

**教务登录页**（`pages/schedule-login/index`）：若用户资料已有 `studentId` 自动回填账号；输入密码点「同步课表」→ 前端调用 `api.syncSchedule(username, password)`，请求层使用更长超时避免被 15 秒超时截断。

**后端同步接口**（`POST /api/v1/schedule/sync`）：

1. 校验 JWT。
2. 校验账号密码非空、账号格式合法。
3. 若用户已认证学号，则校验输入账号必须一致。
4. 读取用户 `schedule_config.start_date`。
5. 调用 `jwScheduleSyncService.syncScheduleFromJw()`。

**爬虫适配服务**（`server/services/jwScheduleSyncService.js`）：

1. 创建 `JwCrawler` 实例。
2. 注入 OCR 语言包路径与超时、限流参数。
3. 按登录模式登录教务系统。
4. OCR 自动识别验证码。
5. 逐周抓取课表 HTML。
6. 解析为课程数组。
7. 将多周课程聚合成「课程 + 周范围 + 单双周」标准结构。

聚合结果字段：`name`、`location`、`teacher`、`weekDay`、`startTime`、`endTime`、`startWeek`、`endWeek`、`weekType`、`color`。

**数据入库**（`user_schedule`，本次新增字段 `week_type` 用于表达单双周）：开启事务 → 删除该用户旧课表 → 插入新课表 → 提交事务 → 返回课程数组与学期开始日期。

**前端同步收口**：将课程数组写入本地 `schedule_courses`；将 `startDate` 写入 `scheduleConfig`；返回上一页；课表页 `onShow` 重新计算当前周并重新拉取列表。最终本地缓存、后端数据库、页面展示三者均刷新。

#### 2.4 同步异常处理

| 场景                       | 处理                                                   |
| -------------------------- | ------------------------------------------------------ |
| 学号/密码为空（前端）      | `wx.showToast`                                         |
| 未登录 / 学号不匹配        | 后端返回 `401/403`，前端弹框提示                       |
| 教务账号/密码错误          | 归一化为「教务系统登录失败，请检查账号或密码」         |
| 网络异常（连接重置/DNS）   | 归一化为「网络异常，暂时无法连接教务系统」             |
| 爬虫请求超时               | 归一化为「爬虫请求超时，请稍后重试」                   |
| 验证码识别失败             | 归一化为「验证码识别失败，请稍后重试」                 |
| 课表数据解析失败           | 归一化为「课表数据解析失败，请稍后重试」               |
| 频繁/重复触发同步          | 同步中再次触发直接拒绝；短时间重复返回限频提示         |

#### 2.5 首页课表提醒流程

入口 `pages/index/index`：读取课程表列表 → 根据 `scheduleConfig.startDate` 推导当前周 → 根据今天星期过滤当日课程 → 根据 `weekType` 判断单双周是否命中 → 根据结束时间判断「今日剩余几节课」→ 渲染到首页提醒卡片/横幅。

#### 2.6 OCR 导入流程

入口 `pages/schedule-ocr/index`；后端 `POST /api/v1/schedule/ocr`：前端上传 OCR 文本或截图 → 后端按规则解析课程文本 → 对低置信度课程给出提示 → 识别结果可再导入为正式课表。与教务同步链互补（OCR 适合截图导入，教务同步适合直接拉全量）。

#### 2.7 社区与私信主流程

**社区内容链**：首页加载帖子流 → 进入帖子详情 → 评论/点赞/收藏/转发 → 数据落到 `forum_post / forum_comment / forum_like / forum_favorite / forum_share`。

**发帖/评论数据流**（来自 FEATURE_DOC.md）：

1. 用户点击发布 → `auth.requireLogin` 检查。
2. 选择图片 → `imageUtil.chooseAndCompress`。
3. 提交 → `wechat.checkContent` 内容安全。
4. `wechat.uploadImages` 上传图片。
5. `POST /post` 创建帖子。
6. 服务端持久化并返回真实记录。

**私信链**：登录成功后 `app.onLogin()` 建立 WebSocket；`messageStore` 同步未读数；聊天页走消息接口 + WebSocket 实时收发。

**聊天页「回到帖子」入口**（`pages/chat/index`）：顶部自定义导航栏提供「回到帖子」胶囊按钮，从聊天直接回到对话发起的原帖子详情页。显示位置为自定义导航栏水平正中（`.back-post-btn` 圆角胶囊），与「返回」同级。

触发条件 `showBackToPost`（解析顺序 `resolveBackToPost`）：

1. 页面栈中仍存在入口携带的原帖子详情页，且 `route` 与 `id` 同时命中 → 目标为该页面实例。
2. 入口未携带 `postId`（如列表卡片直接私信）→ 目标为页面栈中最近的帖子详情页。
3. 携带 `postId` 但原帖子详情页已移出页面栈 → 跳转该帖子详情页。
4. 入口未携带 `postId`，但本地缓存已记录会话来源帖子（如「首页私信入口 → 私信列表 → 聊天」）→ 跳转来源帖子详情页。
5. 页面栈无帖子详情页也无已知来源帖子 → 兜底最近的帖子列表页（首页/搜索/热榜/我的帖子/我的互动）或用户主页，标记「非精确」（`precise = false`）。
6. 仍未命中 → 用服务端记录的会话来源帖子或本地缓存 `pm_src_post_<peerId>[_p_<personaKey>]` 兜底，覆盖第 5 条列表页目标。
7. 以上均无 → 不展示按钮。

> 第 4 条是修复「首页私信入口 → 聊天 → 回到帖子」误回首页的关键：首页是 tabBar 常驻页面永留栈底，来源帖子必须优先于列表页兜底。

**来源帖子持久化**：进入聊天时写入本地缓存 `pm_src_post_<peerId>[_p_<personaKey>]`；`GET /message/history`（`postId` 参数）与 `POST /message/send`（`body.postId`）均上报来源帖子，服务端 `getOrCreateConversation` 仅在 `private_conversation.source_post_id IS NULL` 时写入一次（双方会话都写），之后历史接口返回 `sourcePostId`。来源只在首次写入、不覆盖；从「我的消息」进入匿名会话时可能首屏读缓存落空，需在历史响应拿到真实 `personaKey` 后补读缓存。

**返回逻辑示例**：

| 进入路径                                       | 解析结果           | 点击后                                       |
| ---------------------------------------------- | ------------------ | -------------------------------------------- |
| 帖子详情 → 头像 → 私信 → 聊天                  | 第 1 条，`delta=1` | `navigateBack(1)` 回原帖（保留状态）         |
| 帖子详情 → 个人主页 → 私信 → 聊天              | 第 1 条，`delta=2` | `navigateBack(2)` 回原帖                     |
| 帖子详情 → 个人主页 → 打开另一帖 → 私信        | 第 1 条（新帖 id） | 回到新帖详情                                 |
| 消息通知/列表 → 聊天                           | 第 6 条            | `navigateTo` 跳转缓存来源帖详情页            |
| 首页私信入口 → 私信列表 → 聊天                 | 第 4 条            | `navigateTo` 跳转来源帖详情页（**非首页**）  |
| 帖子列表卡片 → 私信 → 聊天                     | 第 5 条（无来源）  | 回到原列表                                   |

**来源帖子透传链**：帖子详情页经 `profileUrl(userId)` 携带 `postId` 跳个人主页；个人主页 `onLoad` 读 `options.postId` 存 `this.sourcePostId`，「私信」时透传 `&postId=`；`post-card` 头像菜单「私信」直接携带 `this.data.post.id`。用户主页优先级必须低于帖子详情页。

#### 2.8 代拿跑腿流程

来自 FEATURE_DOC.md 与 api-contract.md：大厅（`pages/errand/index`）按类型 Tab + 校区切换展示订单列表（`GET /errand/list`）；发布需登录拦截 + 表单校验后 `POST /errand` 提交；接单时确认弹窗后 `POST /errand/:id/accept`；完成走 `POST /errand/:id/finish`。前端用 `normalizeOrder` 统一 Mock/API 字段差异。

#### 2.9 维修与支付流程

来自 api-contract.md（四篇源文档中未展开详细步骤，此处依据接口契约描述）：用户创建维修预约 `POST /repair/orders` → 支付 `POST /repair/orders/:id/pay` 获取支付参数 → 微信支付回调 `POST /repair/payment/notify` 由服务端最终确认支付状态（该回调为微信服务器调用，无 JWT 鉴权）。支付结果以服务端回调为准。

### 遗留问题与后续建议

1. **内容安全待落地**：`middleware/contentSecurity.js` 仅为占位层，需接入真实微信内容安全（`utils/wechat.js` 的 `checkContent` 已在发帖链路调用），补齐评论/转发等入口。
2. **登录时效管理**：`utils/login-expiry.js` 管理 90 天登录时效，需确认与服务端 JWT 过期策略一致，避免前端拦截与服务端校验错位。
3. **课表同步健壮性**：教务系统不稳定时已有异常归一化，但验证码 OCR 连续失败缺乏人工输入兜底路径，建议补充「验证码识别失败 → 用户手动输入」分支。
4. **支付覆盖不全**：当前仅维修模块含支付与微信回调（`/repair/payment/notify`），跑腿订单完成未涉及支付；若跑腿需担保交易，需参照维修支付模式补齐。
5. **订阅消息文档缺位**：四篇源文档未覆盖订阅消息接口与流程，建议将 `docs/` 下订阅消息相关独立文档纳入本架构文档的「接口契约 / 业务流程」章节，避免架构文档与实现脱节。
6. **计数与一致性**：高赞/计数类指标建议复用后台重算与对账服务（如 `counterReconcileService` 思路），避免前端双写不一致。
7. **后续可扩展能力**：成绩查询、考试安排、空教室查询可直接沿用现有模式「小程序页面 → server 路由/控制器 → 爬虫适配服务 → 教务系统」。
8. **数据归属纪律**：坚持「服务端为单一数据源、本地仅缓存/离线队列」原则，个人资料与课表配置走离线队列前台重放，避免多端状态漂移。

### 一、布局铁律（踩过两次）

- **`position:fixed` 元素不要放进 `.page page-enter`**：`.page-enter` 若带 `animation-fill-mode:both`，动画结束后 `.page` 会永久保留 `transform` → 成为后代 fixed 元素的包含块，再被 `overflow:hidden` 裁剪，元素飘出/错位且刷新不复位。导航栏、浮动按钮、全屏弹层一律写在 `.page` 外层或用 `root-portal`。
- **fixed 导航 + 内部 scroll-view**：`.page` 锁 `100vh`，`.scroll-view` 用 `calc(100vh - var(--nav-h,0px))`，`--nav-h` 由 wxml 内联 `statusBarHeight + navBarHeight` 传入；否则整页可被拖动、导航被顶走且不复位。
- **`<text>` 是 inline**：`height` / 垂直 `padding` / `overflow` 都不生效。胶囊标签必须用 `<view>`。同一视觉元素在不同页面一处用 `<view>` 一处用 `<text>`，是「样式怎么调都对不齐」的常见根因。护栏：`author-label-style.test.js`。

### 二、前端陷阱

- **解构不存在的导出不报错，用时才 `undefined.foo()` 崩**。模块改名/拆导出后必须全仓 grep 旧名。护栏 `tests/local-imports.test.js`。写这类校验**别正则解析 `module.exports`**（实测 429 处误报），应设 `wx`/`Page`/`Component` 桩后 require 取 `Object.keys`，加载失败的跳过。
- **本地「已读 id」集合别做 `slice(-N)` 截断**：会丢掉最旧的永久记录 → 冷启动角标复活（跑腿「已完成」踩过）。单 key 上限 1MB≈10 万条，不截断即可。`wx.setStorageSync` 必须 try/catch，失败只 `console.warn`（内存已更新，保证本会话正确）。
- **跳转后「目标不存在」要预先拦截**：404 只 `setData({loading:false})` 会停在中间态、入口仍可点 → 白屏连锁。要区分 404（已删除/不存在）与其他失败，禁用入口并说明。
- **tab 索引变化必须全仓 grep `?tab=`**：插入一项会整体后移，硬编码索引会静默跳错 tab；wxml 里 `wx:if="{{activeTab===N}}"`、`tabUnread` 长度一并改。
- **静态断言别用易变文案做锚点**：曾按 `aria-label="私信"` 切 WXML 片段，文案改成「消息通知」后测试长期假红、掩盖真实回归 → 改用 `bindtap` 处理器等稳定标识。同理不要把「枚举里必须含 X」写成「X 必须是最后一个元素」。
- **vm 沙箱测试的隐形陷阱**：从沙箱里取出的对象/数组**原型与外层不同**，`assert.deepStrictEqual(外层数组, 沙箱数组)` 会因原型不一致失败，而打印出来的内容**一模一样**，极难排查。这类断言**一律先 `plain()`（JSON 往返）转成本层值**再比较。
- **控制台红错先 grep 域名**：`sdkReport 503`（wxg.waym.com）是工具自身遥测；`text 长文本 user-select` 给正文 text 加 `user-select` 即消；`routeDone webviewId not found` 是短时重复路由 → `app.js installRouteGuards()` 给四类跳转加进行中锁（tabBar 点已选 tab 直接 return），**锁必须在透传原 fail 前释放**，否则回退链被吞。
- **同一份数据在多端显示不同的日期/周次 → 先查「起始锚点」与「派生值同步」，别先怀疑时区**。课表踩过两条独立根因：① 学期起始日存在**周日锚点**写法（校历图注写「教学周 9 月 6 日起」，用户在「设置开始日期」里照抄成 `2026-09-06`），与周一锚点 `2026-09-07` 只差 1 天，但 `floor(天数差/7)+1` 在**周日**这个边界上会差整整一周 → 同一份课表在两台设备上「本周」差一周；修法是 `parseSemesterStart()` 把周日值锚定到次日周一，并让**所有**推算周次/周日期的地方都走它（别直接用只做解析的 `parseLocalDate`）。② `switchWeek()` 只改 `currentWeek`、不重算 `currentWeekText` → 点「下一周」或「本周无课自动跳到有课周」后，标题与表头进了新周、卡片日期还停在上周；**由 A 派生的展示值，改 A 处必须同批改它**，或收敛成单点派生（`weekDateText(week)`）。排查时的另一条硬线索是**残留的旧学期默认值**：`pages/index/index.js` 一直留着上一学期的 `2026-03-02`，未配置起始日的用户首页被算成「第 29 周」、当天课程全筛不出来（课表页却正常）。护栏 `tests/school-term-consistency.test.js`（纯函数 + vm 页面行为 + 源码护栏，两条根因各做过反向验证）。
- **抽视频帧的工具链**：本机无 ffmpeg，用 managed python 的 `cv2`。**OpenCV 在非 ASCII 路径下 `imwrite` 会静默失败**（返回 False、目录为空）→ 必须 `cv2.imencode('.jpg', frame, ...)` 再 `open(path,'wb').write(buf.tobytes())`。

### 三、订阅消息（本项目最复杂的一环，单独成节）

#### 3.1 入口显隐与点击

- **入口显隐别自己造条件**：统一用 `utils/subscribe.js` 的 `entryVisible(trigger)`（= `shouldShowDialog` 的取反，语义「偏好已开 且 微信侧已授权」才静默）；点击统一走 `requestEntryByTap(trigger)`。
- **`requestTriggerByTap` 只写 `grantedXxx`，不写偏好键**。所以引导型入口若要「授权成功后隐藏」，`requestEntryByTap` 会在 accepted 时**只对允许的项**写偏好（评论两键写 `subscribe_comment_prefs`，其余写 `notify_channel_prefs`，与设置页同键）。
- **拒绝时不要写偏好**，否则设置页开关会被误显示成已开启。
- **行式入口的 `bindtap` 与 `<switch>` 必须是兄弟节点**——给整行加 bindtap 时 switch 的 tap 会冒泡，一次点击触发两个处理器、重复申请授权。（switch 与 tap 可复用同一处理器，开头判 `e.detail.value === false` 直接 return。）
- 样式 `.sub-notice-*` 统一在 `app.wxss`，多页共用。触发点→渠道名/节流键的表叫 `TRIGGER_CHANNEL`，**不要往 `TRIGGER_GROUPS` 里加字段**（`settings-notify-channels.test.js` 逐字解析那七条）。

#### 3.2 授权键推导

- **授权键只能由统一映射产出，绝不能手写推导**：授权键 = `granted` + 首字母大写（`grantedKeyOf`），且**必须写回该触发组自己的 `prefsKey`**。
- 历史事故：设置页早期手写 `'granted'+Cap(key)` 并统一塞进 `channelPrefs` → commentNew 写成 `grantedCommentNew` 且落到 `notify_channel_prefs`，而触发组读的是 `grantedNewComment` + `subscribe_comment_prefs`，**双重错位** → 症状是「设置页授权了、业务页入口不消失」。
- 正确做法：一律调 `subscribe.persistAccepted(accepted, types)`。
- **整表重建本地偏好存储会抹掉本页不负责的字段**（`persistChannelPrefs` 曾用 `others` 重建，把各 `grantedXxx` 抹掉导致入口集体复活）→ 一律增量合并。
- 授权键改名必须保留旧键兼容读取，否则老用户被要求重新授权。
- 护栏：`tests/subscribe-binding-audit.test.js`（A 模板 ID 三方一致 / B 授权键推导不变式 / C 全渠道授权闭环 / D 每个模板都要有服务端发送点 / G 前端 `TPL_LABELS` ↔ 服务端 `TPL_CONFIG.label` 一字不差）。

#### 3.3 模板 ID 与配置

- **模板 ID 有三处副本必须同改**：前端 `utils/subscribe.js` 的 `TEMPLATE_IDS`、服务端 `server/.env` 的 `WX_TPL_*`、`server/.env.example`。
- `.env.example` 曾长期停留在废弃的三槽位（`WX_TPL_ACTIVITY/ERRAND/INTERACT`）且缺全部 20 个具名键 → 新环境照此部署后 `templateIdOf()` 全空、`push()` 全返回 `template_not_configured`、**订阅消息一条都不发**（只留站内信，静默）。
- **长期订阅消息对本项目不可用**：微信只对政务民生/医疗/交通/金融/教育等**部分二级行业类目**开放，且「仅支持少量民生公共服务节点通知」，模板库里必须有模板才能调用。官方社区已明确回复「**在线教育类目暂不支持开通长期订阅模板**」。校园论坛的私信提醒属于 UGC 社交互动，两条都不满足 → 不要在这条路上投入时间。要在「小程序已关闭」时仍能触达，唯一可控的替代是**公众号（服务号）模板消息**（需绑定开放平台用 unionid 打通、用户已关注该服务号、企业主体认证），详见 `docs/方案对比_2026-09-15_匿名互动触达通道.md`。

#### 3.4 发送层

- **`push()` 的重试必须区分可重试与不可重试**：
  - 可重试：网络超时/连接重置/HTTP 5xx、微信 `-1`(系统繁忙) / `45009`(接口超限) / `43004`。
  - **绝不重试**：`43101`(用户拒收，应先清零额度) 与 `47003`(模板字段不符——重试不会自愈，只会掩盖配置 bug)。
- **微信对 data 里的空值字段直接返回 47003**，所以「业务上可能为空」的字段一律用 `clipOr(value,max,fallback)` 兜底，宁可显示占位也不能整条发不出去。
- `commentReply` 的 `thing20` 曾因帖子标题选填而长期为空 → 历史 11 次发送 **100% 失败、0 次成功**，且没有任何报错，直到查额度时才被发现。现已加 `findEmptyFields()` 预检 + pm2 warn。
- **合并窗口/额度不足原先都是直接丢内容**，已改为落 `subscribe_pending_message` 待发补发（每个 `(user_id,tpl_type)` 一个槽位，只留最近一条 → 窗口内 N 条最终补发 1 条）。多实例抢占靠「先把自己的 `next_retry_at` 推后 + 判 `affectedRows`」。`push()` 的 `fromPending` 选项用于让补发路径不再二次落待发（防套娃）。配套 `services/subscribeRetryService.js`（每分钟扫）。
- **新增 service 必须同步加进 `deploy.py` 与 `deploy_full.py` 的显式清单**，否则 `app.js` require 失败、线上反复重启。
- **别用中文关键词匹配来路由模板**：`errandController.pushErrandSubscribe` 曾靠 `indexOf('已被接单'/'完成'/'评价')` 匹配，都不命中时兜底成「订单取消通知」→「发单人提出异议」「收到取消接单申请」「取消申请被拒绝」这三个**订单并未取消**的场景全被误发成「订单已取消」。现改为显式 `event`（`accepted`/`finished`/`cancelled`/**`none`**，none = 无合适模板只发站内信），关键词仅作兜底。
- **合并窗口当前是关闭的**：`server/.env` 的 `SUBSCRIBE_MERGE_WINDOW_MS=0`（0 或不设 = 不合并）。改 `300000` 即恢复 `commentNew`/`commentReply`/`message` 三个高频模板 5 分钟合并，**无需改代码**。
- **`access_token` 必须走 `cgi-bin/stable_token`，绝不能回到 `cgi-bin/token`**（2026-09-16 修复）：后者**每调用一次就作废上一次签发的 token**，而本项目是 pm2 cluster 2 实例、`cachedToken` 是**进程内变量**（每实例一份）→ 实例 A 刷新后实例 B 手里的 token 立刻失效 → B 发消息被拒 `40001 invalid credential, access_token is invalid or not latest`，表现为**同一批消息有的成功有的失败**。`stable_token` 在 `force_refresh=false` 时有效期内返回同一个 token，多实例互不作废。`forceRefresh: true` 会透传 `force_refresh=true`（真的签发新 token，仍会作废其它实例的），**只允许在 40001/42001 自愈路径上用**。
- **`40001`/`42001`/`40014` 属于可自愈错误，必须「换新 token 重发」而不是记 failed**：坏的是凭据不是消息。`RETRYABLE_WECHAT_CODES` 必须包含它们，且命中 `TOKEN_ERROR_CODES` 时下一轮要用 `getAccessToken({ forceRefresh: true })`。历史上这些码不在列表里 → token 一被顶掉就永久失败。护栏：`tests/wechat-token-stable.test.js` F/G 组。
- **`server/scripts/verify-wechat-config.js` 也是地雷**：它原来走 `cgi-bin/token`，**跑一次体检就会把线上正在用的 token 弄失效**。已一并改为 `stable_token`。任何新增的「探活/体检」脚本都要遵守这条。

#### 3.5 匿名私信的订阅推送（2026-09-15 已改造）

- `server/controllers/messageController.js` 的 `createPrivateMessage()` 里，`channelAnonymous = conversation.isAnonymous || conversation.peerIsAnonymous`，只要会话**任一侧**是匿名，整条会话所有消息都走匿名渠道。
- **改造前**：该值为真时**整个推送 `if` 块被跳过**，`pushMessage()` 根本不调用 → **`subscribe_message_log` 里连一行记录都不会留**（既没有 `sent` 也没有 `skipped`）。这是与「额度不足」的关键区分判据。该行为由 commit `a863751b`（2026-09-11）引入。
- **改造后**：**无条件推送**，昵称经 `resolveSenderNick(conversation, senderId)` 解析：
  - `conversation.isAnonymous === true`（发送方那一侧匿名）→ 用分身昵称（会话存档的 `anon_self_identity`，与聊天页同一份数据），**刻意不查 `sys_user.nick_name`**，缺失时兜底「匿名用户」。
  - `isAnonymous === false` → 查真实昵称，兜底「有同学」。
  - **判定必须用 `isAnonymous` 而不是 `channelAnonymous`**：后者是会话级，普通用户回复匿名发起人时它也为真，但聊天页显示的是该普通用户的真名，推送文案必须一致。
- **不再泄露身份**：`pushMessage` 的 `thing1`（发送人）与 `summary` 都取自解析结果；匿名分支连查询语句都不会发出（护栏用 SQL 层面断言锁死）。
- 配套事实：`wsServer.sendToUser()` 位于推送逻辑**之前**，匿名路径一直有实时通道，只是不弹微信提醒 —— 排查时别误判成「匿名完全没触达」。
- 幂等约束：会话一旦由匿名方建立，**双方后续消息都走匿名渠道**（普通用户回复也进这条分支）。
- 护栏：`server/tests/anonymous-message-subscribe.test.js`（9 条）。

#### 3.5.1 冷启动未读提示（A3）

- `app.js` 的 `noticeColdStartUnread(total)`：冷启动拿到未读总数后延时 1.5s 提示一次，用户已在消息页则不打扰，`_coldStartUnreadNoticed` 保证一次冷启动只提示一次。
- 定位：小程序被关闭期间，WebSocket（A1）与角标（A2）都触达不到，冷启动是唯一能补上告知的时机。**它不能替代推送**，只是把「关闭期间的空白」压缩成「下次打开必被看到」。

#### 3.6 入口显隐与额度

- **只看本地 granted 会漏掉「额度耗尽」**：一律用 `entryVisibleAsync(trigger)`（本地需引导 → 直接 true 不发请求；本地认为已订阅 → 查一次服务端额度）。搭配 `notifyQuotaExhausted()`（24h 节流，写在待发槽位的 `notice_sent_at`）形成闭环。
- 管理后台「日志 → 订阅消息」分段可查发送流水、额度概览与待补发条数，客服不必连库。

#### 3.7 `wx.requestSubscribeMessage` 的两条硬约束

1. 必须在**用户点击手势的同步调用栈**内调用（`onLoad` / `setTimeout` / `await` 之后都不行，会 `fail: can only be invoked by user TAP gesture`）。
2. **不能在原生弹窗返回后（success 回调里）再自动弹一次**。

所以「用户漏勾一项 → 自动补弹那项」**实现不了**，只能做「**下一次点击时弹窗里只申请缺的那几项**」（`pendingTypesFor(trigger)`：偏好没开或微信侧未授权才算缺；**全组已授权时回退为整组**，因为那时入口重现只可能是额度耗尽、需要重新攒额度）。配合点名式提示即可闭环。

补充机制：**微信原生弹窗里每个模板默认都是未勾选**，用户很容易只勾一项就点「允许」，所以文案要写「再点一次**逐项勾上**」。

#### 3.8 「开关开启后自动关闭」的成因

= 受控 switch + 复位 + 节流三件事叠加：

1. `refreshXxxSubscribeEntry()` 无条件把 `checked` 置 false，请求一返回就把开关「拽回去」（用 switch 承载「一次性授权申请」这个动作本身就别扭，受控 switch 必然回弹）。
2. `requestEntryByTap` 曾把 `throttleKey` 传给 `guideReopen`，**用户主动点击也被 7 天节流吞掉** → 点了、弹回、零反馈。

修法：主动点击**不节流**（节流只留给被动触达，如 chat onSend），且每条失败/被拒/接口失败的出口都必须给可见反馈（引导弹窗或 toast），不能静默。这类问题要在**客户端**看 vConsole 与 storage（`grantedXxx`、节流键），服务端 `subscribe_message_log` 此时不会有记录。

#### 3.9 失败提示文案

- **必须回答「哪里出错 + 接下来做什么」**：只描述现象的提示（如「部分未开启，可再次点击补齐」）等于没说，用户会当成 bug。
- **能点名就必须点名**——前端只有英文模板键，就补一份与后端同源的中文名表（`utils/subscribe.js` 的 `TPL_LABELS` ↔ 服务端 `TPL_CONFIG.label`，有护栏逐项比对），否则提示只能说「部分」二字。
- **`requestSubscribe` 有条隐形静默出口**：`validIds()` 为空（模板 ID 未配置/仍是「请填入」占位符）时直接 resolve —— 不弹窗、不报错、无日志，是「点了没反应」的隐形来源。现已加 `console.warn` + toast + 返回值 `failed` 标记。

### 四、排查订阅问题的标准动作

**判断「订阅消息到底有没有发出去」只看 `subscribe_message_log`：**

```sql
SELECT status, tpl_type, errcode, errmsg, created_at
  FROM subscribe_message_log
 WHERE user_id = ?
 ORDER BY id DESC LIMIT 20;
```

| status | 含义 | 处置 |
|---|---|---|
| `sent` | 我方已交给微信 | 之后到达时间**只由微信决定**，服务端无任何手段可观测 |
| `skipped` | 额度不足，没发 | 瓶颈在授权覆盖率（每次「允许」只 +1 条额度） |
| `merged` | 被合并窗口压掉 | 已转待发补发，不丢内容 |
| `failed` | 带 errcode | `43101` 拒收 / `47003` 字段不符 / `40003` openid / `45009` 限流 / **`40001`·`42001` 凭据失效（现已自愈，不再落 failed）** |
| `throttled` | **客户端本地弹窗节流命中**：该触发组当天已弹满 3 次，连微信都没调用 | 不是故障。这是**唯一由客户端上报**的状态（节流判定在 tap 同步链内，服务端无法感知）；次日自动恢复 |
| **无记录** | **代码路径根本没走到推送**（如匿名渠道） | 去业务代码找 `if` 跳过分支 |

- `failed` 为 0 就说明链路技术上是通的。
- **用户抱怨「延迟/收不到」时，先分清「没发出去」和「发出后由微信投递」**——绝大多数是前者，不是延迟。
- **看额度看板别看错口径**（管理后台「日志 → 订阅消息」顶部）：额度按 `(user_id, tpl_type)` **逐人独立**存。
  看板里的「剩余」是**全体用户总量**、「N 人有额度」才是真正还能收的人数。
  所以会出现「总量还剩 30 条，但某几个用户连续 `skipped`」——那是**那几个人自己用光了**，不是系统故障。
  （2026-09-16 前文案写作「N 人可用」且取的是「有记录人数」（含已用光的人），极易误判成矛盾，已修正。）
- **自证我方无延迟的方法**：把 `subscribe_message_log.created_at` 与业务表（`private_message` / `forum_comment`）的 `created_at` 对比，**同秒即证明发送是即时的**（写日志发生在 `axios.post` 成功之后，所以同秒 ⇒ 整条链路 <1s）。本地测不出来，必须查生产。

### 五、服务端

- **JSON 列不能直接当 SQL 参数**：mysql2 把 JSON 列解析成数组 → 一个 `?` 被展开成 N 个值 → `ER_WRONG_VALUE_COUNT`。静态读代码看不出（列值数配平）。回写一律过 `helpers.js toJsonColumn()`。已知 JSON 列：`group_chat.images`、`group_chat_apply.images`、`club_apply.images`、`forum_post.images/contact/anonymous_identity/components`、`forum_comment.images/anonymous_identity`、`club_category.scope/features`、`errand_order.images`、`virtual_item_log.before_data/after_data`。
- **给 SELECT 加 `?` 必须同步补参数**：不报错只错位（WHERE 的值被当 isFollowed、pageSize 被当 OFFSET）→ 特定输入下 500 或查错数据。改完数一遍 `?`。护栏 `tests/post-query-param-count.test.js`（对每个读接口断言「`?` 个数 === 参数个数」，通杀整类问题）。
- **被多个分支共用的 SQL 片段（`baseSelect` 这类常量字符串）是补参数的高危点**：只改一处、漏补另一处分支，就是静默错位。本项目 `followedList` 的 `baseSelect` 被 `mine` / `theirs` 两个分支共用，加 `isLiked` 子查询后两个分支都要各补 1 个 userId（mine 变 4 个参数、theirs 变 5 个）。改完必须 grep 该常量的**所有**使用点，逐个确认参数个数，再跑 `post-query-param-count.test.js`。
- **「映射里有这个字段」≠「这个字段能正常工作」**：字段可能从来没人往 SQL 里查。本项目「我蹲的帖子」列表的映射一直写着 `isLiked: !!r.isLiked`，但 SQL 从未产出该列 → 恒为 false。排查这类「恒为 0 / 恒为 false」时，要**顺着 SQL 往回追**，别只看映射层是否写了。
- **新增通知类型必须同步扩 ENUM**：`system_notification.type` 不含新值 → `ER_DATA_TRUNCATED`，而 `createNotification().catch(()=>{})` 会静默吞掉 → 症状是「消息不显示」。四处同改：`migrations.js`（建表 + `MODIFY COLUMN`）、`sql/init.sql`、`notificationController.list` 的 `n.type IN (...)`、`notificationService` 白名单/文案。
- **「管理端看得见、用户端看不见」→ 先查两条代码路径**：公开接口走 `mapXxx(row, 关联数据)`，形参传了没写进返回值＝静默丢字段，下游 `|| []` 又把「缺失」伪装成「0」。测试直接断言接口响应字段。同类案例：`utils/club-data.js mapServerCategory()` 漏抄 `id`。
- **DATETIME 会被序列化成 UTC ISO 串**（显示差 8 小时）：出口统一过 `toDateTimeText()`；页面 `fmtDateTime` 对 `T` 开头先 `new Date()` 换算本地时区。activityController 等仍是老行为，待统一。
- **内置素材路径必须白名单校验**：`startsWith('/assets/avatar1/')` 会放过「考拉 (2).jpg」（空格+半角括号，真机解析失败）→ 头像图裂 + 控制台刷「Failed to load image」。素材池三处同源：包内 `assets/avatar1/`、`utils/avatar.js`、`utils/defaultProfile.js`，测试读目录做一一对应断言（含「文件名不得含空格/半角括号」）。`normalizeLegacyAvatarUrl` 是全站头像主出口，新增渲染出口要一起过它。
- **匿名身份纠正失败绝不能返回 `null`**（会降级成真名真头像，暴露匿名者），必须用昵称做种子稳定映射池内素材。
- **分页取总数：多结果解构里的 `count` 是「结果集」不是首行**：`const [[count], [list]] = await Promise.all([...])` 中 `count` 是 COUNT 查询的**行数组**，必须写 `count[0].total`；写成 `count.total` 恒为 `undefined`，`Number(undefined)` → NaN，于是 `total` 出参变成 `null`、`hasMore` **恒 false** —— 症状是「后台列表底部永远没有『加载更多』，数据一超过一页就翻不动」，而代码读起来毫无破绽。注意单查询的 `const [[count]] = await pool.query(...)` 里 `count` 就是首行，`count.total` 是对的，两种解构别互相抄。2026-09-19 修掉 9 处（`adminController` 7 + `paymentController` 1 + `walletController` 1，覆盖举报/帖子/跑腿/订阅日志/用户/认证/操作日志/支付流水/提现）。护栏 `tests/admin-list-pagination.test.js` 是双层：**行为层**顶掉 pool 后调用真实接口，断言 `total` 是有限数字且「返回 2 条 / 共 7 条」时 `hasMore` 必须为 true；**静态层**扫出所有多结果解构并要求函数体内不出现裸 `count.total`（覆盖行为层没测到的控制器）。
- **安全**：`safeMessage` 会把 `ER_*` 统一降级成「数据库操作失败」，排查必须**绕开应用直接跑 SQL**。

### 六、部署（腾讯云 193.112.187.95 / pm2 `GQG-campus` / `/home/springboot/server`）

- 三端各自发布**互不联动**：小程序端 `pages/ components/` 用开发者工具「上传」；管理后台 `pkg-admin/`（分包）随小程序一起上传；服务端 `server/` 用 `python deploy_full.py`（全量）。
- **前端跑本地代码、请求打线上域名 → 极易出现「前端已是新版、后端还是旧版」**（2026-09-11/12 蹲贴功能的 404 就是这么来的：本地代码写了两天，线上完全没有）。
- 判断后端版本用 grep 特征串，别靠猜（如 `grep -c followedList controllers/postController.js`）。
- **上传 controller 前先算清依赖闭包**：线上缺 `services/subscribeService.js` 时上传新版 `notificationService.js` 会让**整个服务 MODULE_NOT_FOUND 崩溃**（pm2 100 次重启、站点 502）。必须先「require 自检」（`node -e "require(...)"`）+ 单独 `node app.js` 起一遍，再 `pm2 restart`。
- 部署顺序：备份 → 上传（md5 逐一比对）→ **单独先跑迁移** → `SHOW COLUMNS` 核对 → restart → 复核启动日志 + 接口 401/200（**无 token 返回 401 说明路由已注册，404 说明没注册**，比等用户在界面上试快得多）。
- `deploy_full.py` 清单会漏模块（club/groupChat/activity 曾长期不在清单里）。跑全量前先核对 `server/controllers/*.js`、`server/routes/*.js` 是否都在清单中。
- `.env` 是 CRLF，取密码必须 `tr -d '\r'`，否则 `Access denied`。`node -e` 跑迁移后进程不退出（连接池 handle）**不代表卡住**，判断依据永远是 `INFORMATION_SCHEMA` / `SHOW COLUMNS` 的实际结果。SSH 里 `node -e "...SQL..."` 引号会被吃，多行脚本一律 sftp 上传 `tmp-*.js` 跑完 `rm`。
- `pm2 logs` 混显 out.log（会滚）与 err.log（不滚），判断「是不是本次新增」用 `wc -c < logs/err.log` + `tail -c +N`。

### 七、测试约定

- 页面回归：`vm` 沙箱加载**真实页面文件** + 假 `setData`，放 `server/tests/*.test.js`，末行 `X tests passed.`，失败 `process.exit(1)`。桩里本地模块**返回真实模块**（返回 `{}` 会让改名/新增依赖立刻崩），页面新增模块依赖后所有加载它的测试桩同步补上。假 `setData` **必须支持数据路径**（`'messages[0].avatar'`），否则断言永远看不到效果。
- 服务端回归：假 `require.cache` 顶掉 `../config/pool` 再 require 真实 controller，能覆盖 SQL 文本与参数。**断言 SQL 参数一律比完整数组，不要 `slice(0,N)`**（默认 `pageSize=10` 恰好等于测试的 `AUTHOR_ID` → 少传参数也「通过」，假绿）。
- **多重防护的代码，每个分支都要有「只让它生效」的测试输入**（否则断言是被同函数另一条分支拦住的，删掉目标校验测试照样绿）。
- **新增测试后必须反向验证**：回退源码跑一遍，确认以 exit 1 失败，否则这条测试是假的。**静态断言的 `assert.match` 必须带行首锚点**（`/^\s*router\.get\('\/x'/m`）—— 不带锚点时被注释掉的 `// router.get('/x'` 同样匹配，正向全绿、反向验证也绿，等于没测。
- **「静态看不出、只有行为能证」的缺陷，用行为层 + 静态层双层护栏**：行为层顶掉 pool 用桩数据调用真实接口、断言数值（分页 `total` 必须是有限数字、`hasMore` 必须正确）；静态层全仓扫模式（如所有多结果解构里禁止裸 `count.total`）兜住行为层没覆盖到的文件。两层各自做一次反向验证。参考 `tests/admin-list-pagination.test.js`、`tests/post-query-param-count.test.js`。
- vm 测试两个坑：跨 realm 的 `[]`/`{}` 用 `assert.deepStrictEqual` 会报「same structure but not reference-equal」，先 `JSON.parse(JSON.stringify(v))`；页面 `fmtDateTime()` 只吃 `'YYYY-MM-DD HH:mm:ss'` 字符串。
- 断言「字段齐备」用子集比较，别用 `Object.keys` 全等 —— 正常新增字段会长期假红（`club-categories-clubs.test.js` 曾因此挂了两天）。
- **接口存在多个 `mapXxx` 映射时，新增字段必须同步所有映射** —— 漏抄一个就是「某个页面显示为 0/空」的经典来源。本项目 `userController.mapProfilePost()` 曾漏 `view_count` 与 `pinned`（SQL 是 `SELECT p.*`，数据一直在结果集里）→ 主页浏览量恒为 0，而首页正常，因为首页走的是 `postController.mapPost()`。用户看到的现象是「所有浏览量都是 0」，很容易误以为是埋点/统计问题，实际是**手工映射漏字段**。
  这条的护栏做法（可复用）：**从组件模板里自动提取字段名做子集断言** —— 正则扫 `components/xxx/xxx.wxml` 里的 `post.xxx`，叠加 `.js` 的 `observers` 里声明的依赖，逐个断言 `f in 响应对象`。这样卡片以后加字段而接口漏给，测试会直接点名缺哪个，而不是等用户报「显示为 0」。只在被隐藏分支里用到的字段要显式列白名单并注明理由（如 `isLiked` 只在 `showFooter` 为真时渲染）。断言仍用子集（`f in obj`），不要 `Object.keys` 全等。参考 `server/tests/profile-post-fields.test.js`。
- **字段豁免名单本身会掩盖缺陷**：按「当前页面看不到这个字段」就把它排除，风险很大。本项目 `profile-post-fields.test.js` 曾把 `isLiked` 列入豁免（理由：主页 `showFooter=false` 不渲染点赞按钮），但**同一接口也被 `pages/my-posts` 的「我的帖子」列表复用，而那里 footer 是显示的** → 豁免直接掩盖了「点赞态恒为 false」。结论：① 豁免前必须确认该接口的**所有**调用方都不需要这个字段；② 豁免理由要写进注释，并把「曾经豁免过什么、为什么又移出」记下来。
- CSS/WXML 改完至少跑 `node --check`（JS）+ 标签/括号配平。
- 仓库 `core.autocrlf=true`，但**工作区行尾是混合的**（`server/controllers/` 下 `adminController.js` 是 LF、`paymentController.js` 是 CRLF）：批量改动脚本必须用 `\r?\n` 感知的正则并**保持原换行符**。**`sed -i` 在 git bash 下会把整个 CRLF 文件转成 LF**，`git diff` 里表现为「几千行全变了」、真实改动被淹没 —— 要按行号改就用 Python `open(path, newline='')` + `readlines()` / `writelines()`，改完必须 `git diff --stat` 确认只动了目标行。
