### 一、帖子与内容

#### 1.1 匿名帖校区显示 / 分享海报内容 / 主题分类校验（2026-09-14）

**现象**
- 匿名帖在列表/详情/热榜永远显示「未设置校区」；
- 分享海报不显示原帖头像/配图/图片，且无标题；
- 未选主题分类点「确认发布」无任何反应。

**根因**
- `server/controllers/postController.js` 的 `mapPost()` 对匿名帖主动把校区置空：`campus: anonymousIdentity ? '' : (r.campus || "")`；发布后写入本地缓存的乐观数据也写 `campus: anonymous ? '' : me.campus`。
- `pages/poster/index.js` 画头像/配图的两处从头到尾只画灰色占位块，从未加载真实图片；海报只画 `post.content`，标题未出现；canvas 2d 的 `drawImage` 不能直接画网络图片（需先落地为本地临时文件）。
- `pages/post-publish/index.js` 的 `onSubmit` 第一行 `if (!this.data.canSubmit || this.data.submitting) return`，未选分类时 `canSubmit===false` 直接 return，后面 `if (categoryIndex < 0)` 的提示成了不可达代码。

**处理方案**
- 校区与普通帖一致：`campus: r.campus || ""`，本地乐观插入数据也改 `campus: me.campus`。
- 海报新增 `downloadImage()`（远程图片先 `wx.downloadFile` 成本地临时文件）、`imageUrlOf()`（兼容 `'url'`/`{url}`/`{path}`/`{thumb}`）、`prepareAssets()`（头像+最多3张配图+小程序码并行准备）、`loadCanvasImage()`（`canvas.createImage()` 预加载，失败降级）。头像真实图片圆形裁剪，配图圆角裁剪（最多3张，超出 `+N`），正文先画标题（加粗最多2行）再画正文。小程序码移卡片底部避免留白/重叠。
- 发布页 `onSubmit` 去掉 `!canSubmit` 的提前 return，校验顺序：先拦截 `submitting` → `auth.requirePublishReady()` → 内容空提示 → `categoryIndex < 0` 提示「请选择分类」（`wx.showToast({ icon: 'none' })`），早于上传与请求。

**涉及文件·接口·SQL**
- `server/controllers/postController.js`（`mapPost`）、`pages/post-publish/index.js`、`pages/poster/index.js`、`server/tests/post-display-and-publish.test.js`。
- downloadFile 合法域名只需填 `https://payun01.cn`（全库 75 处对外资源均在此域）；内置头像 `/assets/avatar2/*.jpg` 走 `readFile` 读 base64，远程走 `downloadFile`。
- 海报视频（2026-09-14 17:40 追加）：新增 `mediaOf()` 识别 `type==='video'` 或 `.mp4/.mov/.m4v/.avi/.webm`，有封面画封面+播放角标、无封面画深色视频卡片；canvas 无法截视频帧，需上传时生成封面图（引入 ffmpeg 或前端截帧）—— 未做。

**验证**
- 线上实测匿名帖 `post#90/#89/#85` HTTP=200 `isAnonymous=true campus="南海北校区"`；未设校区用户仍返回空串→「未设置校区」。
- 头像/正文真机截图确认；版式量算 5 种内容组合卡片高度 300~394，二维码/品牌文字均在画布内；全量 32 项测试通过。

**结论**
匿名帖不再因代码而被隐藏校区；海报能真实呈现标题/头像/配图/视频；未选分类有明确提示拦截。

#### 1.2 已删除帖子仍出现在每日热榜（2026-09-15）

**现象**
作者或管理员在别处删除帖子后，热榜上该帖仍显示，直到手动下拉刷新或重新进入页面。

**根因**
服务端过滤本就正确：`GET /api/v1/post/hot-rank`（`postController.hotRank`）主查询与兜底查询都带 `p.status = 1`，从未把已删除帖放进榜单；生产核对「执行过 `post.delete` 且当前 `status` 仍为 1」的帖子数 = 0（58 条 `post.delete` 全部 `status=0`），热榜返回恰为 23 条 `status=1`。真正原因在客户端：
- 独立热榜页 `pages/hot-rank/index.js` 与搜索页 `pages/search/index.js` 仅 `onLoad` 拉取、不在 `onShow` 重拉；被 `navigateTo` 推入栈后存活，`navigateBack` 只触发 `onShow` → 榜单不刷新。
- 首页/详情页热榜请求失败的 `.catch()` 原样保留旧列表，含刚被删帖。
- 删除成功到下一次拉取之间存在窗口期。
- 响应无 `Cache-Control`，中间层可能缓存旧榜单。

**处理方案**
- 新增 `utils/hot-rank.js`：`markPostRemoved()` / `filterRemovedPosts()`（带 10 分钟 TTL 的本地广播），`buildHotPosts()` 内置过滤，首页/详情/搜索天然一致。
- `pages/hot-rank/index.js`、`pages/search/index.js` 加 `onShow` 重拉（用 `_loadedOnce` 跳过首次）；`pages/post-detail/index.js` 在 `handlePostMissing` 与删除成功后调 `markPostRemoved`，失败 `catch` 剔除已删帖；`pages/index/index.js` 失败 `catch` 剔除已删帖。
- `server/app.js` 对 `/api` 统一设置 `Cache-Control: no-store, no-cache, must-revalidate, proxy-revalidate` + `Pragma: no-cache` + `Expires: 0`。

**涉及文件·接口·SQL**
- `utils/hot-rank.js`、`pages/hot-rank/index.js`、`pages/search/index.js`、`pages/post-detail/index.js`、`pages/index/index.js`、`server/app.js`；接口 `GET /api/v1/post/hot-rank`（`p.status = 1`）。

**验证**
- 新增 `server/tests/hot-rank-deleted-post.test.js`（11 用例）：标记后剔除 / TTL 过期不再过滤 / `buildHotPosts` 内置过滤 / 热榜页 onLoad+onShow 请求次数 / 详情页两路径广播 / 失败剔除 / 捕获真实 SQL 含 `p.status=1` / `/api` 带 `no-store`。73 个测试文件全通过。
- 生产端到端（2026-09-15 13:58）：热榜返回 22 条（已剔除 post 102），已删的 45/78/83/95/102 均不出现，`GET /post/102` → 404，响应头带 `no-store`，pm2 双实例 online，错误日志空。

**结论**
服务端无需改动；客户端已修但需在微信开发者工具重新上传发布后才生效（未上传前用户仍见旧行为）。

#### 1.3 主页帖子浏览量恒为 0（2026-09-16）

**现象**
查看自己或他人主页的帖子，浏览量都显示 0；置顶帖在主页无「置顶」角标；列表卡片点赞态永远未点赞。

**根因（两类）**
- **映射漏字段**：`server/controllers/userController.js` 的 `mapProfilePost()` 专用映射手工列举字段时漏了 `view_count`、`pinned`、`isLiked`。SQL 用 `SELECT p.*` 已含 `view_count`，但映射未抄 → 前端 `utils/api.js` 容错 `viewCount: r.viewCount || r.view_count || 0` 两键皆无 → 恒为 0。`postController.mapPost`（首页/详情/热榜用）字段齐全，故仅主页异常。
- **SQL 未产出列**：`mapProfilePost` / `postController.followedList` 的查询未产出 `isLiked` 列（无 `forum_like` 子查询），映射层虽有 `isLiked: !!r.isLiked` 也拿不到 → 点赞按钮永远未点赞。

**处理方案**
- `mapProfilePost()` 补 `viewCount: item.view_count || 0`、`pinned: !!item.pinned`、`isLiked: !!item.isLiked`。
- `getProfilePosts()` 的 SQL 加 `IFNULL((SELECT 1 FROM forum_like l WHERE l.post_id = p.id AND l.user_id = ?), 0) AS isLiked`，参数最前补 `currentUserId`（数组由 `[profileId, pageSize, offset]` 改为 `[currentUserId, profileId, pageSize, offset]`）。
- `followedList()` 的 `baseSelect` 加同样子查询；`mine` 分支 `[userId, pageSize, offset]` → `[userId, userId, pageSize, offset]`，`theirs` 分支 4 个 userId → 5 个 userId。
- `pages/post-publish/index.wxml` 文案「允许被匿名私信」改为「允许被分身私信」（与全局术语统一）。

**涉及文件·接口·SQL**
- `server/controllers/userController.js`（`mapProfilePost`、`getProfilePosts`）、`server/controllers/postController.js`（`followedList`、`baseSelect`）、`pages/post-publish/index.wxml`。
- 接口 `GET /user/profile/:id/posts`、`GET /user/my/deleted-posts`。
- 子查询 `IFNULL((SELECT 1 FROM forum_like l WHERE l.post_id = p.id AND l.user_id = ?), 0) AS isLiked`；未登录 `currentUserId=0` 子查询恒不命中 → `isLiked=0`。

**验证**
- 新增 `server/tests/profile-post-fields.test.js`（11 条）：viewCount 须为库内 280 非 0、`pinned` 为 true、从 `post-card.wxml` 自动提取 `post.xxx` 逐个断言存在、参数严格等于 `[currentUserId, profileId, pageSize, offset]`、匿名帖带浏览量且不泄露真实昵称、文案含「允许被分身私信」。反向验证三处移除均变红。全量 81/81 通过。

**结论**
服务端部署后主页浏览量/置顶角标/点赞态均正常；无数据库迁移（`forum_like` 表已存在）。注意三端互不联动：若只改前端文案未部署后端仍见 0。

#### 1.4 校区边界与腾讯地图对齐（2026-09-14）

**现象**
小程序校园地图里佛山校区（南海校区北区）蓝色虚线围栏是手工外扩的 9 顶点粗轮廓，与腾讯地图实际 AOI 明显不一致：北侧没到钟边水库南岸、东侧漏宿舍突出块、西/南侧切进校区内部，取景区偏西偏南，校区无法完整入画。

**根因**
旧围栏是「按四个校门坐标外扩闭合」人工推测，非腾讯 AOI 数据。

**处理方案**
以腾讯 AOI 为真值做标定提取：① 标定——腾讯截图 4 个校门像素位置 ↔ 官方坐标线性拟合（`lng = 113.029824 + (x − 78.4)/32672`、`lat = 23.160352 − (y − 298.3)/35615`，残差 <0.2px）；② 提取——按蓝色取虚线短划连通域质心、邻接串链、2-opt 消自交、Douglas-Peucker 简化（容差 2.6px≈4m）；③ 吸附——4 个校门官方坐标插入最近边界段。

**涉及文件·接口·SQL**
- `pages/campus-map/index.js`（`CAMPUSES.foshan.polygon` 换 58 顶点轮廓 + 取景区改 AOI 质心 scale 15）、`server/tests/campus-map-panorama.test.js`（新增 F 组几何护栏：≥40 顶点/0 自交/面积 50~80 万㎡）、新增 `docs/campus-boundary-verify.html`（腾讯底图叠加校验页）。

**验证**

- 真机复核与 `node server/tests/campus-map-panorama.test.js` + `campus-map-boundary.test.js`。

**结论**

### 二、评论与回复

#### 2.1 回复子评论时父评论跳顶（2026-09-11）

**现象**
评论区存在嵌套结构（父评论+子评论）时，对某个父评论下的子评论回复，该父评论（主评论）异常跳回评论区顶部。

**根因**
`pages/post-detail/index.js` 的 `onSendComment` 成功后 `applySuccess` 构造置顶标记：`parentId ? { rootId: findCommentRootId(parentId), replyId } : { rootId }`；而 `buildCommentThreads` 对 pin 无条件 `if (pin && pin.rootId) moveToTopById(sortedRoots, pin.rootId)`。回复场景 `rootId` 是被回复评论所属根评论 id，整条主评论被挪到顶部——「顶层新评论置顶」与「回复置顶」两种语义混在一起。

**处理方案**
- `buildCommentThreads` 的 pin 处理新增 `rootToTop` 语义：`rootToTop !== false` 才置顶根评论；`false` 时只把新回复置顶到所属回复列表顶部，根评论保持原位。
- `onSendComment` → `applySuccess`：回复场景 pin 加 `rootToTop: false`；顶层评论保持置顶。
- 乐观更新阶段即按最终规则传 pin（回复 `{rootId, replyId: tempId, rootToTop: false}`；顶层 `{rootId: tempId}`），消除二次跳动。

**涉及文件·接口·SQL**
- `pages/post-detail/index.js`（`buildCommentThreads`、`onSendComment`、`applySuccess`、`moveToTopById`、`findCommentRootId`）。
- 新增 `server/tests/comment-reply-no-jump.test.js`（vm 沙箱加载真实页面文件，9 项）。

**验证**
- 覆盖：hot 排序回复子评论父评论保持原位、回复非首位评论不跳顶、顶层新评论仍置顶、time 排序不重排、失败回退。该用例在修复前源码上 exit 1（反向验证）。

**结论**

#### 2.3 管理员删除评论的级联与计数重算（2026-09-12）

**现象**
管理员/帖子作者在帖子详情页点评论「···」菜单无「删除」；调 `DELETE /api/v1/comment/242` 返回 403。

**根因**
`commentController.remove` 的 SQL 为 `UPDATE forum_comment SET status = 0 WHERE id = ? AND user_id = ?`，只认评论作者，管理员/帖子作者删他人评论命中 0 行返回 403。线上诊断 `grep -c post_author_id = 0` 确认后端仍是旧实现（前端跑本地新代码、后端旧版）。

**处理方案**
- 权限矩阵：管理员（`content_admin`/`super_admin`）可删任意帖任意评论；帖子作者可删自己评论区里任意评论（含他人发的，不能删别人帖下）；评论作者删自己那条；其他用户 403。
- `commentController.remove` 重写：一次查询 `LEFT JOIN forum_post` 同时取评论与帖子作者；权限 管理员 ∨ 评论作者 ∨ 帖子作者，皆不满足→403；先查 `status=1` 不存在→404（重复删除也 404）；逐层收集后代回复一次性软删（数据存在二级及更深回复）；同步 `forum_post.comment_count`（按实际删除条数扣减，`GREATEST(...,0)` 兜底）；返回 `{ removed: N, asPostAuthor }`。
- 前端 `utils/api.js` 新增 `deleteComment`；`pages/post-detail/index.js` 新增 `canDeleteOtherComment(isOwner)`（管理员任意帖、帖子作者 `post.userId === currentUserId` 为是）、`onCommentMore` 按身份生成菜单、新增 `deleteCommentAsModerator`（确认弹窗写明「及其 N 条回复将对所有用户不再展示」）、`onDeleteComment` 改走 `api.deleteComment` 并同步计数。
- `utils/auth.js` 加固：`saveUser` 的 `role` 由 `user.role || 'user'` 改为 `user.role || current.role || 'user'`。

**涉及文件·接口·SQL**
- `server/controllers/commentController.js`（`exports.remove`）、`utils/api.js`、`utils/auth.js`、`pages/post-detail/index.js`、接口 `DELETE /api/v1/comment/:id`、表 `forum_comment`（`status=0` 软删）、`forum_post.comment_count`。

**验证**
- 新增 `server/tests/comment-admin-delete.test.js`（16 项）：无关用户→403、评论作者删自己连带三层回复 `removed:3` 参数 `[3,77]`、帖子作者删自己评论区他人→200 `asPostAuthor:true`、删别人帖下→403、管理员跨帖→200、非法/重复删除→404；前端菜单分支与计数 3→1。反向验证三处回退均 exit 1。全量 29 项通过。

**结论**
评论删除权限、级联软删、计数重算三处缺陷一并修复；线上后端为旧版是 403 直接原因，已单独上传该文件（备份 `commentController.js.bak-20260912-005122`）。小程序端需开发者工具上传后生效。

### 通用经验

- **计数重算（跨 3.1 / 2.3）**：凡是涉及计数器的软删或新增，要么按明细表重算（`forum_post_follow` 启动时按明细表幂等重算 `follow_count`，修正历史脏数据），要么同事务双写/扣减（`follow` 明细表与 `follow_count` 双写；删除评论按实际删除条数扣减 `forum_post.comment_count`，`GREATEST(...,0)` 兜底）。否则会出现「列表显示 N 条、点进去只剩 M 条」的计数虚高。
- **字段映射（跨 1.3 / 3.1）**：列表接口一旦新增前端卡片要用到的字段，必须同时改服务端映射函数（`postController.mapPost` / `userController.mapProfilePost`）与前端卡片；`mapProfilePost` 漏映射 `view_count`/`pinned`/`isLiked`、`mapPost` 漏下发 `isFollowed`/`followCount` 都曾导致字段恒为 0/undefined。建议用「从 `post-card.wxml` 自动提取 `post.xxx` 逐个断言接口返回存在」（见 1.3 测试第 3 条）作为护栏，防止后续新增字段而接口漏给。
- **参数占位符数必须配平（跨 3.1 / 3.3）**：新增 SQL 子查询会引入新 `?`，参数数组未同步补位时 mysql2 不报错、只静默错位（`profileId` 被当 `userId`、`pageSize` 被当 `OFFSET`），现象是 500 或查错数据。统一用「`?` 个数 === 参数个数」断言（见 3.3 `post-query-param-count.test.js`）通杀整类问题。
- **前端本地新代码 vs 后端旧版（跨 1.2 / 2.3 / 3.3）**：多起 403/404/500 根因都是「前端跑本地新版、后端仍是旧实现」。上线前用「无 token 调接口看 401（路由已注册）还是 404（路由不存在）」快速定位；上传 controller 前先算依赖闭包并离线 `require` 自检，避免 `MODULE_NOT_FOUND` 拖垮服务。

### 遗留问题与后续建议

- **海报视频帧**：canvas 2d 无法截视频帧、服务器未装 ffmpeg，海报对视频仅用封面/视频卡片表达。若需真实画面，应在上传时生成封面图（引入 ffmpeg 或前端截帧上传）并对历史视频回填。
- **广州校区边界精度**：缺少参考坐标，形状为腾讯 AOI 实描、位置锚定既有数据，绝对精度（残差 <0.2px）未达佛山水平。提供 2 个参考点（如 1 号门、新海医院）即可按同一流程重标。
- **蹲贴历史数据不可补**：用户此前本地蹲贴标记已被服务端真值覆盖且无法自动补录，需引导用户重新蹲贴。
- **三端互不联动**：多文档提示「前端改了但后端未部署」会呈现半成品（如浏览量仍 0、蹲贴仍 404）。建议上线 checklist 同时核对服务端版本特征（如 `post_author_id` 计数、`forum_like l WHERE l.post_id` 存在性）与前端包版本。
- **客户端多改动未上传**：1.2 客户端 5 文件、2.3 小程序端、3.3 小程序端均需在微信开发者工具重新「上传」后才生效，目前仍依赖人工操作，建议纳入发布流程自动校验。

社团模块覆盖「管理后台社团审核」与「用户端社团浏览」两端能力：后台含社团分类管理、社团审核（通过 / 驳回）；服务端提供公开接口 `GET /api/v1/club/categories`（分类 + 社团下发）、`GET /club/detail/:id`（社团详情）、管理接口 `GET /admin/club/applies` 与 `POST /admin/club/applies/:id/review`；小程序端含「社团&组织」列表页、分类详情页（`pages/club/detail`）与社团详情页（`pages/club/club-detail`），并伴生群聊 / 社团审核的自愈补建逻辑。

### 社团列表与数据下发

#### 公开接口不下发社团列表（clubs 字段丢失）

**现象**

1. 管理后台「社团分类管理」能看到审核通过的社团（艺术类：武术社、你好，均「启用」），统计「社团 2 个（启用 2）」；
2. 用户端「社团&组织」页（佛山校区）每个分类都显示「0 个重点社团」，顶部统计「0+ 重点社团」，分类详情页同样空无社团；
3. 不只是新通过社团——人文类 / 实践类 / 创新创业类各 5 个内置社团也全是 0。

**根因**

`server/controllers/clubController.js` 的 `mapCategoryRow(row, clubs)` 声明了 `clubs` 形参却从未写入返回值；`loadClubsByCategory()` 查出的社团被传入后又直接丢弃，公开接口 `GET /api/v1/club/categories` 响应里连 `clubs` 字段都不存在。用户端 `utils/club-data.js` 的 `mapServerCategory()` 对缺失字段兜底成 `[]`，于是「分类都在、社团全是 0」。管理端 `adminListCategories()` 走另一条路径，自带 `clubs: grouped[row.id] || []`，故管理端看不见该 bug。

线上实测（只读）：`club` 表「武术社」(全部校区) 与「你好」(佛山校区) 均为 `status=1 / deleted=0`，`club_apply` 1 号为 `approved`，数据正常；但接口返回分类对象到 `"sortOrder":1,"status":1` 即结束，确实无 `clubs`。

**处理方案**

| # | 文件 | 改动 | 目的 |
| --- | --- | --- | --- |
| 1 | `server/controllers/clubController.js` | `mapCategoryRow()` 返回值补上 `clubs: Array.isArray(clubs) ? clubs : []` | 公开接口按分类下发社团明细，用户端「重点社团」计数与详情页恢复。管理端仍用含停用社团的完整列表覆盖该字段，行为不变 |
| 2 | `deploy_full.py` | 文件清单补入 `clubController` / `groupChatController` / `activityController` 及三个对应路由 | 这三个模块从不在部署清单里（社团 / 群聊为后加），下次全量部署会降级回旧代码。顺带加注释提醒新增模块同步清单 |

**涉及文件·接口**

- 服务端：`server/controllers/clubController.js`（`mapCategoryRow` / `listCategories`）、`deploy_full.py`
- 接口：`GET /api/v1/club/categories`（公开）
- 用户端：`utils/club-data.js`（`mapServerCategory`）

**验证方式**

- 新增 `server/tests/club-categories-clubs.test.js`：用假 pool 加载真实 `clubController`，跑 `listCategories`——每个分类必带 `clubs`、审核通过的社团在内、已下架 / 已删除社团被过滤、空分类为 `[]`、校区筛选（佛山校区 = 全部校区 + 佛山校区，排除广州校区专属）、主校区匹配其分校区、未知校区回退不过滤、停用分类不下发；再喂给 `mapServerCategory` 断言用户端艺术类 `clubs.length === 2`。
- 反向验证：回退 `clubController.js` 跑测试以 exit 1 失败（报「每个分类都应带 clubs 数组」），恢复后全绿。
- 生产端到端：部署后直连 `127.0.0.1:3000`，全部校区 / 佛山校区均正确返回各分类社团；重启后 `logs/err.log` 无新增错误；线上四个文件与本地 md5 逐一比对一致。

**结论**

纯增量字段，管理端行为不变；用户端「重点社团」计数与分类详情页恢复正常。

#### 顺带修复：群聊自愈补建每次启动报错（同一文档内发现）

**现象**

重启日志每次必出两条：

```
[migrations] 补建申请 1 群聊记录失败： Column count doesn't match value count at row 1
[migrations] 补建申请 2 群聊记录失败： Column count doesn't match value count at row 1
```

**根因**

`group_chat_apply.images` 是 JSON 列，mysql2 将其解析成 JS 数组；把数组直接当 `?` 参数传入 SQL 时，mysql2 转义器把数组展开成「逗号分隔的多个值」——一个占位符撑成 N 个值，列数（11）与值数（11 - 1 + N）对不上，抛 `ER_WRONG_VALUE_COUNT_ON_ROW`。

连带隐患：自愈 JOIN 为 `LEFT JOIN group_chat g ON g.apply_id = a.id AND g.deleted = 0`，被管理员主动删除的群聊会被当成「不存在」。线上申请 1（交易）、2（你好）群聊 `deleted=1`，每次启动都被判「待补建」。crash 掩盖了它；只修崩溃不修 JOIN 会复活这两条群聊。

**处理方案**

| # | 文件 | 改动 | 目的 |
| --- | --- | --- | --- |
| 3 | `server/utils/helpers.js` | 新增导出 `toJsonColumn(value)`（数组 / 对象 → JSON 字符串；字符串原样返回；空值 → null），与 `parseImages` 互逆 | 给「从库读 JSON 列再写回 SQL」提供统一入口 |
| 4 | `server/utils/migrations.js` | 补建 `images` 参数改用 `toJsonColumn(apply.images)`；JOIN 去掉 `AND g.deleted = 0` | 崩溃消失；管理员删过的群聊不再复活 |
| 5 | `server/controllers/groupChatController.js` | `reviewApply()` 通过时把申请单图片介绍同步进群聊（UPDATE / INSERT 都补 `images` 列，用 `toJsonColumn` 序列化） | 此前审核通过创建的群聊完全没有图片介绍（自愈补建反而有，说明漏写），用户端群详情缺图 |

**涉及文件·接口**

- `server/utils/helpers.js`、`server/utils/migrations.js`、`server/controllers/groupChatController.js`
- 接口：`POST /admin/club/applies/:id/review`（群聊审核通过路径）

**验证方式**

- 新增 `server/tests/json-column-param.test.js`：`toJsonColumn` 边界（数组 / 对象 / 已序列化字符串 / 空值）；`reviewApply` 通过时 INSERT 必须含 `images` 列且传入字符串而非数组；`migrations.js` 自愈补建不得带 `g.deleted = 0`、`images` 必须过 `toJsonColumn`。
- 反向验证：回退 `migrations.js` + `groupChatController.js` 跑测试以 exit 1 失败，恢复后全绿。
- 已排查其余同类位置（`forum_post` / `forum_comment` 的 `images`、`contact`、`anonymous_identity`、`components`，`club_category` 的 `scope` / `features`，`virtual_item_log` 的 `before_data` / `after_data`，`notificationService` 的 `imagesJson`）写入前均已 `JSON.stringify`，无同类问题。
- 生产验证：重启后 `err.log` 无新增错误；`group_chat` 表仍 5 行，管理员删除群聊 `deleted=1` 未被复活。

**结论**

自愈 JOIN 去掉 `deleted = 0` 后，线上「待补建」数量从 2 变 0（无真正需补建），逻辑成为无害空转；`reviewApply` 多写 `images` 列仅影响新审核通过群聊，存量群聊不被自动回填（需单独刷数据）。

### 审核状态常量体系

#### 管理端社团审核列表 CLUB_APPLY_STATUS_TEXT 未定义

**现象**

进入管理后台「群聊 / 社团 → 社团 → 社团审核」后：

1. 开发者工具控制台抛红：`CLUB_APPLY_STATUS_TEXT is not defined`（栈顶 `pkg-admin/admin/index.js:1292`）；
2. 列表恒空，仅显示「暂无社团申请」；
3. 切换「待审核 / 已通过 / 已驳回」筛选均无效——非没数据，是列表渲染逻辑中途抛错中断。

**根因**

`loadClubApplies()` 映射每行申请时使用了未定义的 `CLUB_APPLY_STATUS_TEXT`：

```js
// pkg-admin/admin/index.js:1291-1292
const list = (data.list || []).map((row) => Object.assign({}, row, {
  statusText: CLUB_APPLY_STATUS_TEXT[row.status] || row.status,   // ← 常量从未声明
  ...
}))
```

本文件只声明了群聊同类常量 `GC_APPLY_STATUS_TEXT`（第 66 行），新增社团审核功能照抄映射逻辑却漏掉对应 `CLUB_APPLY_STATUS_TEXT` 声明。接口层 / 路由层本身无问题：`pkg-admin/utils/admin.js` 已封装 `clubApplies` / `reviewClubApply`，`server/routes/adminRoutes.js:57-58` 已注册 `GET /admin/club/applies` 与 `POST /admin/club/applies/:id/review`。JS 的 `??`/`||` 只兜得住「取值 undefined」，兜不住「标识符未声明」，故必然抛 `ReferenceError`。

**处理方案**

| # | 位置 | 改动 | 目的 |
| --- | --- | --- | --- |
| 1 | `pkg-admin/admin/index.js` 第 66 行后 | 新增 `const CLUB_APPLY_STATUS_TEXT = { pending: '待审核', approved: '已通过', rejected: '已驳回' }`，补注释「与服务端 `club_apply.status` 一致」 | 消除 `ReferenceError`，列表正常渲染 |

改动仅 3 行（2 行注释 + 1 行常量），未触既有逻辑；`node --check pkg-admin/admin/index.js` 通过。

**涉及文件·接口**

- `pkg-admin/admin/index.js`、`pkg-admin/admin/index.wxml:231-234`
- `pkg-admin/utils/admin.js`（`clubApplies` / `reviewClubApply`）
- `server/routes/adminRoutes.js:57-58`：`GET /admin/club/applies`、`POST /admin/club/applies/:id/review`
- `server/controllers/clubController.js`（`club_apply.status` 取值 `pending` / `approved` / `rejected`）

**验证方式**

- 新增 `server/tests/admin-club-apply-status.test.js`：用 `vm` 沙箱加载真实 `pkg-admin/admin/index.js`，stub 掉 `wx` / `getApp` / `require`，注入假 `admin` API；覆盖 5 组共 11 条断言（页面不再抛 `ReferenceError` 完成 `Page()` 注册、`pending/approved/rejected` 三态正确映射、`images` 非数组兜底 `[]`、`clubChar` 取首字符、`reviewedAtText` 生成 / 留空、未知状态回退原值、服务端不返回 `list` 落空数组、`clubApplyStatus` 随请求透传、竞态保护）。
- 反向验证：回退 `pkg-admin/admin/index.js` 运行，测试以 `FAILED: loadClubApplies 不应抛错 → CLUB_APPLY_STATUS_TEXT is not defined` 失败（exit 1），恢复后 11 条全过。

### 校区常量与详情页报错

#### 分类详情页因 CAMPUS_OPTIONS 未定义白屏

**现象**

分类列表页已正常显示社团数量（艺术类 2 个、共 17+ 个重点社团），但点进任一分类即崩，控制台报：

```
TypeError: Cannot read properties of undefined (reading 'indexOf')
    at di.onLoad (weapp:///pages/club/detail.js:15:34)
```

页面白屏 / 停在上一页。

**根因**

`pages/club/detail.js` 从校园工具模块解构了一个不存在的导出：

```js
const { CAMPUS_OPTIONS, getDefaultCampus } = require('../../utils/campus')   // ← CAMPUS_OPTIONS 不存在
…
this.campus = CAMPUS_OPTIONS.indexOf(fromQuery) >= 0 ? fromQuery : getDefaultCampus()  // ← undefined.indexOf → 崩
```

`utils/campus.js` 实际只导出 `CAMPUS_GROUPS` / `MAIN_CAMPUS_OPTIONS` / `APPLY_CAMPUS_OPTIONS` / `getProfileCampus` / `getDefaultCampus` / `isValidCampus` / `getSubCampus`。`CAMPUS_OPTIONS` 在整个 git 历史从未出现（「校区能力拆成主校区 / 申请用两套选项」时漏改），import 从写下那天起即错，且仅在「点进分类」时触发，故一直未被发现。解构不存在的导出不会在 require 时报错（仅拿到 `undefined`），要等到使用时才炸。

**处理方案**

选 `isValidCampus()` 而非 `MAIN_CAMPUS_OPTIONS.indexOf()`，并单独放行 `''`：

```js
const campusQuery = options && options.campus
const fromQuery = typeof campusQuery === 'string' ? decodeURIComponent(campusQuery) : null
this.campus = fromQuery !== null && (fromQuery === '' || isValidCampus(fromQuery))
  ? fromQuery
  : getDefaultCampus()
```

| 取值来源 | 期望行为 | 说明 |
| --- | --- | --- |
| 列表页带入主校区（佛山校区） | 原样采用 | 详情页与列表页看到同一批社团 |
| 列表页带入分校区（南海南校区） | 原样采用 | `isValidCampus()` 覆盖主校区与分校区两级，比原 `CAMPUS_OPTIONS`（只含主校区）更准确 |
| 列表页「全部校区」（`''`） | 原样采用 | `isValidCampus('')` 返回 `false`，须单独放行；否则「全部校区」下点进去反而只看某校区社团 |
| 未带入 campus（非列表页入口） | 回退用户设置校区 | 用 `typeof === 'string'` 区分「没传」与「传空串」 |
| 非法 / 乱码取值 | 回退用户设置校区 | 不把野值透传接口 |

**涉及文件·接口**

- `pages/club/detail.js`（小程序端，随开发者工具上传生效，无需服务端部署）

#### 1.1 头像素材文件名规范（含空格与半角括号真机渲染失败）

用户个人资料页顶部头像渲染为空白圆圈，但昵称、校区、手机号等其他字段均正常；首页信息流部分帖子作者头像缺失。微信开发者工具下不复现，真机（iOS/Android）必现。

**根因**
素材文件名含空格与半角括号，如 `assets/avatar2/1 (1).jpg`、`assets/avatar1/考拉 (2).jpg`、`老虎 (2).jpg`。`utils/avatar.js` 原实现用 `encodeURIComponent(filename)`，只把空格编码为 `%20`、不编码 `()`，生成 `/assets/avatar2/1%20(9).jpg`，括号裸奔留在路径中。真机对包内资源路径里的 `()` 解析行为不一致，导致图片加载失败。线上用户 70「秋日的果园」的 `avatar_url` 正是 `/assets/avatar2/1%20(53).jpg`，与现象吻合。

**处理方案**
- `assets/avatar2/`：`1 (1).jpg` … `1 (55).jpg` 重命名为 `avatar_01.jpg` … `avatar_55.jpg`（55 个），保留 `assets/avatar2/1.jpg`（WXML 兜底默认值仍引用）。
- `assets/avatar1/`（分身头像池）：`考拉 (2).jpg` → `考拉2.jpg`，`老虎 (2).jpg` → `老虎2.jpg`。
- 前端路径生成去掉 `encodeURIComponent`，新增 `normalizeLegacyAvatar()` 把旧路径映射到新文件名；`DEFAULT_AVATARS` 改为循环生成；`getDefaultProfile()` 自愈旧缓存。

**涉及文件·接口**
`utils/avatar.js`、`assets/avatar2/*`、`assets/avatar1/*`、`server/utils/defaultProfile.js`、`server/utils/migrations.js`（`repairUserAvatars()`、`normalizeLegacyAvatarUrl()`）。

**验证**
端到端模拟：用户 67/68/70（旧路径）与 69/71（空头像）全部解析到真实存在的文件；所有 `DEFAULT_AVATARS`(56) 与分身头像(38) 文件经脚本校验全部存在。

**结论**
素材文件名统一为纯 ASCII 是根治真机图裂的根手段；同时保持旧路径归一化函数兼容存量数据。

#### 1.2 新用户默认资料写入（空头像 + 硬编码默认昵称）

**现象**
部分新注册用户头像为空、昵称固定为「校园用户」。线上 12 个用户中 4 人命中：id 69/73「校园用户」且头像空，id 71「欧阳文界」/72「欧阳志鑫」头像空。

**处理方案**
- 新增 `server/utils/defaultProfile.js` 共用模块（避免 `userController` 与 `migrations` 循环依赖），提供 `buildDefaultProfile()`（生成 `avatar_XX.jpg` + 随机中文昵称）、`normalizeLegacyAvatarUrl()`（旧路径 → 新文件名）、`DEFAULT_NAME_VALUES`（历史默认昵称集合）。
- `phoneLogin()` 新用户注册改为写入非空随机头像 + 随机昵称。
- `getInfo()` / `getProfile()` / `getProfilePosts()` / `getInteractionList()` 返回值归一化。
- `server/middleware/auth.js` 在 `success()` 里递归归一化响应体头像字段（覆盖 `avatarUrl` / `avatar` / `actorAvatar` / `anonAvatar` / `fallbackAvatar`），对分散在帖子、评论、通知、聊天、社团、活动等十几个控制器中的头像字段统一处理。
- `repairUserAvatars()` 每次启动自动执行：① 旧路径 `1%20(N).jpg` → `avatar_0N.jpg`；② `avatar_url` 为空的用户补发默认头像；③ 昵称为「校园用户」等历史默认值的用户补发随机昵称；④ `system_notification.actor_avatar` 中历史头像快照同样修正（线上 28 条）。

**涉及文件·接口**
`server/controllers/userController.js`、`server/utils/defaultProfile.js`、`server/middleware/auth.js`、`server/utils/migrations.js`、`sys_user` 表、`system_notification` 表。

**验证**

**结论**
新用户默认资料从「空头像 + 校园用户」改为「随机头像 + 随机中文昵称」，历史数据由迁移自愈。

#### 1.3 客户端补报去重与本地缓存反向覆盖

**现象**
同一用户在不同页面头像/昵称不一致；部分用户服务端头像永远为空。

**根因**
- `utils/auth.js` 的 `saveUser()` 用内存对象 `saveUser._syncedProfiles` 做去重，且 `.catch(() => {})` 静默吞异常：杀掉小程序重进 → 内存标记丢失 → 重复上报；某次上报失败 → 永久不再重试 → 服务端头像永远为空。
- `pages/profile/index.js` 原实现 `Object.assign({}, profile, ext)`，清理条件只覆盖「两边都有且不同」的情况；当本地缓存有值、服务端为空时，缓存不会被清理，反而在 `Object.assign` 中盖住服务端空值，造成页面间不一致。

**处理方案**
- `saveUser()` 去重标记改为持久化 `wx.setStorageSync('profile_synced_<id>')`；失败改为 `console.warn` 并保留下次重试；`syncProfile()` 增加 `queued` 语义说明。
- `pages/profile/index.js` 修复缓存覆盖逻辑：服务端有值以服务端为准，缓存冲突项一律清除。
- `app.js` 启动读取本地缓存时归一化头像；`pages/user/index.js`、`pages/account-settings/index.js`、`pages/profile-edit/index.js` 的展示/刷新/初始化均做归一化；`utils/api.js` 的 `mapPost()` 对 `avatarUrl` 做归一化（所有帖子流量统一入口）。

**涉及文件·接口**
`utils/auth.js`、`pages/profile/index.js`、`app.js`、`pages/user/index.js`、`pages/account-settings/index.js`、`pages/profile-edit/index.js`、`utils/api.js`。

**验证**
前端 `local-imports.test.js`：65 处引用全部解析通过。

**结论**
去重标记持久化 + 服务端优先的合并策略，解决了跨页面不一致与静默失败问题。

#### 1.4 匿名身份纠正与真名降级风险（含分身昵称）

**现象**
私信聊天页控制台报渲染层错误：`Failed to load image .../assets/avatar1/XX%20(2).jpg`。库里仍有旧匿名形象路径存量：帖子/评论的 `anonymous_identity`、通知的 `actor_avatar` 快照、私信会话的分身档案。

**根因**
- `normalizeLegacyAvatarUrl` 只认 `avatar2` 的 `1 (N).jpg`，**不认识 `avatar1`**；服务端 `parseAnonymousIdentity` 只校验 `startsWith('/assets/avatar1/')`，**不校验文件名是否真实存在**——任何脏路径都能入库并长期渲染。
- 匿名素材池（分身昵称/头像）在 `utils/anonymousIdentity.js` 与控制器里各有一份定义，可能不一致或与 `avatar.js` 形成循环依赖。

**处理方案**
- `server/utils/defaultProfile.js` 新增匿名素材池常量 `ANONYMOUS_AVATARS`、`normalizeAnonymousAvatarUrl`（`考拉 (2).jpg` / `考拉%20(2).jpg` → `考拉2.jpg`）、`isAnonymousAvatarUrl`（白名单校验）、`pickAnonymousAvatar`（未知路径稳定映射，同一种子恒等同一形象）；`normalizeLegacyAvatarUrl` 顺带处理 `avatar1`。此函数是全站头像主出口，改这里一次性覆盖用户资料/帖子/评论/通知。
- `server/controllers/{comment,post,user,message}Controller.js` 的 `parseAnonymousIdentity` 改为「先纠正旧名 → 再做池内白名单校验 → 不在池内则稳定映射」。**纠正失败也绝不返回 null**——那会让匿名身份降级成真实昵称/头像，等于把匿名者暴露给被打扰的人。
- `server/controllers/messageController.js` 统一引用 `defaultProfile` 常量，去掉重复定义。
- `server/utils/migrations.js` 新增 `repairAnonymousAvatarPaths()`：修 `forum_post`/`forum_comment` 的 `anonymous_identity`、`private_conversation` 的 `anon_peer_identity`/`anon_self_identity`/`persona_key`、`system_notification.actor_avatar`（JSON 列经 `toJsonColumn` 写回）。
- `utils/avatar.js` 将池与归一化下移到底层，新增 `normalizeAnonymousAvatar`/`isAnonymousAvatar`/`looksAnonymousAvatar`/`pickAnonymousAvatar`；`anonymousIdentity.js` 改为引用，解除循环依赖。

**涉及文件·接口**
`server/utils/defaultProfile.js`、`server/controllers/{comment,post,user,message}Controller.js`、`server/utils/migrations.js`、`utils/avatar.js`、`utils/anonymousIdentity.js`、`forum_post`/`forum_comment`/`private_conversation`/`system_notification` 表。

**验证**
新增 `server/tests/anonymous-avatar-path.test.js`：`9 tests passed.`（覆盖旧名纠正含 `%20` 形态、avatar2 规则未回归、白名单、稳定映射、素材池与包内 `assets/avatar1/` 一一对应且文件名不含空格/括号、客户端与服务端池同源、评论列表与帖子详情出口必须下发池内路径且不得回落真实资料、迁移结构护栏）。
注意：测试需每个防护分支都有只让它生效的输入——曾出现「匿名会话 + 匿名素材」被白名单分支拦住、使 `anonymousMode` 分支假绿的案例，补「匿名会话 + 普通头像」用例后才拦得住。

**结论**
匿名形象路径必须走「纠正 → 白名单 → 稳定映射」且纠正失败不降级；素材池单点定义并前后端同源，是避免脏路径与真名泄露的关键。

### 二、聊天页头像点击跳转主页

#### 2.1 聊天页头像进主页需求

#### 2.2 网络请求失败兜底（原帖 404 / 主页白屏）

**现象**
消息详情页点「查看原帖」白屏一次：控制台 `GET https://payun01.cn/api/v1/post/34 404`、`/post/44 404`。`loadPost()` 请求已删除帖子 → 404，而 `.catch()` 只做 `setData({loading:false})`，页面停在「暂无法查看」，入口却仍可点，点进去又是一个 404。`pages/profile/index.js` 整页 `wx:if="{{profile}}"`，加载失败直接白屏。

**根因**
404 后仅关闭 loading，无不可用态标记与拦截；入口未禁用，导致反复 404。

**处理方案**
- `pages/message-detail/index.js`：新增 `postMissing` / `postMissingText`，404 → 「原帖已被删除或下架」，其他失败 → 「原帖加载失败，请稍后重试」；`viewOriginalPost()` 已知不可用时**不再跳转**，只提示原因。
- `pages/message-detail/index.wxml/.wxss`：卡片转虚线灰底，底部按钮转灰并显示「原帖已无法打开」。
- `pages/profile/index.js`：区分 404（「该用户不存在或已注销」）与网络失败；新增 `loadErrorText` 与重试。
- `pages/profile/index.wxml/.wxss`：新增 `.load-state` 兜底视图 + 「重新加载」按钮。

**涉及文件·接口**
`pages/message-detail/index.js`、`.wxml`、`.wxss`、`pages/profile/index.js`、`.wxml`、`.wxss`、`/api/v1/post/:id`。

**验证**
`chat-avatar-profile.test.js` 覆盖 404 标记 + 不再跳转、非 404 文案、正常可跳；反向验证去掉 `viewOriginalPost` 的 `postMissing` 拦截 → 退出码 1。

**结论**
网络失败态显式化，已知不可用即拦截跳转并给出原因，避免反复 404 与白屏。

**结论**


#### 4.3 交互改进与用户端群详情

**交互改进**

**用户端群详情**
- 群公告：独立卡片（浅黄底 + 保留换行），与「群介绍」区分。

### 遗留问题与后续建议

1. **`club-categories-clubs.test.js` 长期红灯**：`clubController` 返回了测试期望列表之外的 `adminQrcodeUrl`/`qrcodeUrl`/`images`/`clubType` 字段，属工作区另一条进行中的社团改动，与头像/群聊修复无关，建议尽快同步测试期望以免掩盖真实回归。
2. **`deploy_full.py` 清单治理**：此前社团、群聊、活动三模块也曾漏在清单外；建议将「新增目录/模块即同步部署清单」固化为提交前检查项（或改为目录扫描），避免修复无法上线。
3. **匿名形象与真名降级风险**：`parseAnonymousIdentity` 纠正失败绝不返回 null 的原则已落地，但跨控制器仍依赖集中归一化；建议持续以 `anonymous-avatar-path.test.js` 的「每分支独占输入」用例守护，防止脏数据组合绕过白名单。
4. **前端缓存旧路径兜底依赖 `binderror` 抖动保护**：当前「兜底值不变则不动」可避免抖动循环，但若默认头像本身缺失仍可能反复触发，建议上线后观察默认头像命中率。
5. **群聊「成员管理」边界**：小程序侧无法增删微信群真实成员，当前仅提供群主/规模/规则展示，建议在管理后台表单持续以灰底说明明示此边界，避免运营误以为可管理成员。
6. **发版协同**：头像/昵称修复与群聊表单均涉及前后端，需一起发布（前端重新上传审核、后端 `deploy_full.py` + `pm2 restart`），避免新旧版本字段/路径不一致。
