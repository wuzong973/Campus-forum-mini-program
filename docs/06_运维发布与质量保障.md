### 一、小程序内管理模块

#### 1.1 范围与数据模型

后端为原生微信小程序 + Express + MySQL。现有公开帖子查询仅返回 `forum_post.status = 1` 的记录，隐藏/已删除帖子不暴露给普通用户。

本次迁移新增字段：`sys_user.role`、`forum_post.pinned`、`forum_post.review_note`；新增数据表：`admin_audit_log`、`system_content`、`feature_config`、`virtual_item`、`virtual_item_log`。

初始功能配置项：`community.enabled`、`errand.enabled`、`repair.enabled`、`schedule.enabled`。已禁用的配置会在其 API 路由之前被拦截并返回 HTTP 503；不存在的配置默认视为启用，保证迁移期间向后兼容。

#### 1.2 角色与权限

| 角色 | 权限 |
| --- | --- |
| `super_admin` | 全部权限，包括角色分配与管理员账号管理（`admin.manage`） |
| `content_admin` | 帖子审核、内容/配置管理、仪表盘 |
| `user_admin` | 用户状态管理、仪表盘 |
| `operator` | 虚拟物品、功能配置、仪表盘 |
| `user` | 无管理权限 |

管理员账号管理仅 `super_admin` 可用（新增 `/admin/admins`、`/admin/audit-logs` 路由，权限标识 `admin.manage` 只被 `*` 命中）：

- **管理员列表**：按角色排序展示全部管理员及其权限说明、启用状态。
- **新增管理员**：输入已有用户 ID / 手机号 / 学号将其提升；服务端校验用户存在、未启用防护、重复提升拦截，多匹配时要求改用用户 ID。
- **调整角色 / 停用启用**：复用 `/admin/users/:id/role`、`/admin/users/:id/status`，含"最后一个启用的超级管理员"保护与"不能操作自己"限制。
- **操作日志**：`/admin/audit-logs` 分页展示全部审计记录，支持按操作类型前缀过滤（如 `post.`、`user.`）。

首个管理员通过数据库引导（刻意设计为仅 DB 引导，防止公开账号自行提权）：

```sql
UPDATE sys_user SET role = 'super_admin' WHERE id = <受信任的用户ID>;
```

#### 1.3 安全与审计行为

所有 `/api/v1/admin/*` 路由都验证 Bearer Token、检查当前数据库账户状态，并在服务端校验所需角色权限。禁用账户会使后续认证请求立即失效。客户端入口仅为便捷访问，直接导航无法绕过 API 校验。

帖子删除、审核、置顶、批量审核、内容变更、功能变更、虚拟物品变更、用户状态变更和角色变更都会写入 `admin_audit_log`；虚拟物品的创建/更新还会将操作前后快照写入 `virtual_item_log`。最后一个启用的超级管理员不能被降级或禁用。

#### 1.4 概览统计

`GET /admin/stats` 返回注册用户、7 日活跃、帖子各状态、跑腿单、虚拟物品销量与最近 8 条管理操作。计数查询相互隔离（`statOne`）：单表异常只影响对应指标并记录服务端日志，不会导致整个接口 500；响应携带 `generatedAt`。管理后台概览页每 15 秒自动轮询刷新，`onShow` 立即刷新一次，支持下拉刷新与手动刷新。

#### 1.5 校园活动：报名名单

`pkg-admin` 活动管理 tab 的活动卡片右侧操作列新增 **活动详情** 入口（位于「编辑 / 下架 / 删除」之上），仅渲染在管理端。服务端接口 `GET /admin/activities/:id/signups` 走 `requireAdmin('content.manage')`，非管理员得 403。

| 项目 | 说明 |
| --- | --- |
| 入口位置 | `pkg-admin` 活动管理 tab → 每张活动卡片右侧操作列第一项（蓝色胶囊按钮「活动详情」） |
| 可见范围 | 仅持有 `content.manage` 权限的管理员 |
| 接口权限 | `GET /api/v1/admin/activities/:id/signups`，`requireAdmin('content.manage')` |
| 数据范围 | 单活动维度，按报名时间升序；`keyword` 按昵称或手机号过滤，分页每页 50 条 |
| 审计 | 查看名单为只读，不写入 `admin_audit_log` |

展示形式：弹窗分活动概要、报名用户列表（头像+昵称+手机号+校区+报名时间，顶部搜索，超过 50 条"加载更多"）、隐私提示（固定文案）。手机号属敏感个人信息，仅由管理端接口返回，用户端 `/activity/*` 不输出他人手机号。

#### 1.6 群聊模块：群聊信息 / 群聊审核

「群聊/社团」父级菜单 →「群聊」子页，用三级分段控件切换。

| 选项卡 | 内容 |
| --- | --- |
| 群聊信息 | 原页面保留：建群申请审核（列表+通过/驳回）、群聊列表（添加/编辑/上下架/删除）、群聊类别编辑 |
| 群聊审核 | 用户提交的建群申请审核：状态筛选（全部/待审核/已通过/已驳回）+ 卡片 + 详情弹窗 + 通过/驳回（可改判），可见范围 `config.manage` |

通过：立即按申请信息创建群聊并上架用户端「广轻群聊」；驳回：审核意见必填并在用户端「我的申请」可见；均支持改判。申请人手机号仅由管理端接口返回。

#### 1.7 社团模块：社团审核

小程序「社团&组织」页入口 → 首次入驻弹窗 → 填写申请单提交，经管理员审核通过后才出现在用户端分类。

- 入口：`pkg-admin` 社团/群聊 tab →「社团」子页 → 顶部分段「社团审核」（同段另一位为「社团分类管理」）。
- 接口：`GET /api/v1/admin/club/applies`、`POST /api/v1/admin/club/applies/:id/review`，均 `requireAdmin('config.manage')`。
- 数据：全部申请，支持 `status`（`pending`/`approved`/`rejected`）筛选与关键词搜索，分页每页 50 条，默认待审核优先、其后按申请时间倒序。
- 审核行为：通过→在所选分类下上架一条 `club`；驳回→下架关联社团、意见必填且用户端可见；均支持改判，重复通过只刷新不重复上架；写入 `admin_audit_log`（动作 `club.apply.approve` / `club.apply.reject`）。
- 隐私约束：申请人手机号仅由管理端接口返回，用户端 `/club/*` 不输出他人手机号，`/club/mine` 只返回本人申请。

#### 1.8 维修信息（日志 tab 第三分段）

用户端「预约维修」提交后只落 `repair_order` 表，管理员此前没有任何入口能看到，只能在用户端「我的订单」里看自己下的单 —— 表现为「用户说提交了维修预约，后台查不到」。2026-09-19 在日志 tab 内新增第三个分段「维修信息」，位置紧接「订阅消息」右侧。

| 项目 | 说明 |
| --- | --- |
| 入口位置 | `pkg-admin` 管理后台 →「日志」tab → 顶部分段控件第三项：跑腿订单流程 / 订阅消息 / **维修信息** |
| 可见范围 | 仅持有 `admin.manage` 权限的管理员（与同 tab 的跑腿订单流程、订阅消息一致） |
| 接口权限 | `GET /api/v1/admin/repair-orders`，`requireAdmin('admin.manage')` |
| 数据范围 | 全部用户的预约维修记录，按 `id` 倒序；`status` 支持 `unpaid`/`paid`/`accepted`/`repairing`/`finished`/`cancelled` 六态筛选；`keyword` 匹配订单号 / 联系人 / 手机号 / 上门地址 / 昵称 / 记录 ID；分页每页 20 条 |
| 展示形式 | 列表卡片 + 完整资料弹窗 |
| 审计 | 查看为只读，不写入 `admin_audit_log` |

列表卡片直接展示 **用户头像 + 昵称 + 注册手机号 + 状态胶囊**，其余逐行为：联系人（姓名 · 手机号 · 微信号）、上门地址、服务内容（故障描述）、预约上门时间与提交时间、订单号与金额。点卡片弹出完整资料弹窗，追加订单号、支付时间、维修人员与故障照片（可点开大图），并提供「复制手机号 / 复制微信号」便于联系用户约上门时间。

字段来源：提交人资料（`nick_name` / `avatar_url` / `phone`）来自 `sys_user`，上门信息与故障内容来自 `repair_order`。`images` 是 JSON 列，出口统一过 `parseImages` 归一化（库中可能是数组、对象或字符串三种形态），否则前端 `.length` 会把对象当数组用。

隐私边界：他人手机号仅在管理端接口返回；用户端 `/repair/orders` 只返回本人订单，不输出他人资料。

### 二、Web 管理后台迁移方案（重点）

> 本部分合并 `Web管理后台迁移方案.md`（设计稿）与 `Web管理后台_推荐路径与决策备忘.md`（决策层），两篇均标注 2026-09-12，结论一致，已去重。（以 2026-09-12 文档为准）

#### 2.1 结论摘要

| 维度 | 结论 |
| --- | --- |
| 功能模块 | 小程序管理后台共 **10 个一级 Tab**（含 3 个合并父级菜单、7 个子页），覆盖约 **50 个 `/api/v1/admin/*` 接口**、**8 个权限点** |
| 后端是否重建 | **否**。`/api/v1/admin/*` 是纯 JSON + Bearer 的客户端无关接口，Web 可直接复用，无需 BFF |
| 数据库 | **单实例单库共享**，不做双写、不做同步 |
| 认证 | **必须新建**。现有 `phone-login` 依赖 `wx.login`/`getPhoneNumber` code，Web 无法复用；且 `sys_user` 表**无任何密码字段** |
| 最大风险 | 认证通道新建、接口契约适配、资金类操作暴露面扩大、限流与审计 IP 失真 |
| 建议路径 | 后端加 `admin/auth` 模块 → Web 独立 SPA → 双端并行观察 → 小程序端 admin 入口下线 |

#### 2.2 背景与现状盘点

系统架构：微信小程序（原生）+ Nginx（`payun01.cn`）+ Node/Express（`:3000`）+ 单库 MySQL + Redis；`sys_user.role` 是唯一权限真源。

关键事实：

- 生产域名 `https://payun01.cn/api/v1`，服务器单机 + `pm2` **cluster 2 实例**，端口 3000。
- 认证：JWT（HS256，单密钥，`7d` 有效期），载荷仅 `{ userId }`；每次请求都回查 `sys_user` 的 `role` 与 `status`（`server/middleware/auth.js`）。
- 授权：`requireAdmin(permission)` 服务端强制校验，客户端隐藏菜单只是便捷层，直接调接口无法绕过。
- 限流：全局 `rateLimit({ max: 120 })`（120 次/分钟），优先走 Redis（`server/middleware/rateLimit.js`），Redis 不可用时降级为单实例内存计数；当前仅此一处全局限流，未按路由分配配额。
- 跨域：生产 `CORS_ORIGIN=https://payun01.cn`（单值白名单，**不含 admin 域**）。小程序 `wx.request` 不发 `Origin` 故现状无感，但浏览器跨域会被直接拦截——这是 Web 上线的硬阻塞项。
- Redis（`ioredis`）已是实际依赖，`config/redis.js` + `.env.example` 中 `REDIS_HOST/REDIS_PORT/REDIS_PASSWORD/REDIS_DB` 均已具备。

管理后台 10 个一级 Tab（`pkg-admin/admin/index.*`，JS 1714 行 / WXML 1234 行 / WXSS 252 行，通过 `activeTab` 切换）：

| # | Tab | 名称 | 可见权限 | 核心能力 |
| --- | --- | --- | --- | --- |
| 1 | `overview` | 概览 | `stats.view` | 注册用户/7日活跃/帖子各状态/跑腿单/虚拟物品销量 + 最近 8 条管理操作；15 秒轮询刷新 |
| 2 | `reports` | 举报 | `content.manage` | 举报列表、处置（状态 + 备注） |

#### 2.3 目标架构

核心原则：**后端只有一个，数据库只有一个，Web 与小程序是同一后端的两类客户端。**

- 总体：`微信小程序(pages/* + pkg-admin)` 与 `Web 管理后台 SPA(admin.payun01.cn, Vue3 + ElementPlus)` 共用 Nginx（`/api/v1/*` → `:3000`、`/ws` → `:3000`）→ Express（`pm2 cluster ×2`，`auth`/`requireAdmin` 共用，`/api/v1/admin/*` 复用，新增 `/api/v1/admin/auth/*`）→ MySQL（单库）+ Redis（票据/刷新令牌/分布式限流）。
- 技术选型：Vue 3 + Vite + TypeScript、Element Plus、Pinia（`token/role/permissions`）、Vue Router（动态路由+守卫）、Axios 封装（注入 Bearer、401 刷新、错误提示，对齐 `{code,message,data}`）、ECharts（概览趋势）、Nginx 静态托管 + HTTPS。不建议引入 SSR（Nuxt）。
- 部署拓扑（两种可选）：
  - **方案甲（推荐）：独立子域** `admin.payun01.cn` → Nginx 静态目录，`/api/v1/*` 反代 `127.0.0.1:3000`。优点：Cookie 域隔离干净、CSP 独立、可单独做 IP 白名单；需新增 HTTPS 证书。
  - 方案乙：同域子路径 `payun01.cn/admin/` → 静态目录。零证书成本、同源无跨域，但 CSP/安全头互相影响。若未来采用 httpOnly Cookie，方案甲更安全。

#### 2.4 推荐路径与决策结论

**一句话结论**：别一次迁完 10 个模块。先做"能跑起来、只覆盖高频与高风险操作"的 Web 后台：认证走**账号密码**（不依赖小程序发版），部署用**独立子域**，技术栈用 **Vue 3 + Element Plus**，第一期只做 **4 个模块**。

四个决策（建议）：

| 决策 | 建议 | 关键理由 |
| --- | --- | --- |
| D1 认证方案 | 账号密码优先（A），扫码排第二迭代（B） | 不依赖小程序发版（该项目曾被微信审核驳回过一次，审核是真实排期风险）；零小程序改动，服务端加路由即可当天联调；后台管理员个位数规模，密码体系够用 |
| D2 部署形态 | 独立子域 `admin.payun01.cn` | 后台能审提现/裁退款，值得叠 IP 白名单；与小程序 `web-view` H5 隔离避免 CSP/Cookie 干扰；证书成本近零 |
| D3 前端技术栈 | Vue 3 + Vite + TypeScript + Element Plus + Pinia | WXML→Vue 模板近乎机械映射（`wx:if`→`v-if`、`wx:for`→`v-for`、`{{ }}` 一致、`bindtap`→`@click`），现有 1234 行 WXML 翻译成本最低；`el-table/el-form/el-upload` 正好对应表格+表单+上传 |
| D4 小程序发版 | 可接受，但不放进关键路径 | 首版 Web 不需任何小程序改动；将来做扫码登录或下线小程序 admin 入口时各发一次版即可 |

排除的两个方案：① 用 Taro/uni-app 把 `pkg-admin` 编译成 H5——产出是移动端布局，桌面端最需要的多列表格/批量勾选/并排表单全部作废；② 一次把 10 个 Tab 全迁完再上线——周期长、风险集中、低频模块收益小于成本。

第一期只做 4 个模块：① 登录 + 权限守卫（验证 `/admin/me` 渲染机制）；② 概览（15s 轮询先例，端到端验证请求层/错误处理/令牌刷新）；③ 帖子 + 举报（最高频，最依赖表格与批量勾选）；④ 提现审核 + 异议裁决（最高风险，需清晰金额展示、二次确认、审计留痕）。暂缓（双端并行继续用小程序端）：群聊/社团、物品、配置、活动管理、管理员管理、跑腿日志。

上线前不能省的三件事：① CORS 白名单加 admin 域（生产当前单值 `https://payun01.cn`，不加则浏览器全被拦）；② 管理端独立限流（现有按 IP 计数，同一 NAT 出口管理员共享 120 次/分钟，需按 `userId` 计数并置于 `auth` 之后）；③ 后台 IP 白名单（Nginx `allow/deny` 或云安全组，替代 TOTP 的主要风险兜底）。

2026-09-12 当周即可启动的三件事：① 抽接口契约（把约 50 个 `/admin/*` 接口的入参/出参/权限点从代码抽成完整文档，补齐 `docs/api-contract.md` 缺口，与 D1/D3 无关、不会浪费）；② 拍板 D1/D3；③ 建 Vue 工程 + 打通登录（脚手架、请求层、路由守卫、`admin/auth/login`、概览页跑通）。

#### 2.5 认证打通方案（技术核心）

三种方案对比：

| 方案 | 实现要点 | 优点 | 缺点 | 需改小程序 |
| --- | --- | --- | --- | --- |
| A 账号密码 | 新增 `sys_user.password_hash`（或独立 `admin_credential` 表）+ bcrypt/argon2 | 不依赖微信、最快落地 | 新增凭据面；现有用户无密码需初始化；需密码策略/锁定/找回；当前无 bcrypt 依赖 | 否 |
| B 小程序扫码登录 | Web 出二维码 → 小程序扫码确认 → Web 轮询换 token；票据存 Redis（5min TTL） | 零新增凭据、复用微信身份、免密、安全性最高 | 需新增小程序页面并发版审核；需 `wxacode.getUnlimited` | **是** |
| C 手机号+短信验证码 | 接入短信服务商 | 用户无感 | 需短信资质与费用、通道风险、仍属新增凭据面 | 否 |

推荐分阶段：

- **阶段一（快速解锁）→ 方案 A：账号密码 + TOTP 二次验证**。仅对 `role != 'user'` 的账号开放 Web 登录；新增独立表 `admin_credential(user_id, password_hash, totp_secret, failed_count, locked_until, last_login_at, last_login_ip)`，**不动 `sys_user` 主表**；首个 `super_admin` 密码通过服务器命令行脚本初始化（与"仅 DB 引导首个管理员"的安全约定一致）；必须实现密码强度校验、连续失败锁定、登录审计（写 `admin_audit_log`）。
- **阶段二（长期最优）→ 方案 B：小程序扫码登录作为主通道**。复用阶段一权限与令牌体系，仅替换"身份确认"环节，逐步停用密码通道（或仅保留给超级管理员应急）。

令牌策略：

| 项目 | 小程序（现状） | Web（建议） |
| --- | --- | --- |
| 类型 | 单 access token | access + refresh 双令牌 |
| 有效期 | 7 天 | access 2 小时 / refresh 7 天 |
| 载荷 | `{userId}` | `{userId, aud:'admin-web', jti}` |
| 存储 | 内存 + storage | 内存（Pinia）+ refresh 存 httpOnly Cookie **或** localStorage |
| 失效 | 改 `sys_user.status` 即失效 | 同左 + Redis 黑名单支持主动登出 |

必须保留现有安全特性：`auth` 中间件每次请求回查 `sys_user.status`，禁用账号立即失效；Web 端不要改成"仅验签不查库"。

#### 2.8 风险与回滚

**认证与安全风险（最高优先级）**：无密码字段 → 独立 `admin_credential` 表；令牌同源（单 JWT 密钥、无 `aud`）→ 加 `aud/iss` 区分、Web 用短 TTL、服务端按 `aud` 拒绝跨端；令牌存储 XSS（localStorage 可被窃取）→ 优先 httpOnly Cookie + CSRF Token，或内存 + refresh 轮转；密码体系维护成本 → "停用即失效" + 强制首次改密 + 登录审计；扫码钓鱼 → 确认页展示设备/IP/时间 + 二次点击；暴力破解 → 独立限流 + 失败计数锁定 + 图形验证码；越权 → 所有接口继续走 `requireAdmin`（不得退化）。

**接口契约风险**：字段命名驼峰/下划线混用（`success()` 对十余个键归一化）→ Web 侧建统一 adapter，不为 Web 改后端；分页无 total → 扩展返回 `total`；筛选能力弱 → 新增可选参数；503 语义（`featureFlag` 关闭模块）→ Web 必须识别为"功能已关闭"而非服务异常。

**数据一致性与并发风险**：双端并存期并发编辑 → 审核类写操作引入 `updated_at` 乐观锁校验；审计重复 → 标注来源端（`detail.source = 'web' | 'miniprogram'`）；缓存一致性 → 管理端不建议缓存业务列表，或仅短 TTL + 写后失效。

**性能与限流风险**：全局 `rateLimit({ max: 120 })` 挂在认证之前、key 取 `req.userId || req.ip`，尚未解析 `userId` 故实际按 IP 计数；Redis 不可达时静默降级为单实例内存计数（cluster 下 120×2 且不稳定）；同一 NAT 出口多名管理员共享 120/min，Web 多标签页+轮询+批量+导出易触顶 → 为 `/api/v1/admin/*` 挂独立限流并按 `userId` 计数（置于 `auth` 之后），并确认生产 Redis 可用；批量操作（100 条）同步串行，Web 端加进度反馈与超时保护。

**业务连续性风险**：迁移期功能回退——小程序 admin 是当前唯一入口，Web 未验证完成前**不可下线**，必须保留双端并行窗口；角色权限同步——若 Web 引入更细按钮级权限，须回到服务端扩展 `ROLE_PERMISSIONS` 并同步 `TAB_PERMISSIONS`，避免两端可见性不一致，建议权限定义收敛为服务端唯一真源由 `/admin/me` 下发；首个管理员引导——沿用"仅 DB/脚本引导"，绝不开放公开注册提权。

**资金与合规风险**：提现审核（`payment.manage`）与跑腿异议裁决是真实资金出口，暴露面扩大后须二次确认弹窗 + 展示金额与收款方 + 幂等键（现有 `X-Idempotency-Key` 机制务必继续传递）+ 强制审计留痕；个人信息——后台可查看手机号，Web 端需默认脱敏（`138****0000`）、查看明文二次授权、导出必须留痕可追溯；审计 IP 真实性——`admin_audit_log.ip` 已存在、服务端 `trust proxy = 1`，须确认 Nginx 正确透传 `X-Forwarded-For`；访问控制——建议对 `admin.*` 子域叠加 IP 白名单/VPN 并启用登录告警。

**部署与运维注意事项**：Web 静态与后端同机时注意 `helmet()` 默认 CSP 影响（Nginx 托管则无影响）；`CORS_ORIGIN` 硬阻塞须把管理后台域名加入白名单（`app.js` 已支持逗号分隔多值）；令牌密钥轮换需同时兼容小程序与 Web，建议引入 `JWT_SECRET` 多版本（kid）机制。

**回滚策略**：迁移全程保留小程序端 `pkg-admin` 作为应急入口（S6 前不下线）；Web 首版出问题可降级为只读或直接切换回小程序 admin；认证模块（`admin/auth/*`）为唯一后端改动，可独立回退而不影响既有 `/api/v1/admin/*`。

### 三、运维

#### 3.1 备份与恢复策略

1. 启用 MySQL 二进制日志，保留期应长于全量备份保留期。
2. 低流量时段每日运行一次 `server/scripts/backup-mysql.ps1 -Mode full`。
3. 每小时运行 `server/scripts/backup-mysql.ps1 -Mode incremental -BinlogStart mysql-bin.000001:4`；下次运行前将成功结束的文件/位置持久化到调度器状态。
4. 备份复制到应用服务器之外并加密存储；每日全量至少保留 14 天，每季度进行一次恢复测试。

脚本从 `server/.env` 读取数据库凭证，仅对子客户端进程设置 `MYSQL_PWD` 并在退出前清除；要求 `mysqldump`、`mysqlbinlog`、`mysql` 在 `PATH` 中可用。

恢复演练：

1. `restore-mysql.ps1 -BackupFile <路径> -ConfirmRestore` 将最新全量备份恢复到隔离数据库。
2. 按时间顺序用 `mysql` 应用增量 binlog 文件。
3. 完整性检查：`sys_user`、`forum_post`、`private_message`、`user_schedule`、`errand_order`、`repair_order` 的行数；验证最新创建时间戳。
4. 记录恢复点目标（RPO）与恢复时间目标（RTO）。

#### 3.2 RPO / RTO

建议初始目标：**RPO ≤ 1 小时，RTO ≤ 4 小时**（以恢复演练实测记录为准）。

#### 3.3 监控告警

对以下指标设置告警：5xx 错误率、MySQL 连接池饱和、Redis 错误、WebSocket 重连量、支付回调失败、备份作业失败。

#### 3.4 访问控制

- 应用程序、备份工作进程、模式迁移分别使用独立 MySQL 用户；应用程序用户不得拥有 `DROP`、`GRANT` 或全局管理权限。
- 生产环境仅保持 HTTPS 和 WSS。
- 引入浏览器管理控制台时，CORS 配置使用显式允许来源（如 `admin.payun01.cn`），而非 `*`（与 2.8 中 `CORS_ORIGIN` 硬阻塞项一致）。
- 建议对 `admin.*` 子域叠加 IP 白名单 / VPN 限制并启用登录告警（见 2.4、2.8）。

#### 3.5 日志脱敏

- 在隐私政策允许范围内，发送含 `requestId`、路由、状态码、耗时和认证用户 ID 的结构化日志。
- **切勿记录** JWT、授权码、手机号、密码或支付密钥。
- 后台可查看手机号（活动报名名单、社团/群聊申请人）；Web 端需默认脱敏展示（`138****0000`）、查看明文二次授权、导出功能必须留痕可追溯（与 2.8 资金与合规风险一致）。

### 五、失败原因分析

#### 5.1 `press-spring-shared.test.js`：新按钮未按共享层规范接入（真实产品缺陷）

**触发源**：`pages/post-publish/index.wxml:49`（本次未提交改动，该行 `git diff` 显示整行被替换）

```html
<!-- 新增：投票编辑器头部胶囊「添加」 -->
<view class="poll-editor-add spring-btn" hover-class="poll-editor-add-hover" hover-stay-time="80" bindtap="saveComponentEditor">添加</view>

<!-- 原（HEAD）：底部确认按钮，合规写法 -->
<button hover-class="press-spring" class="sheet-confirm spring-btn" bindtap="saveComponentEditor" hover-stay-time="120">保存投票</button>
```

**判定依据**：`docs/2026-09-30_按钮弹性按压反馈.md` §7 明确两种合规写法，其中「方式二：页面已有 hover 类」要求 `hover-class="xxx-hover press-spring"`，且该 hover 类在 wxss 中必须含 `scale(0.96)` + inset 内阴影。

**实际状态**：

- WXML 侧：`hover-class="poll-editor-add-hover"`，**未追加** `press-spring`；
- WXSS 侧：`pages/post-publish/index.wxss:108` 的 `.poll-editor-add-hover { background: #f4f6f8; }` **只有背景色**，无 `scale(0.96)`、无 inset 阴影。

**影响**：该「添加」按钮只挂到了 `spring-btn`（释放回弹过渡），按压态没有物理压缩与凹陷质感，反馈退化为「仅背景变色」。这属于护栏设计的典型静默失效（不报错、只是没手感），不影响功能可用性，属**中低危交互缺陷**。

**连带发现（同一断言的第二处违规）**：本次还新增了未跟踪模块 `pages/market/`，其中 `pages/market/index.wxml:10` 使用 `hover-class="category-hover press-spring"`（已带 `press-spring`），但 `pages/market/index.wxss:7` 的 `.category-hover { background: #eef3fa; }` 同样缺 `scale(0.96)`。即：修好第 1 处后，`press-spring-shared.test.js` 的「每个 hover 类必须有 scale(0.96)」断言（`:140`）会紧接着在 `category-hover` 上失败。

**全站扫描量化（只读独立分析脚本，非测试文件）**：

| 指标 | 当前工作区 | 干净 HEAD |
|---|---|---|
| 交互元素挂 `spring-btn` | 278 | 277 |
| hover-class 追加 `press-spring` | 274 | 273 |
| hover 类总数 | **65** | 63 |
| hover 类缺 `scale(0.96)` | **2**（`poll-editor-add-hover`、`category-hover`） | 0 |
| 缺 `press-spring` 的 hover-class | **1**（`poll-editor-add-hover`） | 0 |
| 缺 `hover-stay-time` / 裸 `<button>` | 0 / 0 | 0 / 0 |

**修复建议（二选一）**：

1. 推荐：`hover-class="poll-editor-add-hover press-spring"`，同时给 `.poll-editor-add-hover`、`.category-hover` 补 `scale(0.96)` + inset 内阴影；或
2. 若刻意要自定义按压幅度，则按文档「方式二」保留并补齐样式，同时更新护栏文案。

#### 5.2 `settings-publish-privacy.test.js`：测试断言陈旧（契约漂移，非产品缺陷）

**触发源**：`pages/profile/index.js` + `pages/profile/index.wxml`（本次未提交改动）

本轮改动把「隐藏主页帖子」从**设备本地开关（只作用于本人主页）**改为**服务端驱动的访客视角开关**：
