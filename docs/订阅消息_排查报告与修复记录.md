## 概述

这些排查的共同结论是：**用户感知的「收不到 / 延迟」绝大多数不是服务端发得慢，而是「根本没发出去」**。按实测，主因依次为：① 微信一次性订阅额度用尽（`skipped`，占比最高）；② 5 分钟合并窗口静默丢弃（`merged`）；③ 匿名私信分支整块跳过推送（无记录）；④ 代码缺陷导致失败（`40001` 凭据被多实例互相作废、`47003` 字段空值）。微信侧投递延迟服务端不可观测，属微信机制。额度用尽是平台硬上限，只能靠提高授权覆盖率；凭据失效的代码修复已实现，但截至 2026-09-16 排查报告采集时**尚未部署上线**。

## 一、排查订阅消息的标准动作与判据

### 1. 核心表与各状态含义

排查以 `subscribe_message_log` 为唯一事实源。拿用户 id 跑一句 SQL，按 `status` 分流：

```sql
SELECT id, user_id, tpl_type, status, errcode, errmsg, page, created_at
FROM subscribe_message_log
WHERE user_id = ? ORDER BY id DESC LIMIT 20;
```

| 查到的状态 | 含义 | 是不是「延迟」 |
|---|---|---|
| 查不到记录 | 业务事件没触发；或该类型不推送（点赞只发站内信，`notificationService` 只推 comment/follow/reply）；或消息被合并窗口判到别处 | 不是延迟，是没发 |
| `skipped`（errmsg = 额度不足） | 用户没授权过，或授权次数已用尽 | 不是延迟，是没发 → 引导重新订阅 |
| `merged` | 5 分钟窗口内同类消息已发过，本次**直接丢弃且不补发** | 不是延迟，是丢弃 |
| `failed` + errcode | `43101` 用户拒收/未订阅（服务端已清零额度）· `47003` data 字段超长/与模板不符 · `40003` openid 无效 · `45009` 接口调用超限 | 是失败，不是延迟 |
| `throttled` | **客户端本地弹窗节流命中**：该触发组当天已弹满 3 次，本次**连微信都没调用**。这是唯一由客户端上报写入的状态（见《功能实现与改造》§七） | 不是延迟、也不是失败 → 用户当天被弹窗次数上限拦下，次日自动恢复 |
| `sent` | **我方已成功交给微信**，之后到达时间由微信投递决定，服务端无任何可观测手段 | 延迟在微信侧 |

> `sent` 之后的延迟只能靠用户配合定位：① 微信是否在后台运行/刚开机联网；② 微信「设置 → 新消息通知」是否开启；③ 小程序订阅消息设置里该项是「允许」还是「拒绝」。这三项都在微信客户端，服务端查不到。

### 2. 如何自证我方无延迟（时间戳对比法）

把 `subscribe_message_log.created_at`（发送成功返回后才写）与业务表（`private_message` / `forum_comment`）的 `created_at` 对齐比较，**同秒即证明我方即时发出**。

此外：`subscribe_message_log` 是**授权阶段不产生流水**的——订阅授权（微信弹窗）阶段不会有新记录，故「开关自动关闭」类问题**不能靠查库**，必须在客户端看（见第七节）。

### 3. 标准排查顺序（可复用）

1. 取 `subscribe_message_log` 按用户/类型/状态分流（上表）。
2. 看 `status` 分布：`skipped` 多 → 额度；`failed` 多 → 看 errcode；`merged` 多 → 合并窗口。
3. 服务端 `err.log` 中 `[Subscribe]`/`[MessageSubscribe]`/`[ErrandSubscribe]`/`[SubscribeLog]` 计数若为 0，说明微信接口从未返回 errcode、也从未抛异常。
4. 客户端问题（授权弹窗/开关回弹）→ 用 vConsole 看原生弹窗、`wx.getStorageSync('subscribe_comment_prefs')`、`subscribe_reopen_guide_*` 节流键。

## 二、推送延迟排查结论（2026-09-14）

### 现象

用户反馈订阅消息「明显延迟 / 收不到」。

### 根因结论

**不是小程序/服务端发送时机问题。** 实测服务端在业务事件发生的**同一秒**就调用了微信发送接口，全链路耗时 < 1 秒，且历史 156 次发送**零失败**。真实原因排序：

| 排序 | 真实原因 | 占比/证据 | 是否小程序自身问题 |
|---|---|---|---|
| 1 | 订阅额度已用尽被跳过（`skipped` 额度不足） | 125 / 156 = **80%** | 是（机制设计导致，需补引导） |
| 2 | 5 分钟合并窗口把重复提醒直接丢弃（`merged`） | 13 / 156，集中在高频类型 | 是（丢弃且不补发） |
| 3 | 微信客户端投递延迟（用户不在线/被后台清理时下次联网才到达） | 服务端不可观测 | 否（微信机制） |
| 4 | 用户侧设置：关闭新消息通知 / 开了消息免打扰 / 订阅消息设「拒绝」 | 一旦有此情况服务端应记 43101，当前 `failed = 0` → 目前非主因 | 否 |
| 5 | 定时任务扫描粒度（活动提醒提前 30 分钟 + 每 10 分钟扫一次） | 实际提前量 30~40 分钟 | 是（但属预期行为） |

### 处理 / 涉及文件·接口·表

- 表：`subscribe_message_log`、`user_subscribe_quota`、`private_message`、`forum_comment`、`system_notification`。
- 状态分布（2026-09-14 快照）：`sent` 18 · `merged` 13 · `skipped` 125 · `failed` 0。
- 额度分布（2026-09-14 快照）：`commentNew` 9 人有额度/剩余 15；`commentReply` 7/18；`message` 5/20；其余 15 个模板 1~4 人、剩余 1~8。
- 关键链路文件：`server/services/subscribeService.js`（`MERGE_WINDOW_MS` 5 分钟、`push()`、`pushBroadcast()`、`quotaOf`/`consumeQuota`）、`server/controllers/errandController.js:94-133`（`pushErrandSubscribe` 靠中文字符串匹配路由：`text.indexOf('已被接单')`/`'完成'`/`'评价'`）、`server/services/notificationService.js:53-71`（仅 comment/follow/reply 下发）、`server/controllers/messageController.js:241-249`（commit 后不 await 推送）、`server/utils/wechatToken.js`、`server/.env` 的 20 个 `WX_TPL_*`、`client/utils/subscribe.js`。
- `MERGE_WINDOW_MS`：`commentNew`/`commentReply`/`message` 均为 **5 分钟**；`allowByMergeWindow()` 命中即写 `merged` 并 `return {sent:false}`，**消息内容被丢弃不补发**。
- `push()` 顺序：额度检查 → 合并窗口 → 查 openid → 取 token → `axios.post`；`{ timeout: 8000 }` 且无重试；`catch` 全吞返回 `{sent:false, reason:'exception'}`。
- `pushBroadcast()`：串行 `for` + `await push()`，上限 200 人，不 await 调用（不阻塞审核接口），但队列尾部投递时间被拉长。
- **只读排查，未改任何生产数据/线上代码**（临时脚本用完即删）。

### 结论

链路没问题，卡在「没有额度可发」。额度 = 用户点「允许」的次数，一次性订阅每允许一次只 +1 条，用尽即 0，服务端再也发不出去。

### 遗留的修复方向（按性价比，待确认后实施）

- 【高】额度耗尽后让入口重新出现：`client/utils/subscribe.js` 已导出 `shouldShowDialogAsync(trigger)`（拉服务端额度判 `Number(quota[key]||0) <= 0`），当前全仓零调用；应本地判「已订阅」时再用异步额度判定复核。
- 【高】`merged` 不再静默丢弃：落待发表或窗口内聚合为「等 N 条新评论」。
- 【中】`push()` 加退避重试，仅对可重试错误重试 1~2 次：`axios` 超时/网络错误/`errcode = -1`/`45009`；`43101`/`47003` 不重试。
- 【中】广播改分批并发（每批 10~20 人 `Promise.allSettled`）。
- 【中】跑腿模板路由去掉中文关键词匹配，改显式 `event` 参数（`'accepted'|'finished'|'cancelled'`）。
- 【低】额度耗尽时写站内信「微信提醒次数已用尽」形成闭环；管理后台加「订阅消息日志」查询页。

## 三、订阅开关「开启后自动关闭」根因与修复（2026-09-15）

### 现象

视频（7.05 秒）逐帧还原：顶部「订阅评论消息提醒」开关在 2.4s 点亮变绿，2.80~2.93s 动画回弹到灰色关闭，全程**无微信原生授权弹窗、无任何 toast/提示**。

### 根因

1. **受控组件被无条件复位**：入口行 `<switch checked="{{xxxSubscribeChecked}}">`，点击链 `onXxxSubscribeTap → applyXxxSubscribe`（先 `setData({xxxSubscribeChecked:true})` 变绿，再 `subscribe.requestEntryByTap(trigger)`），而 `refreshXxxSubscribeEntry()` **无条件**把开关置回关闭：

   ```js
   refreshXxxSubscribeEntry() {
     ...
     subscribe.entryVisibleAsync('trigger')
       .then((need) => this.setData({ showXxxSubscribeEntry: !!need, xxxSubscribeChecked: false }))
     //                                                              ↑ 无条件复位
   }
   ```

   请求一返回（不论成败）开关就被数据拽回关闭。

2. **主动点击被 7 天节流导致「无任何提示」**：`requestEntryByTap()` 把用户主动点击也交给带 7 天节流的 `guideReopen()`（`subscribe_reopen_guide_post_publish`），节流初衷是「别被动打扰」，但主动求助被节流 `if (last && Date.now() - last < 7天) return false` → 静默返回。这是「自动关闭且无解释」的确定性根因。

3. **请求为何快且无声**：`utils/subscribe.js` 的 `requestSubscribe()` 四条出口中三条不弹窗——① 无可用模板 ID（`validIds()` 为空）直接 resolve 不弹窗；② 微信侧已「拒绝/不再询问」（`reject`/`ban`/`filter`）不展示弹窗；③ 接口失败（20004 总开关关闭 / 20001 模板不可用）有 toast（已排除，因视频无 toast）；④ 正常有弹窗（已排除）。结合 `TEMPLATE_IDS` 的 `commentNew`/`commentReply` 均为真实有效 ID，最可能是 **② 微信侧已记住「拒绝」**。

### 处理

`utils/subscribe.js`：

- `requestEntryByTap` 调用 `guideReopen` 时**不再传 `throttleKey`**（节流只保留给被动触达如聊天页发送顺带引导），用户每次主动点击必得反馈。
- `requestSubscribe()` 返回值新增 `failed` 字段；`requestEntryByTap()` 新增 `guided` 字段。
- 三条静默路径全部补齐可见反馈：

  | 场景 | 修复前 | 修复后 |
  |---|---|---|
  | 微信侧已拒绝/不再询问 | 静默回弹 | 弹「微信通知已关闭」引导弹窗，带「去开启」跳设置页 |
  | 用户本次点了「取消」 | 静默回弹 | toast「未开启，可再次点击重试」/「部分未开启，可再次点击补齐」 |
  | 请求失败（20004/20001） | 已有 toast | 保留 toast，不再叠加引导弹窗 |
  | 无可用模板 ID | 完全静默 | toast「订阅模板暂不可用」+ `console.warn` 留痕 |

- 补 `TPL_LABELS`（20 个模板中文名，与服务端 `subscribeService.js` 的 `TPL_CONFIG.label` 同源一致），提示改为点名式：漏 1 项 →「评论回复通知未勾选，再点一次勾上」；漏 2+ 项 →「还有 N 项未勾选，再点一次逐项勾上」；全未勾 →「未勾选，再点一次逐项勾上」。
- 新增 `pendingTypesFor(trigger)`：**只申请还没允许的那几项**，第二次点击原生弹窗里只剩缺的项；全已授权时回退整组（`rule.keys.slice()`）用于额度耗尽后重新攒。抽出 `requestTypesByTap(types)` 复用「申请 + 落库」。

> 微信硬约束：`wx.requestSubscribeMessage` 必须在用户点击手势同步调用栈内调用，原生弹窗 `success` 回调里再调会被拒（`fail: can only be invoked by user TAP gesture`），故技术上无法自动连弹两次——只能让下一次点击弹窗只剩缺的项。

### 涉及文件·接口·表

| 文件 | 改动 |
|---|---|
| `utils/subscribe.js` | `requestSubscribe` 新增 `failed` + 无模板 ID 留痕；`requestEntryByTap` 去节流、补三类反馈、返回 `guided`；新增 `TPL_LABELS`；新增 `pendingTypesFor` + `requestTypesByTap` |
| `server/tests/top-subscribe-entries.test.js` | 新增 F3（点名式反馈）与 F4（补齐时弹窗只含缺的项）；A~E/F 断言按新语义更新 |
| `server/tests/subscribe-binding-audit.test.js` | 新增 G 组：前端 `TPL_LABELS` 与服务端 `TPL_CONFIG.label` 逐项一致 |
| `pages/chat/index.js` | 修正过时注释（原写「按 subscribe_reopen_guide_chat 节流」，主动点击现已不节流） |

### 验证

- F4 核心断言第二次点击 `tmplIds` 只含未勾选项（反向验证：换回 `typesForTrigger` 立刻变红）。
- 全量回归：**71 / 71 通过**。

### 结论与进一步建议（待拍板）

根因是交互语义：一次性订阅额度会被用尽，开关永远无法如实表达状态。建议把入口右侧 `<switch>` 改为按钮式（`[ 去订阅 › ]`），点一次申请一次授权，右侧显示真实状态文案（`未订阅` / `已订阅 · 剩余 2 次`），从根上消除「开关自动关闭」误解，也顺带解决「额度耗尽后用户不知要补订阅」。影响面：8 个页面 WXML 各一行 + `app.wxss` 的 `.sub-notice-*` 样式 + 相关测试断言，属视觉改动需确认。

## 四、订阅额度分布与发出率看板口径（2026-09-16）

### 5. 看板指标定义与计算口径（修复后）

管理后台「日志 → 订阅消息」额度看板数据来自 `GET /api/v1/admin/subscribe-logs` 的 `quota` 字段：

```sql
SELECT tpl_type tplType,
       COUNT(DISTINCT user_id) users,
       SUM(remain > 0)        availableUsers,   -- 本次新增
       SUM(remain)            remain,
       SUM(total_sent)        sent
FROM user_subscribe_quota
GROUP BY tpl_type
ORDER BY tpl_type
```

| 字段 | 含义 |
|---|---|
| `availableUsers` | **真正还有额度、还能收通知的用户数** |
| `users` | 在额度表里有该模板记录的用户数（**包含已用光的**，只表示「订阅过」） |
| `remain` | 全体用户剩余额度**之和**（总量，非人均） |
| `sent` | 累计已发送条数 |

**原口径为何让人误判**：原前端文案 `{{item.users}} 人可用 / 剩余 {{item.remain}}` 把 `users` 写成「人可用」，但它含 `remain=0` 的人，于是出现「图二 `commentNew: 20 人可用 / 剩余 30`」与「图三连续 6 条 `commentNew` 额度不足」看似矛盾。其实**不矛盾**：额度按 `(user_id, tpl_type)` 逐人独立存，剩余 30 条属于其他用户；`凋零的花瓣(68)`、`广轻观察(67)`、`欧阳文界(71)` 等人自己的额度已用光，故他们触发的每条都是 `skipped`。

**修复**：SQL 增 `availableUsers`，前端文案改为 `{{item.availableUsers}} 人有额度（共 {{item.users}} 人订阅过）/ 剩余 {{item.remain}} / 已发 {{item.sent}}`，看板顶部加口径说明。客户端对未升级服务端做了降级：`availableUsers` 缺失时 `quotaText` 退化为 `N 人订阅过 / 剩余 M / 已发 K`。

### 6. 涉及文件·接口·表（看板部分）

- 表/接口：`user_subscribe_quota`、`subscribe_message_log`、`GET /api/v1/admin/subscribe-logs`。
- `server/controllers/adminController.js`：额度看板 SQL 增加 `availableUsers`，补字段口径注释；`listSubscribeLogs` 给日志行补 `tplLabel`、额度行补 `label`。
- `pkg-admin/admin/index.wxml`：文案改为「N 人有额度（共 M 人订阅过）」+ 口径说明。

### 结论

「额度不足」是**平台硬上限**（每「允许」只 +1 条），代码无法突破；`skipped` 占多数时该解决「授权覆盖率」而非发送链路。`commentNew` 长期只能靠提高授权频次（在每次产生互动的页面给入口）。

## 五、凭据失效（access_token / 模板 ID 失效）的处理

> 与第四节同源（2026-09-16 修复说明 + 排查报告第八节）。冲突以最新（2026-09-16）为准：凭据失效的代码修复**已实现，但截至 2026-09-16 13:19 排查采集时尚未部署上线**。

### 现象

管理后台「发送失败」截图：`#733 message`、`#720 auditPass` 报 `invalid credential, access_token is invalid or not latest`；`#259/#258/#252 commentReply` 报 `argument invalid! data.thing20.value is empty`。实为**两类互不相干的失败**。

### 根因 A（真 Bug，本次修复）：access_token 被多实例互相作废

1. **用了会互相作废的 `cgi-bin/token`**：`server/utils/wechatToken.js` 原本请求 `GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&...`。微信文档明确：该接口每调用一次就签发新 token 并让上一次立即失效。而本服务是 **pm2 cluster 2 实例**，`cachedToken` 是**进程内变量**（每实例一份）：

   ```
   实例 A 缓存到期 → 刷新 → 拿到 token-A2（token-A1 作废）
   实例 B 手里还是 token-A1（本地缓存认为没过期）→ 发消息 → 微信拒绝 40001
   ```

2. **40001 不在重试列表、也没换 token 动作**：修复前 `const RETRYABLE_WECHAT_CODES = [-1, 45009, 43004]`，`callWechatSend` 遇不在列表的码立刻 return，`postToWechat` 只 `getAccessToken()` 读本地缓存。token 被顶掉后这条消息直接记 `failed` 永久失败，无自愈。

3. **为什么能确定是多实例不一致而非 token 全局失效**：看 2026-09-15 23:42~23:49 上下文，失败与成功在几分钟内交替出现（720 失败 23:42:13 → 722 成功 23:43:53 → … → 733 失败 23:49:04 → 734 成功 23:49:54）。若全局失效会全部失败。微信报错文案自身即答案：`...could get access_token by getStableAccessToken`。

### 处理 A（凭据失效）

1. `server/utils/wechatToken.js` 改用 **`cgi-bin/stable_token`**（POST JSON）：

   ```json
   { "grant_type": "client_credential", "appid": "..", "secret": "..", "force_refresh": false }
   ```

   `force_refresh=false` 时有效期内反复调用**返回同一 token**，多实例互不作废。`forceRefresh: true` 映射 `force_refresh: true`（签发新 token），**只在拿到 40001/42001 之后的自愈路径用**，常规路径绝不传。

2. `server/services/subscribeService.js`：

   ```js
   const RETRYABLE_WECHAT_CODES = [-1, 45009, 43004, 40001, 42001, 40014]
   const TOKEN_ERROR_CODES = [40001, 42001, 40014]
   ```

   命中 `TOKEN_ERROR_CODES` 打标记，下一轮 `postToWechat` 用 `getAccessToken({ forceRefresh: true })` 换新 token 重发，属可自愈错误，不该记 failed。

3. `server/scripts/verify-wechat-config.js` 也改 `stable_token`——原脚本走 `cgi-bin/token`，**跑一次就把线上正在用的 token 弄失效**，是隐藏地雷。

### 根因 B（已修复的历史记录）：`thing20` 空值

`argument invalid! data.thing20.value is empty` 是 `commentReply` 模板 `thing20`（原文内容）为空，微信返回 47003（不可重试）。该模板历史 11 次发送 **100% 失败、0 次成功**，已于 2026-09-15 修复：

```js
thing20: { value: clipOr(postDigest, 20, '你发布的帖子') }
```

截图里 `#259/#258/#252` 的时间是 2026-09-15 02:21~02:23，早于修复部署，属修复前历史流水。

### 区分两类失败

| 判据 | 凭据失效（Bug A） | 字段空值（Bug B） |
|---|---|---|
| errmsg 关键词 | `invalid credential` / `access_token is invalid or not latest` | `argument invalid! data.xxx.value is empty` |
| 涉及模板 | 随机（取决于命中哪个实例） | 固定（同一模板同一字段） |
| 时间分布 | 零散、突发 | 连续、稳定复现 |
| 是否已修 | 本次（截至排查时待部署） | 2026-09-15 已修，旧流水留库 |

### 涉及文件·接口·表

| 文件 | 改动 |
|---|---|
| `server/utils/wechatToken.js` | `cgi-bin/token` → `cgi-bin/stable_token`；`forceRefresh` 透传 `force_refresh` |
| `server/services/subscribeService.js` | `RETRYABLE_WECHAT_CODES` 增 40001/42001/40014；新增 `TOKEN_ERROR_CODES` 与换新 token 重发逻辑 |
| `server/scripts/verify-wechat-config.js` | 体检改用 `stable_token` |
| `server/controllers/adminController.js` | 额度看板 SQL 增 `availableUsers` |
| `pkg-admin/admin/index.wxml` | 额度看板文案 + 口径说明 |
| `server/tests/wechat-token-stable.test.js` | **新增** 9 组回归（A~H） |

### 验证 / 回归护栏

`server/tests/wechat-token-stable.test.js`（运行：`cd server && node tests/wechat-token-stable.test.js`）：

```
A. 常规获取走 stable_token + force_refresh=false（禁止回 cgi-bin/token）
B. 有效期内复用进程内缓存，不打微信接口
C. forceRefresh=true 透传请求体并换新 token
D. 并发调用只打一次微信接口（refreshPromise 去重）
E. 40125 映射可暴露的 503；E2 空响应抛错而非把 undefined 当 token
F. 40001 首次失败 → 强制换 token 重发成功，日志只记 sent、不记 failed
G. 40001 持续失败 → 记 failed(errcode_40001)，共 3 次后停止
H. 43101 用户拒收仍只调一次（防新增可重试码把 43101 带进来）
```

### 失败对业务/用户的影响

- 所有通知先写站内信（`system_notification` + WebSocket 实时推送），订阅消息只是增强层，**失败绝不影响下单/评论/报名/提现主流程**；`push()` 内部吞异常不抛回业务方。
- 对用户只影响「微信弹窗提醒」，站内信照常收到。
- 最近 14 天错误码：`47003` 11 条（全部在 2026-09-15 10:23 前，属历史流水）；`40001` 4 条（09-15 09:44 ~ 23:49，间歇性）。2026-09-16 当天 `failed = 0`，但非修复生效。

### 结论

凭据失效根因是 `cgi-bin/token` 多实例互作废 + 40001 未进重试/换 token 列表。修复已实现（代码 + 9 组测试），但**截至 2026-09-16 排查采集时尚未部署**，当前「安静」是间歇性故障正常表现，**不能因今天没出现就认为已修好**，仍需部署上线。

## 六、匿名私信订阅提醒（2026-09-15 修复说明）

### 现象

使用匿名（分身）私信发消息后，对方明明已开启订阅消息，却收不到任何微信提醒；且 `subscribe_message_log` **连一行记录都不留**（既无 `sent` 也无 `skipped`），与「额度不足」症状极相似，是本次排查绕弯的主因。

### 根因

`server/controllers/messageController.js` 的 `createPrivateMessage()` 把推送逻辑整块包在条件里，由 commit `a863751b`（2026-09-11）引入，理由「保留匿名性，避免泄露身份或打扰」：

```js
// 修复前
const channelAnonymous = conversation.isAnonymous || conversation.peerIsAnonymous
...
if (!channelAnonymous) {                 // ← 匿名会话永远进不来
  pool.query('SELECT nick_name FROM sys_user WHERE id = ?', [senderId])
    .then(([rows]) => subscribeService.pushMessage(receiverId, {...}))
}
```

`channelAnonymous` 是**会话级**（`isAnonymous || peerIsAnonymous`，任一侧匿名即为真），故：匿名发起方发消息 → 不推；**普通用户回到匿名会话回复 → 也不推**（很多人不知自己在「匿名渠道」）。该分支在 `writeLog()` 之前就返回，故无日志。

### 处理

| 位置 | 问题 | 修复 |
|---|---|---|
| `messageController.js`（新增 `resolveSenderNick`） | 匿名身份只能靠「不推」保护，代价功能不可用 | 抽昵称解析：**匿名方用分身昵称**（会话存档 `anon_self_identity`，与聊天页同源），匿名分支刻意不查 `sys_user.nick_name` |
| `messageController.js`（`createPrivateMessage` 推送段） | `if (!channelAnonymous)` 整块跳过 | 移除该条件，**改为无条件推送**，发送人昵称统一经 `resolveSenderNick` 解析 |
| `app.js`（新增 `noticeColdStartUnread`） | 小程序关闭期间收到消息零触达 | 冷启动拿到未读总数后延时 1.5s 给一次 toast；已在消息页不打扰，一次冷启动只提示一次 |
| `utils/messageStore.js` | — | 未改动，A1/A2 原本具备 |
| `wsServer.sendToUser()` 调用 | — | 未改动，原本就在 `if (!channelAnonymous)` **之前**，匿名私信一直有实时通道，只是不弹微信提醒 |

### 昵称判定为什么用 `isAnonymous` 而不是 `channelAnonymous`

| 谁在发 | `channelAnonymous` | `isAnonymous` | 推送该显示 |
|---|---|---|---|
| 匿名发起方 | true | **true** | 分身昵称（如「深幽的洞穴」） |
| 普通用户回复匿名方 | true | **false** | 真实昵称 |

普通用户回复时聊天页显示他自己的真名，推送文案须一致，否则对方看到的身份对不上。故判定锚定**发送方自己那一侧**的匿名标记。

### 涉及文件·接口·表

- 服务端：`server/controllers/messageController.js`（`resolveSenderNick`、`createPrivateMessage` 推送段）。
- 小程序端：`app.js`（`noticeColdStartUnread`）。
- 既有未改：`utils/messageStore.js`、`wsServer.sendToUser()`。
- 表：`private_message`、`sys_user`、`private_conversation.unread_count`、`subscribe_message_log`。
- **无数据库迁移**（不涉及表结构）。

### 验证

新增 `server/tests/anonymous-message-subscribe.test.js`（9 条，全量回归 **74 / 74 通过**）：匿名方→必调 `pushMessage` 且 `senderNick`=分身昵称；匿名分支不得查 `sys_user.nick_name`；普通私信 `senderNick`=真实昵称；**普通用户回复匿名方同样必推送**（旧实现整块跳过，核心回归点）；分身缺失兜底「匿名用户」且不查真名不产生空值（防微信 47003）；源码护栏不得再出现 `if (!channelAnonymous)`；A1 推送位于订阅前、A2 联动角标、A3 冷启动提示仅一次。

### 影响与注意事项

1. 匿名私信会消耗对方 `message` 模板额度（每次扣 1 条），同一收件人若同时收普通与匿名私信，额度更快耗尽——既有机制必然结果，非新增缺陷。
2. 消息摘要出现在微信通知（`digest` = 内容前 20 字），锁屏可见，与普通私信一致。
3. 匿名性未被削弱：发送人栏只有分身昵称，分身缺失兜底「匿名用户」，**绝不回落真实昵称**。
4. 不会刷屏：`SUBSCRIBE_MERGE_WINDOW_MS=0`（不合并）保持原样。

### 部署清单

- 服务端 `server/controllers/messageController.js`：`deploy.py`/`deploy_full.py`，改完 `pm2 restart`。
- 小程序端 `app.js`：开发者工具「上传」（A3 才生效）。
- 三端发布互不联动；真机仍显示旧聊天页入口说明上次入口改动也还没上传，本次一起发布。
