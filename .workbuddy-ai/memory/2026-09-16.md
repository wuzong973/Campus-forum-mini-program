## 概念澄清：「发送失败」≠「没额度」（用户再次问混）

用户问「发送失败是指用户没有额度了无法发送消息提示是吗」—— **不是**，两者是 `push()` 里的两条互斥分支：

- `remain <= 0` → 写 `skipped`（额度不足）后直接 `return`，**压根没调用微信**。
- `remain > 0` → 才走 `callWechatSend`；被微信拒（带 errcode）才写 `failed`（发送失败）。

所以 **`failed` 与额度无关**：14 天实测 47003 × 11（字段空值）、40001 × 4（凭据失效），**一条都不是额度问题**。

**根因是面板文案让人误读**，已改 `pkg-admin/admin/index.wxml` 的 `sub-hint`：
把原来一行平铺的「已发送/已合并/额度不足/发送失败」拆成两行，**首行专门写这条区分**
（「额度不足」= 压根没调用微信；「发送失败」= 调用了微信但被拒，与额度无关，看错误码）。
护栏加进 `subscribe-logs-endpoint.test.js` D 组（断言 WXML 里必须同时出现「额度不足…压根没调用微信」与「发送失败…与额度无关」）。

**还记下 `failed` 的第三个来源**：`push()` 末尾的 `catch` 只 `console.error` 后 `return {reason:'exception'}`，**不写日志** ——
所以异常类失败在 `subscribe_message_log` 里连一行都不留，排查时别误判成额度不足。
另两个来源：用户无 openid（自己写的 failed 日志，没调微信）、微信返回 errcode。

## 新增「弹窗触发节流层」（utils/subscribe.js）

需求：8 个触发组，同一组在用户**未勾选「总是允许」**时，一天最多弹 3 次原生授权弹窗。

**硬约束（决定了整个设计）**：`wx.requestSubscribeMessage` 必须在 tap 的**同步调用链**内调用，
所以「今天还能不能弹」必须同步判定完 → 计数只能放 `wx.getStorageSync/setStorageSync`，**不能走服务端**。

**两个本地键**（刻意分开，生命周期不同）：
- `subscribe_popup_throttle` = `{ day: 'YYYY-MM-DD', groups: { 触发组: 次数 } }` —— 跨天惰性重置。
- `subscribe_always_choice` = `{ 模板类型: 'accept'|'reject'|'ban', updatedAt }` —— 微信侧「总是」选择缓存，
  **不能按天重置**。刷新时机：`app.js onShow` + 每次 `requestSubscribeMessage` 回调后。
  键消失（用户改回「每次询问」）时**必须 delete 缓存**，否则会永久跳过节流。

**三个设计要点**：
1. 存储按**触发组**维度（`groups[trigger]`），单键 + 对象（不是每组一个键）—— 便于整体查看/清空，同步 API 无并发问题。
2. `day` 用**本地时区**（不是 UTC，否则东八区早上 8 点才换天）；**惰性重置**（不写定时器 —— 小程序无常驻定时器，整天不打开时定时器根本不会跑）。
3. 「总是允许」判定：`itemSettings[模板ID] === 'accept'`，组内**全部** accept 才算。
   **勾选后跳过节流但仍照常调用微信** —— 微信静默 accept、每次仍 +1 额度，停调等于主动掐断额度来源。

**闸门位置**：只加在 `requestTriggerByTap`。**`requestEntryByTap`（顶部入口）天然不受节流** ——
它走 `requestTypesByTap` 不经过闸门；那是用户主动点击，拦了会「点了没反应」（本项目修过的老问题）。
**计数在调用微信之前 +1**（乐观计数）：连点 5 次只调 3 次；改在回调补记会因页面卸载而漏记。

**降级**：`setStorageSync` 抛错 → 退化为不节流（宁可多弹，不能因存储异常掐断额度来源）；
`getSetting` 失败 → `refreshAlwaysChoice` resolve null 且**保留旧缓存**。

护栏：**新增** `server/tests/subscribe-throttle.test.js`（13 组 A~J）。
写测试踩的坑：**微信 `itemSettings` 是以模板 ID（长串）为键，不是模板类型名** —— 桩里按类型名写会一直判为「未勾选」。
另：测试 I 要把抛错范围限定在节流键，否则 `persistAccepted` 的 `setStorageSync` 也会抛（那是另一类问题）。

## 节流层补强：persistAccepted 保护 + 「命中节流」状态与日志

### 1. 补上 persistAccepted 的健壮性保护（用户要求）
`persistAccepted()` 原来直接调 `getStorageSync/setStorageSync` 且无 try/catch —— 它在 `.then` 里被调用，
而调用方是 `subscribe.requestTriggerByTap('x')`（没接 catch），存储抛错会冒泡成**未处理的 promise rejection**。
现已把整个循环体包 try/catch，失败只 `console.warn`。

### 2. 新增 `status='throttled'`（「命中节流」）
管理后台「日志 → 订阅消息」筛选栏最右新增「命中节流」按钮，节流命中会写一行日志。

- **为什么必须客户端上报**：节流判定在 `wx.requestSubscribeMessage` 的**同步调用链**内，服务端无从感知。
  `throttled` 是**唯一由客户端主动写入**的状态。
- 链路：`requestTriggerByTap` 命中 → `reportThrottleHit(trigger, used)`（fire-and-forget，不 await 不抛错）
  → `POST /api/v1/subscribe/throttled`(auth) → `subscribeService.logThrottleHit()` → INSERT。
- **落库映射**：`tpl_type` = 该触发组**首个模板类型**（触发组是客户端概念，服务端只认模板类型；
  用真实模板类型后台才能显示中文标签）；`summary` = 渠道文案（如「评论通知」）；`errmsg` = 「今日已弹 3 次，上限 3 次，本次不再弹窗」。
- **枚举必须同步扩展**：`subscribe_message_log.status` → `('sent','merged','skipped','failed','throttled')`，
  `migrations.js`（带 `SHOW COLUMNS` 守卫的 MODIFY COLUMN）+ `sql/init.sql` 都改了；漏了会 `ER_DATA_TRUNCATED` 截断成空串。
- **后台**：`adminController.listSubscribeLogs` 的 status 白名单加 `throttled`（漏了会让筛选静默返回全部）；
  `pkg-admin/admin/index.{wxml,js,wxss}` 加按钮 + `SUBSCRIBE_STATUS_TEXT/HINT` + `.st-throttled` 紫色角标（与 failed 的红色区分）。
- **每次都上报、不按天去重**：与 `skipped` 一样按次记录，便于看被拦频率。量级与用户点击次数同阶 ——
  嫌吵就在 `reportThrottleHit` 加一个「同组每天只报一次」的窗口（一处改动）。
- 上报失败不影响节流判定（护栏 K2）。
