## 排查：用户反馈「头像和昵称显示有问题」（两个录屏）

结论：**代码问题**，不是用户操作问题。定位到 4 个关联缺陷。

### 线上数据证据（193.112.187.95 / gqg_campus / sys_user，共 12 个用户）
| id | nick_name | avatar_url | 状态 |
|----|-----------|------------|------|
| 66 | A.Twelve | https://payun01.cn/uploads/xxx.jpeg | 正常（上传的 http 头像） |
| 67 | 你好 | /assets/avatar2/1%20(39).jpg | 本地包内资源 |
| 68 | 凋零的花瓣 | /assets/avatar2/1%20(18).jpg | 本地包内资源 |
| 69 | 校园用户 | (空) | **异常**：无头像无昵称 |
| 70 | 秋日的果园 | /assets/avatar2/1%20(53).jpg | 录屏2 用户，资料页头像空白 |
| 71 | 欧阳文界 | (空) | **异常**：无头像 |
| 72 | 欧阳志鑫 | (空) | **异常**：无头像 |
| 73 | 校园用户 | (空) | **异常**：无头像无昵称 |

即 12 人中 **4 人头像昵称为空**（69/71/72/73），命中率 1/3。

### 缺陷 1（根因）：新用户注册时昵称/头像默认值为空
`server/controllers/userController.js` → `phoneLogin()`：
```js
INSERT INTO sys_user (openid, nick_name, avatar_url, phone) VALUES (?, '校园用户', '', phone)
```
头像写空串、昵称写死「校园用户」。表结构 `nick_name` 默认值也是「校园用户」，`avatar_url` 默认 NULL。
前端 `utils/auth.js` 的 `saveUser()` 本有补偿逻辑（第 150-162 行：服务端缺头像时把本地随机头像回传），
但只跑了 `saveUser._syncedProfiles` 内存去重 —— **杀掉小程序重进就重新触发，且失败静默吞掉**（`.catch(() => {})`）。

### 缺陷 2：昵称为「校园用户」的用户永远同步不上头像
`utils/auth.js` `saveUser()` 条件：
```js
if (user.id && (!serverAvatar || avatar.isDefaultName(serverNickName)))
```
`nickName='校园用户'` 时走 syncProfile，但 `syncProfile()` 里 `avatarUrl` 依赖传参；
`utils/wechat.js` `phoneLogin()` 的补写条件写的是 `if (!data.avatarUrl && saved && saved.avatarUrl)`
—— 而 `data.avatarUrl` 此时是空字符串 `''`，`!''` 为 true 本应进入分支，
但 `saved.avatarUrl` 来自 `saveUser()` 已回填的默认头像，两者**取值链路不一致**，
导致部分路径下 defaultFields 为空对象，不发同步请求。

### 缺陷 3：`/assets/avatar2/` 路径的括号未转义，真机不渲染
`utils/avatar.js`：
```js
return '/assets/avatar2/' + encodeURIComponent(filename)   // → 1%20(9).jpg
```
`encodeURIComponent('1 (9).jpg')` **只编码空格为 %20，不编码半角括号**，
所以产出 `/assets/avatar2/1%20(9).jpg` —— 括号裸奔。
真机（iOS/Android）对本地包内路径的 `()` 解析不一致，录屏 2 中「秋日的果园」(id=70)
用的正是这个路径，资料页头像渲染为空白圆圈。开发者工具不复现（工具容错更宽松）。

### 缺陷 4：`profile_ext` 本地缓存与服务端互相覆盖
`pages/profile/index.js`（第 61-78 行）用 `Object.assign({}, profile, ext)`，
且清缓存条件写在 `["avatarUrl","nickName","campus"].forEach` 里只处理"两者都存在且不同"的情况；
当 `ext.avatarUrl` 有值而服务端为空时**不会被清理**，反而 mergedProfile 用缓存值覆盖空的服务端值，
造成「同一个人在不同页面头像不一致」。

### 录屏对照
- 录屏 1（18:24，广轻校园圈首页）：信息流里「你好」「触中的微风」正常，
  「凋零的花瓣」头像正常、「触中的微风」缺失 → 对应用户 67/68/70 数据，与缺陷 3、4 一致。
- 录屏 2（18:27，秋日的果园 id=70 资料页）：顶部头像**空白圆圈**，
  昵称「秋日的果园」、校区「南海北校区」正常显示。
  接着进入设置页，学校/校区/手机号均有值 —— 说明**只有头像渲染失败**，完美对应缺陷 3。

### 修复建议（按优先级）
1. `avatar.js` 去掉 `encodeURIComponent`，改用不含空格括号的文件名（如 `avatar_09.jpg`），
   或显式转义括号 `%28`/`%29`；同步重命名 `assets/avatar2/` 下 58 个文件。
2. `userController.js` `phoneLogin()` 新用户写库时给非空昵称+头像（或返回后由前端补写并确认成功）。
3. `auth.js` `saveUser()` 把 `_syncedProfiles` 去重改为持久化存储（`wx.setStorageSync`），
   并把 `.catch(() => {})` 改为记录失败以便重试。
4. `profile/index.js` 合并逻辑改为「服务端为空时才用本地 ext 兜底」，并在服务端有值时强制清理 ext。

## 修复：帖子详情评论区多个头像显示为灰色空圆

用户反馈截图：评论区 `萤火的夏夜`（4 条）、`零落的花瓣` 头像为灰色空圆，
但同屏 `你好` 头像正常。**根因是 `success()` 的头像归一化漏了下划线字段名。**

### 根因（关键，容易再犯）
`server/middleware/auth.js` 的 `AVATAR_KEYS` 只列了**驼峰**键：
```js
['avatarUrl','avatar','actorAvatar','anonAvatar','fallbackAvatar']
```
但 `commentController.presentComment()` 返回的是 MySQL 原始行数据，字段是**下划线**：
```js
{ nick_name: ..., avatar_url: ... }
```
`AVATAR_KEYS.indexOf('avatar_url') === -1` → **归一化对评论完全没生效**。
而帖子走 `utils/api.js` 的 `mapPost()`（字段是 `avatarUrl` 驼峰）所以正常 ——
这解释了"为什么帖子头像好、评论头像坏"。

叠加历史数据：`sys_user.avatar_url` 存在旧路径 `/assets/avatar2/1 (39).jpg`，
文件已重命名为 `avatar_39.jpg`，旧路径真机渲染失败 → 灰底空圆（`background:#edf1f6`）。

### 修复（三道防线）
| 层 | 文件 | 改动 |
|---|---|---|
| 服务端(出口) | `controllers/commentController.js` | `presentComment()` 直接调 `normalizeLegacyAvatarUrl()` |
| 服务端(全局) | `middleware/auth.js` | `AVATAR_KEYS` 补下划线变体：`avatar_url`/`actor_avatar`/`anon_avatar`/`fallback_avatar` |
| 前端(兜底) | `pages/post-detail/index.js` | `normalizeComment()` 调 `avatar.normalizeLegacyAvatar()`，且空值兜底 `/assets/icons/avatar.png` |

前端那道是**最后防线**：即使服务端数据没修好，也在渲染前修正，且空头像不再显示灰圆。

### 验证
`normalizeLegacyAvatarUrl` 8 个用例全通过（编码空格 / 裸空格 / 个位数 / 最大编号 /
新路径原样 / 匿名头像 / 用户上传 / 空值）。模拟 `presentComment` 4 行数据：
旧路径正确转为 `avatar_39.jpg`、`avatar_18.jpg`；新路径与 http 头像不受影响。

### 教训（长期，务必记住）
**头像归一化的字段名必须同时覆盖驼峰与下划线两种命名。**
控制器直接返回 MySQL 行数据时字段是下划线的；经前端 mapper 转换后才是驼峰。
新增任何头像字段（或新增返回原始行数据的接口）时，都要同步检查这里。

### 注意
`repairUserAvatars()` 只在**服务端启动时**跑一次。若旧路径数据是启动后由旧版
客户端写入的，不会被修复 —— 所以「服务端出口归一化」比「批量修库」更可靠，
两者要同时存在。

## 修复：首页私信入口进入聊天页，「回到帖子」误回首页

### 现象
首页右下角私信入口 → 私信列表（`pages/my-messages`）→ 点用户头像进聊天页 → 点顶部「回到帖子」
→ 错误地返回**首页**，而不是用户最初在帖子详情页点用户头像发起私信的那个帖子详情页。

### 根因
`pages/chat/index.js` 的 `resolveBackToPost()` 判定顺序里，「返回页面栈中的帖子列表页」
（第 4 条，含 `pages/index/index`）排在「按本地缓存/服务端来源帖子」兜底（原第 5 条）**之前**。

而首页是 **tabBar 常驻页面**，永远躺在页面栈底部。该路径栈为 `index → my-messages → chat`：
- 入口未带 `postId`（`my-messages` 不带），第 1/2/3 条全部落空；
- 第 4 条命中栈底的 `pages/index/index` → `delta` 指回首页，且 `showBackToPost=true`
  → 导致服务端来源帖子的补显分支（原逻辑 `if (!showBackToPost)`）**被跳过**，无法纠正。

通知入口（`my-messages → chat`，栈里无 `index`）因为命中该分支才表现正常 —— 这就是两条路径行为不一致的原因。

### 修复（`pages/chat/index.js`）
1. **调整优先级**：新增第 3' 步 —— 入口未带 `postId` 时，先读本地缓存的来源帖子并直接跳转，
   让来源帖子**优先于**列表页兜底；列表页兜底降级为第 4 步。
2. **引入 `precise` 标记**：解析结果区分「精确帖子目标」与「列表页兜底」（`precise:false`）。
3. **纠正兜底**：历史接口返回后，条件由 `if (!showBackToPost)` 改为
   `if (!showBackToPost || !this._backToPostPrecise)` —— 列表页兜底结果可被服务端真实来源帖子覆盖
   （同时把 `_backToPostDelta` 重置为 0，避免残留 delta 指回首页）。

### 测试

## 排查：Console 报错「帖子不存在」+ 帖子详情页白屏

### 报错定位
截图两条红字其实是**两件独立的事**：

1. `Failed to load image .../assets/avatar1/%E8%80%83%E6%8B%89%20(2).jpg net::OK`
   —— **历史遗留噪音**。文件名含空格+半角括号，真机/工具解析不一致。
   该文件已在 2026-09-11 早期批次改名为 `考拉2.jpg`，但**本地存储里可能仍缓存着旧路径**（如 `profile_ext`、老帖子的 `avatar_url`）。
   属于"看着吓人但不影响功能"，可通过清缓存或服务端 `repairUserAvatars()` 归一化解决。

2. **`GET https://payun01.cn/api/v1/post/44 → 404 帖子不存在`** ← **白屏的直接原因**。

### 根因（两层）
**第一层：数据层。** 线上 `forum_post` 中 **id=44 的帖子确实不存在/已被删除**（`status=0`）。
证据：同一时间 43/45/58/59 都返回 200，**只有 44 返回 404**，排除接口与数据库整体故障。
`postController.detail` 的 SQL 硬性带 `AND p.status = 1`，软删除的帖子必然 404。

**第二层：代码缺陷（真正的"报错"来源）。** `pages/post-detail/index.js` 的 `onLoad` 中：
```js
this.loadPost(id);                                              // ← 无 .catch()
this.loadComments(id, ...).catch(() => toast('评论加载失败'));   // ← 有 .catch()
```
`loadPost` 内部只处理了 `post` 为 falsy 的分支，**未处理 Promise reject**。帖子被删除时接口抛 404，
返回的 rejected Promise 无人接管 → 变成**未捕获的 Promise 异常**打红到 Console（就是截图里那一坨堆栈）。
同时 `setData` 从未执行，页面停在**空白骨架**，用户没有任何反馈。

### 修复
**`pages/post-detail/index.js`**
- `loadPost()` 末尾补 `.catch(() => this.handlePostMissing())`，兜住接口失败（含 404 已删除）。
- 抽出 `handlePostMissing()`：`_postMissingHandled` 去重保护 + toast「帖子不存在或已被删除」+
  1.5s 后 `navigateBack`（失败兜底 `switchTab` 回首页）。原 falsy 分支也改走该方法，逻辑统一。
- 三处调用点（`onLoad`、`onShow` 刷新、分享返回）都经此路径，自动获得兜底。

**`pages/chat/index.js`**
- `onBackToPost()` 的 `navigateTo` 补 `fail` 回调：来源帖子被删除时提示「帖子不存在或已被删除」，
  避免按钮卡在 `returning` 半透明态不可再点。

### 验证
- 两个文件 `node --check` 通过；`chat-back-to-post.test.js`、`local-imports.test.js` 全通过。
- 用 vm 沙箱模拟 `getPostDetail` reject：修复前触发 `unhandledRejection`，修复后
  toast=「帖子不存在或已被删除」、navigateBack 1 次、**无未捕获异常**。

### 结论给用户
**44 号帖子不是被这次改动弄没的，它本来就被删了。**
上一轮修好「回到帖子」后，按钮能正确跳回原帖子了，才把这个历史删除帖暴露出来。
属于"修复生效后暴露的既有数据问题"，代码侧已加兜底，不会再白屏/报红。

**实现上已抽象掉这个差异**：`SEMESTERS` 每项显式声明 `firstWeekSunday` 字段，
`weekOfSemester()` 内部比较 `firstWeekSunday === startDate` 决定 `weekBase` 取 1 还是 2。
**换学年时不要照抄公式，要重新核对开学日是周几、第 1 周是否完整。**
