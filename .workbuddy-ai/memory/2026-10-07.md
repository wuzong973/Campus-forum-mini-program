### 用户原话

### 根因（「抄了一半」）
帖子详情页（`pages/post-detail/index.wxml`）里自己的评论有**两个入口**：

## P0 线上故障：发布跑腿 100% 失败（「数据库操作失败」）

### 现象
用户贴图：填完发布跑腿表单点「支付发布」，toast 报 **数据库操作失败**。

### 定位链路（可复用的排障范式）
1. **文案溯源**：`数据库操作失败` 是 `server/utils/helpers.js` 的 `safeMessage()` 对 **`ER_*` 的唯一降级文案** → 一定有真实 SQL 报错被吞。
2. **日志定性**：`grep '/api/v1/errand' logs/out.log` → `POST /api/v1/errand 500` 连续 5 次，**每次 ~1.1s**。
   （1.1s 不是 SQL 报错的毫秒级 → 说明前面还有慢操作；后查证是 `contentSecurity` 调微信 `msg_sec_check` 的网络耗时。）
3. **排除表结构**：只读探针查 `errand_order` → 43 列全在、INSERT 的 23 列都能 `SELECT ... LIMIT 0` 解析 → **不是缺列**。
4. **排除代码漂移**：`errandController.js` 本地与线上 **sha256 完全一致** → 不是部署不一致。
5. **决定性一步 —— 在生产库事务里复现那条 INSERT**（跑完 rollback，零副作用）：
   ```
   code    : ER_WRONG_VALUE_COUNT_ON_ROW
   errno   : 1136
   sqlState: 21S01
   message : Column count doesn't match value count at row 1
   ```

### 根因
`errandController.exports.create` 的 INSERT：

| 项 | 数量 |
|---|---|
| 列清单 | **23** |
| VALUES 里的 `?` | **21**（应为 22） |
| 传入参数 | **22** |

末列 `payment_status` 用字面量 `'UNPAID'`，所以 VALUES 应是 **22 个 `?` + 1 个字面量**。实际只有 21 个 `?` → 22 个值塞 23 列 → MySQL 拒绝。

**回归点**：提交 `7562640` 往列清单加了 `private_info` + `private_images` 两列、参数也加了 2 个，**但 VALUES 只加了 1 个 `?`**。
（`9e655f8` / `5260cb4` 都是 21 列 / 20 占位符，配平；`7562640` 起变成 23 列 / 21 占位符。）

### 修复
1. `server/controllers/errandController.js`：补上缺失的第 22 个 `?`。
2. 同文件 `create` 的 catch 补 `console.error('[errand.create] 建单失败:', code, message)` —— **本次排障最大的障碍就是「真实错误被吞且不落日志」**，照 `userController.verifyRiderByJw` 的范式补。
3. **护栏加强** `server/tests/sql-placeholder-param-count.test.js`：
   - **盲区修复**：`extractCalls` 原来只认 `"` 与 `'`，**模板字符串（反引号）被整条 `continue` 跳过** → 这条 INSERT 从未被检查。加上反引号支持（含 `${}` 插值的动态 SQL 仍跳过）。
   - **新增判据**：`INSERT 列清单个数 == 每行 VALUES 值的个数`（含多行 VALUES）。专治「删列忘了删参数」——此时 `?` 与参数仍配平，只看旧判据会漏。
   - **新增可诊断性判据**：`errandController.create` 的 catch 必须含 `console.error(`（断言调用表达式本身）。
4. 部署 `errandController.js`（备份 `.bak-20261007-122057`）。

## Bug 修复：回复子评论却显示父评论（事件冒泡覆盖）

### 现象
用户贴图：在评价页点**子评论**（如「严寒的隆冬」）去回复，底部提示却显示 **「回复 广轻观察」**（父评论作者）。

### 根因：`bindtap` 冒泡，父级 handler 覆盖了子级的结果
`pages/review/target.wxml` 的结构是：

```
<view class="comment-content-wrap comment-reply-trigger" bindtap="onReplyComment" data-id="{{item.id}}">
  ...正文...
  <view class="reply-list">
    <view class="reply-item" bindtap="onReplyComment" data-id="{{reply.id}}" data-nick="{{reply.nickName}}">   ← 嵌在父级内部
```

`bindtap` **会冒泡**：点子评论时
1. 先触发子评论自己的 handler → `replyTo = reply.id` ✅
2. 紧接着冒泡到父容器又触发一次 → **`replyTo = item.id` 覆盖** ❌

`onReplyComment` 读的是 `e.currentTarget.dataset`，所以第二次触发时拿到的是父评论的 id/nick。

**对比基准**：`pages/post-detail`（评价页是照它复刻的）**两处都用 `catchtap`**（阻止冒泡）→ 不会覆盖。
**是复刻时把 `catchtap` 误写成了 `bindtap`。**

### 修复
`pages/review/target.wxml` 两处 `bindtap="onReplyComment"` → **`catchtap="onReplyComment"`**：
- L73 父级 `.comment-content-wrap.comment-reply-trigger`
- L121 子评论 `.reply-item`

（父级也要改 `catchtap`：否则点子评论时事件会继续冒泡到 `.comment-item`；且与 post-detail 保持一致。）

### 护栏（已加）

## 需求：评价页评论展示逻辑对齐帖子详情页（提交置顶 → 刷新归位）

### 需求
「评论后先显示在最上面，刷新后回到属于它的位置，回复也一样」—— 与帖子详情页一致。

### 根因：评价页的 buildCommentTree **完全不排序**
| | 顶层排序 | 回复排序 |
|---|---|---|
| **post-detail** 客户端 | `sortComments(roots, sort)` + `pin` 置顶 | 时间正序 |
| **post-detail** 服务端 | `like_count DESC, created_at ASC`（likes）/ `created_at DESC`（time） | — |
| **review/target** 客户端 | **无排序**（roots 按 flat 顺序 push） | 按 flat 顺序 |
| **review/target** 服务端 | `like_count DESC, id DESC`（likes）/ `id DESC`（time） | `id ASC` |

→ `flat.concat([comment])` 后新评论落在 **roots 最末尾 = 列表最底部**。

### 修复（`pages/review/target.js`，1 个文件）
1. 新增 `sortCommentRoots(roots, sort)` / `moveToTopById(list, id)` 两个模块级助手（对齐 post-detail）。
2. `buildCommentTree(flat, expandedIds, sort, pin)` 增加 `sort` / `pin` 两个参数：
   - 顶层按 `sort` 排序；`pin` 时把刚提交那条临时置顶；
   - 回复恒按 **id 正序**（= 服务端顺序）→ 新回复落在所属评价的回复列表末尾。
3. `onSend`：`const pin = parentId ? null : { rootId: Number(comment.id) }` —— **顶层传 pin、回复不传**；
   并新增 `findCommentRootId()`，回复提交后**自动展开所属评价**（新回复立即可见）。
4. 另两处重建点（`loadComments` / `applyCommentRemoval`）**不传 pin** → 刷新/翻页/切排序都走真实排序。

### ⚠ 关键点：客户端排序必须对齐「各自服务端」的 ORDER BY，不能照搬
两个服务端 likes 的**次级键不同**：
- post-detail：`like_count DESC, created_at ASC`
- review：`like_count DESC, **id DESC**`

所以 review/target 的 `sortCommentRoots` 用 `likeCount DESC || id DESC`，**没有**照抄 post-detail 的
`sortComments`（后者是 `likeCount DESC || timeA - timeB`）。照搬会导致「刷新后回到属于它的位置」时
因 tie-break 不同而**再跳一次**。
**通用：客户端本地排序是「服务端排序的镜像」，两边 ORDER BY 不同时不能互抄。**

### 护栏
`review-comment-parity.test.js` 新增 **G 组**（现 27 项全绿）：顶层必须排序、必须支持 pin、
回复必须 id 正序、likes 次级键必须与服务端一致（并反向断言服务端 SQL 口径）、
`onSend` 必须「顶层传 pin / 回复不传」、必须自动展开、其余两处重建点不得传 pin。

**反向验证 6/6 全被捕获**：顶层不排序（复现原 bug）/ 去掉 pin / 回复也置顶 / 回复改倒序 /
likes 次级键不一致 / 回复后不自动展开。

## Bug 修复：评价页回复子评论不显示「回复 xxx」前缀

### 现象
用户贴图：评价页回复**子评论**时没有「回复 某某：」前缀；帖子详情页有（图二为期望）。

### 根因：服务端把 `parent_id` **收口成了顶层**，「回复的是谁」被丢掉
| | 回复「回复」时存的 `parent_id` |
|---|---|
| **帖子详情页** `commentController.js:157` | **实际父评论 id**（不收口）→ 端上 `parent.parentId` 为真 → 前缀显示 ✓ |
| **评价页** `reviewController.js:790`（旧） | `Number(parent.parent_id) \|\| Number(parent.id)` → **压平成顶层** → 端上判据恒假 → 前缀永远为空 ✗ |

端上逻辑本身是对的（`node.replyToNick = parent && parent.parentId ? parent.nickName : ''`），**只是永远收不到正确数据**。

### 改动（1 个服务端文件 + 1 个端上文件）
**服务端 `reviewController.js`**：
1. **`addComment`**：`parentId = Number(parent.id)` —— 存**实际被回复的那条**（与论坛评论同款），不再压平。
2. **`comments` 接口**：加 `rootIdOf()`（沿父链**循环**上溯）用于「归属本页顶层」过滤与排序。
   ⚠ 旧的 `rootIdSet[c.parentId]` 假定 parent_id 恒为顶层，改存真实父级后会把「回复的回复」**整条漏掉**。
3. **`deleteComment`**：改为**逐层 BFS 收集后代**（与论坛评论同款）。
   ⚠ 旧的 `WHERE parent_id = ?` 只删到第一层，更深的回复会变成点不到的孤儿。

**端上 `pages/review/target.js`**：
4. `buildCommentTree` 的「上溯到顶层」从**只往上一层**改成**循环**：
   `const rootOf = (node) => { while (current.parentId && byId[current.parentId]) … }`
   ⚠ 只往上一层时，「回复的回复的回复」会掉成顶层 → 渲染错位。

### 兼容性
- **历史数据无法回溯**：已有回复的 `parent_id` 已被压平成顶层，「回复的是谁」已丢失 → 它们不会显示前缀（预期）。
- 新回复起正常显示；展示层级由端上上溯归并，仍只两级。

### 护栏
- `review-module.test.js`：客户端桩数据改为 `丙(13).parentId = 12`；断言 `parentId = [11, 12]` 且
  **`replyToNick = ['', '乙']`**（回复顶层无前缀、回复「回复」有前缀）；服务端 C2 用例改为断言
  `insert.params[1] === 52`（存真实父级）；**新增 2 条 `deleteComment` 用例**（顶层逐层收集后代 / 回复只删自身）。
- `review-comment-parity.test.js` G 组：新增静态断言「`buildCommentTree` 必须**循环**上溯」。

**反向验证 4/4 全被捕获**：服务端又收口成顶层 / 端上上溯只一层 / 端上不显示前缀 / 删除退回「只删一层」。

### ⚠ 通用教训
> **「写入口做了数据压平」会永久丢掉信息，下游再想用就补不回来了。**
> 展示层级（只两级）是**端上的渲染决策**，不该让服务端把 `parent_id` 压平来实现 —— 那是把渲染逻辑写进了存储。
> **存储要保真，展示可归并。**

### ⚠ 写这类扫描器踩的两个坑（都写进了测试文件头注释）
1. **词法剥离必须识别正则字面量** —— 否则源码里的 `/["']/` 会被当成字符串开头，
   把后续源码整段吞掉 → 误报从 0 暴涨到 **189 处**。修好后降到 60。
2. **取 JS 方法名必须容忍 `async` 前缀** —— `async onSend() {` 若判据只认 `name(`，
   会把所有 async 方法判成「不存在」→ 剩余 60 处全是误报。修好后归 0。
   判据：`/^(?:async\s+)?([A-Za-z_$][\w$]*)\s*(?=[(:])/`。
3. 另两处小坑：内置组件白名单要含 `checkbox-group`/`radio-group`/`label`/`form`；
   路由解析时「变量名 → 路由文件」的 require 与 `app.use` **分处不同行**，必须分开解析
   （否则 260 条路由全解析成 0）；服务端与前端路径归一化都要剥掉 `/api/v1` 前缀。
4. 「wxml 引用了但 js 未声明」的检查**必须先把 `{{}}` 里的字符串字面量抹掉** ——
   否则 `{{x ? 'chip active' : ''}}` 里的 CSS 类名会被当成数据字段（56 页误报 → 修好后 3 页）。
