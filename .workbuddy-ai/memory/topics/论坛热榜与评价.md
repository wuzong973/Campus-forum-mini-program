## 匿名身份
- **⚠ 默认昵称池 = 匿名分身昵称池的子集（100%，70/134）** —— `defaultProfile.js` 的 `DEFAULT_NICK_NAMES` 既做**新用户默认昵称**，又被 `utils/avatar.js` 的 `DEFAULT_NAMES` 整体包含做**匿名分身名**。后果：**真实用户昵称与匿名分身字面无法区分**（实测 714/876 = 81.5% 撞名），用户以为点的是分身、实际进了真人主页。**判定匿名只能靠 `anonymous_identity`，绝不能靠昵称或头像路径猜** —— `notificationController.list()` 用 `actor_avatar.startsWith('/assets/avatar1/')` 反推匿名，路径一旦被归一化改写就会暴露匿名者。**一个「身份标识池」不能同时承担真名与分身名两种语义。**
- **匿名判据**：评论/帖子看 `anonymous_identity IS NULL`（`forum_post` **没有** `is_anonymous` 列）；通知看 `system_notification.actor_user_id` 是否为空。**匿名帖不隐藏校区**。

## 热榜
- **唯一数据源** `GET /post/hot-rank`；4 个展示位全走它；前端统一 `utils/hot-rank.js`，服务端过滤已正确 —— **别先怀疑这里**。
- **刷新约定**：`navigateTo` 推入的页面常驻，从榜单进详情删除再返回**只触发 `onShow`** —— 每个热榜展示页必须在 `onShow` 重拉（`_loadedOnce` 跳首次）。已删帖本地广播 `markPostRemoved()`/`filterRemovedPosts()`（键 `hot_removed_post_ids`，TTL 10 分钟）。

## 消息点评论 → 直接进详情定位
- `my-messages.onOpenNotification` 互动通知（有 `postId`）**直接跳 `post-detail?id=&commentId=<sourceCommentId>`**（无中间页）；链路 `source_comment_id` → API `sourceCommentId` → `commentId` → `_pendingCommentAnchor` → `resolveCommentAnchor` 出 `comment-<id>`/`reply-<id>`。**⚠ `type:'like'` 通知原先不带 `sourceCommentId`，已补。**
- **⚠ `scroll-into-view` 与「高亮样式」必须用两个字段**：`scroll-into-view` **值被清空立刻跳回顶部**，只在值变化时触发 → 同一字段兼做锚点+高亮时，高亮淡出（清空）会把页面弹回顶部。正解：**`commentAnchor` 常驻只滚动（从不置空）；`commentHighlight` 单独承载视觉高亮（定时 2.4s 清空）**；必须**先设锚点 → 下一帧再开高亮**。凡「滚动定位 + 临时视觉反馈」共存处一律照此拆字段。

## 校园评价（review）
- **表结构**：`review_target` 单表**自关联**两层 —— `parent_id IS NULL` = **根级**（食堂 / 商圈门店 / 课程），`parent_id = <id>` = **子级**（档口 / 店铺）。父级与子级是**不同行**，计数**都按 target_id 自身统计**。
- **两级评论树** `review_comment.parent_id`（0=顶层，>0=回复）：**服务端两级收口**（杜绝三级深链），端上 `buildCommentTree` 防御性上溯。**分页单元是「顶层评价」不是「行」**（否则一页内回复把顶层挤到下一页 → 回复变孤儿）：`hasMore` 只看顶层数，`total` = 顶层 + 回复。
- **`comment_count` 一律全量重算**（`refreshCommentCount`），不写 ±1；`migrations.js` 启动时对 `rating_sum`/`rating_count`/`comment_count` 做 `WHERE <>` 对账。端上取服务端回传值，**不本地 +1**。
- **⚠ 根级食堂 / 商圈 = 「容器」，不可评分（2026-10-06 改造）**：服务端 `mapTargetRow` 下发 **`rateable`**（`!容器 || category==='course'`）与 **`commentTotal`**（容器 = 全部子级 `comment_count` 之和，走**独立聚合查询** `JOIN review_comment GROUP BY t.parent_id` —— **不能用 JOIN SUM，一对多会重复累加**）；`exports.rate` 对容器 **400 拒绝**；`exports.random` 食堂/商圈**恒只抽子级**。端上按容器分支输出 **`'有 N 条评论'`**。
  **通用原则：把「父级」降级为「容器」时，必须同时处理 ① 自身评分入口 ② 列表计数口径（聚合子级）③ 详情页评分区 ④ 随机/推荐抽取的候选集 —— 漏掉 ④ 会抽到没有评分卡的对象。**
- **「移除可评分性」要选功能层而非数据层**：子级靠 `parent_id` 关联，删掉根级行会破坏层级 —— 正解是把根级标记为容器（仍在表里，仅降级）。

## 评论系统：帖子 ↔ 校园评价 对照（详见 `docs/校园评价评论_对齐帖子评论_对照梳理.md`）
- **两套评论并行**：`forum_comment`（挂 `post_id`，下划线出参）与 `review_comment`（挂 `target_id`，驼峰出参）。**命名风格差异是有意的，不要「修正」**。
- **评价侧多处更严，别为对齐而倒退**：① 分页单元 =**顶层**；② 计数 =**全量重算**；③ 有父级归属校验 + 图片硬限；④ **两级收口在服务端**（帖子收口在端上，可被绕过）。
- **评价侧写入侧三大缺口（P0）**：① `POST .../comments` **未挂 `contentSecurity`**；② **匿名身份不按评论区复用**（每次重新生成 → 同一对象下分身各不相同）；③ **完全没有删除评论接口**。
- **`likeComment` 无 `createNotification`**（帖子有）；补时**必须加「首次点赞才通知」判据**（对齐帖子 `likedNow`），否则重复点赞重复通知。
- **必须差异化**：评价**无「楼主」** → 删除权限建议**仅「评论作者 + 管理员」**；**无「蹲对象」** → `follow` 通知不适用。
- **软删语义**：评价用 `deleted` + `status` **双字段**，所有读写必须统一 `deleted=0 AND status=1`；帖子只用 `status`。
