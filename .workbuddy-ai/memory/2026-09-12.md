## 修复：群聊表单字数统计导致 WXML 编译失败

**报错**：`pkg-admin/admin/index.wxml` 编译失败 `Bad value with message: unexpected token`，定位第 1023 行。

**根因**：上一节群聊表单里写的 `{{(form.xxx || '').length}}` —— **WXML 表达式解析器不支持「括号分组后再取属性」**（`(...).length`）。全项目仅这 5 处这么写，且第 1023 行是文件内首次出现，所以报错停在 1023。

**修复**：改为项目里已验证可用的「先取属性再兜底」写法 `{{form.xxx.length || 0}}`，共 5 处：
- 1023 `form.name` /30、1039 `form.intro` /300、1043 `form.notice` /500、1050 `form.ownerName` /32、1092 `form.meta.images` /5

安全性：这些字段在 `beginChatGroupCreate` / `beginChatGroupEdit` 里都初始化为 `''` 或 `[]`，且标记只存在于 `wx:elif="{{form.kind === 'chatGroup'}}"` 分支内。

**经验（写 WXML 时注意）**：
1. 禁止 `(a || b).length`、`(a || b).x` 这类写法 → 改 `a.x || 0`；
2. 禁止 `?.` / `??` / 箭头函数 / 模板字符串 / `{{}}` 内方法调用（`.map()` 等）；
3. `{{}}` 内不要出现全角括号等非 ASCII 字符（中文字符串字面量除外）。

已用脚本全量扫描该 wxml 的 `{{}}` 表达式，确认无其他非法写法；文件保持 UTF-8 无 BOM、LF 换行（字节数 103455 → 103440，正好等于 5 处 × 3 字符）。

## 修复：提现审核打款失败（微信商户运营账户余额不足）

**现象**：后台提现审核点「通过」报 `NOT_ENOUGH 商户运营账户资金不足`，接口返回 502；管理员看到商户平台「基本账户 2.00 元」却提不出来。

**根因（资金规则，非程序 bug）**：微信「商家转账」**只能从【运营账户】出款**；用户付款结算进的是【基本账户】，**基本账户只能收款**，按结算周期打给商户自己的结算银行卡。且微信自 2022 年底起**取消了「基本账户 → 运营账户」的划转**，运营账户**只能用银行卡充值（专款专用）**。截图里基本账户的 2 元不能用于给用户打款，运营账户 0 元 → `NOT_ENOUGH`（HTTP 403 只是微信表达"拒绝"，不是权限问题）。

**运营解法**：商户平台 → 交易中心 → 充值/转入 → **入款账户选「运营账户」** → 扫码/网银充值（银行卡）→ 回后台点「重试打款」（**必须原商户单号**，不要驳回让用户重申请，否则白耗用户每日 5 次提现额度）。官方文档：<https://pay.weixin.qq.com/doc/v3/merchant/4013747269>

**代码改动**：
1. `server/services/wechatPayV3Service.js` 新增 `describeTransferError(error)` → `{ code, message, hint }`，覆盖 9 类微信错误。**分支顺序有坑**：openid 判断必须排在通用「场景/参数」分支前（openid 不匹配时微信也返回 `PARAM_ERROR`）。
2. `server/controllers/walletController.js`：失败改用翻译后的提示 + `last_error` 存 `结论｜指引`；返回 **422 + `{code,hint}`**（原为裸 502，会被当成网关故障且触发前端重试）；`listWithdrawals` 回传 `lastError`。
3. `server/middleware/auth.js`：`fail(res, message, code, data = null)` 增加可选 data（旧契约不变）。
4. 后台：审核失败改 `wx.showModal` 弹完整原因+指引（原来 `catch (e) {}` 静默吞掉）；请求加 `silent`；列表显示「上次打款失败：结论」并多一个「重试打款」按钮；`admin.js` 的 `post`/`reviewWithdrawal` 支持透传 opts。
5. 新增 `server/tests/wallet-withdraw-error.test.js`（已入 `npm test`），含**反例护栏**：禁止再出现「把基本账户资金划转到运营账户」的错误指引。
6. 文档：`docs/修复说明_2026-09-12_提现失败运营账户余额不足.md`。

**验证**：`npm test` 10 个测试文件全绿；5 个改动 JS `node --check` 通过；wxml 标签配对与表达式合法性通过。

**踩坑教训**：给运营写指引前必须查微信官方文档。我第一版写的「把基本账户资金划转到运营账户」是**错的**（微信已取消该划转），靠测试里的反例护栏 + 联网核实官方文档才发现并修正。

## 设计：小程序内嵌管理后台迁移至独立 Web 管理后台（方案文档，未动代码）

**产出**：`docs/Web管理后台迁移方案.md`（8 节 + 2 附录），另建 `.workbuddy-ai/memory/MEMORY.md` 沉淀管理后台架构事实。

**现状盘点（读码结论）**：
- `pkg-admin/admin/index.*` 单页 10 个一级 Tab（含 3 个合并父级菜单 / 7 个子页），覆盖约 50 个 `/api/v1/admin/*` 接口、8 个权限点。
- 接口按权限分布：config.manage 25 / content.manage 12 / admin.manage 6 / user.manage 5 / item.manage 3 / payment.manage 2 / stats.view 2 / role.assign 1。
- **两处「接口已实现但小程序端无界面」**：`GET /admin/audit-logs`、`GET/PUT /admin/features`（功能开关目前只能改库）。Web 端可纯增量补齐。

**核心结论**：
1. **后端零重建** —— `/api/v1/admin/*` 是纯 JSON + Bearer 的客户端无关接口，Web 直接复用，不做 BFF。
2. **数据库单库共享** —— 禁止双写/同步；管理端写操作必须继续走现有 service（如 `walletController.reviewWithdrawal`），避免资金状态机分叉。
3. **认证必须新建** —— `phone-login` 依赖 `wx.login` code + `getPhoneNumber` code，浏览器拿不到；`sys_user` 无密码字段。给出三方案对比（账号密码 / 小程序扫码 / 短信），推荐「阶段一账号密码+TOTP 快速解锁（不改小程序），阶段二扫码登录为主通道」。
4. **权限不用重做** —— 服务端 `ROLE_PERMISSIONS` 已是真源，`/admin/me` 下发 role+permissions，Web 只需实现按权限渲染。

**重点风险**：令牌同源（单密钥无 aud，建议加 `aud:'admin-web'` + 短 TTL）；接口字段驼峰/下划线混用需 Web 侧 adapter；列表无 `total`、筛选能力弱；全局限流 120/min 且 cluster 不共享（建议 Redis 限流 + admin 单独配额）；审计 IP 需确认 Nginx 透传；资金操作需二次确认 + 幂等键 + 留痕；手机号等个人信息需脱敏展示与导出留痕。

**未做**：按用户要求「暂不需要动代码」，仅设计稿。

**补充核查（同日）**：用户追问"还差什么"，复查代码后发现方案文档两处描述与实现不符，已修正并新增第 9 节「启动前缺口清单」：
1. **限流描述有误**：`server/middleware/rateLimit.js` **已支持 Redis**（Redis 可达则全局共享计数，不可达静默降级为内存态），不是纯内存。且全局限流挂在 `auth` **之前**，key 取 `req.userId || req.ip` 时 userId 尚未解析 → **实际按 IP 计数**，同一 NAT 出口的管理员共享 120/min。
2. **CORS 是硬阻塞（新发现）**：生产 `CORS_ORIGIN=https://payun01.cn` 为**单值白名单，不含 admin 域**。小程序 `wx.request` 不发 `Origin` 所以现状无感，但浏览器跨域会被直接拦截。上线前必须加白名单（`app.js` 支持逗号分隔多值）。
3. **接口契约文档严重不足（新发现）**：`docs/api-contract.md` **仅 46 行**，admin 相关只列了 3 个端点（实际约 50 个）→ 这是 Web 前端开发的前置输入，必须先补齐。
4. 其他确认：仓库**无 `web/` 前端工程目录**、**无 CI 配置**、`server/package.json` **无 bcrypt/argon2**；`.env.example` 已含完整 Redis 与 COS 配置项。

**新增产出**：`docs/Web管理后台_推荐路径与决策备忘.md`（决策层文档）。给出的推荐结论：
- **D1 认证**：账号密码优先（不依赖小程序发版；该项目刚被微信审核驳回过一次，审核是排期风险），扫码登录排到第二迭代；能碰钱的角色第二迭代加 TOTP，MVP 用 IP 白名单兜底。
- **D2 部署**：独立子域 `admin.payun01.cn`（便于叠 IP 白名单 + 与 web-view H5 隔离）；备选同域子路径 `payun01.cn/admin`（天然无 CORS）。
- **D3 技术栈**：Vue 3 + Vite + TS + Element Plus + Pinia。**决定性理由：WXML → Vue 模板近乎机械映射**（`wx:if`→`v-if`、`wx:for`→`v-for`、`{{}}` 一致、`bindtap`→`@click`），1234 行 WXML 翻译成本最低。
- **排除方案**：Taro/uni-app 编译 H5（产出移动端布局，桌面表格/批量操作作废）；一次性迁完 10 个 Tab。
- **第一期只做 4 个模块**：登录+权限守卫、概览、帖子+举报、提现审核+异议裁决；其余低频模块双端并行期继续用小程序入口。
- **上线三件不能省**：CORS 白名单加 admin 域、管理端按 userId 独立限流、后台 IP 白名单。
